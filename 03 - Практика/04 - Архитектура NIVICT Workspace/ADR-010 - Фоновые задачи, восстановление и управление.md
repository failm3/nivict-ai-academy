# ADR-010 — Фоновые задачи, восстановление и управление

> **Утверждено владельцем 03.11.2026:** выполнение задач **не зависит от того, открыто ли окно интерфейса**. Прогресс и результаты сохраняются устойчиво; после ошибки система возобновляет работу с последнего надёжного этапа, не дублируя внешние действия. Если компьютер с исполнителем выключен, выполнение возможно **только на другом реально работающем и авторизованном устройстве/сервере**. Это целевое архитектурное решение: техническая реализация, доступность второй машины и восстановление после сбоя пока не проверены.

## 1. Что означает «закрыть интерфейс»

- Пользователь может закрыть браузер/десктопное окно, потерять соединение или открыть другой проект: **исполнительный сервис** продолжает разрешённую работу, пока его среда реально работает.
- Веб-интерфейс — наблюдатель и контроллер, **не единственный носитель состояния**. Очереди, прогресс, журнал, checkpoints и артефакты располагаются в устойчивых хранилищах.
- После повторного подключения показывать фактический текущий статус, последние подтверждённые события, затраты, ошибки, ожидаемые согласования и ссылки на результат.
- Закрытие интерфейса **не равно команде «остановить»**. Пауза и отмена — отдельные явные управляющие действия.

## 2. Два режима исполнения

| Режим | Условие | Поведение |
|---|---|---|
| **Основной ПК активен, UI закрыт** | Работает фоновый сервис / worker | Задачи продолжаются, если имеют права, ресурсы и не требуют A3 |
| **Основной ПК выключен / недоступен** | Есть отдельный **работающий, настроенный и доступный** сервер/worker, доверенная очередь и разрешённые ресурсы | Задачи могут продолжиться или восстановиться на другом устройстве **после проверки условий и состояния** |
| **Никакой worker недоступен** | Нет исполняющей среды | Задача не выполняется; состояние сохраняется, после восстановления сервисов — безопасный resume |
| **Задача ждёт владельца** | Действие A3 требует подтверждения | Запрещённый шаг остаётся `WAITING_APPROVAL`, независимые разрешённые ветви могут исполняться |

**Нельзя обещать работу «всегда», пока нет фактически работающего хоста, сети, доступа к секретам, мониторинга и испытанного восстановления.**

## 3. Рекомендуемая логическая архитектура (не выбранный стек)

`UI/Chat` ↔ `Task API` ↔ `Persistent Queue / Task State` ↔ `Workers + Orchestrator` ↔ `Tools/LLM/Quality Gate`.

Боковые сервисы: `Policy Engine`, `Memory`, `Evidence Store`, `Event Log`, `Backup/Recovery`, `Notifications`.

- **Task State:** задача, владелец, проект, текущая версия плана, зависимости, этап, lease/heartbeat, статус, budget, deadlines.
- **Persistent Queue:** устойчивые задания, ограничение параллелизма, приоритеты, отложенные попытки, cancel/pause requests.
- **Worker:** исполняет только выданную аренду/lease с TTL, обновляет heartbeat, фиксирует шаги, прекращает действия по отмене и политике.
- **Orchestrator:** назначает шаги, видит зависимости, ведёт успешные и неуспешные ветви, решает retry/replan/escalation.
- **UI:** подключается к актуальному состоянию, а не реконструирует задачу по тексту старого чата.
- **Event Log:** фактические события создания, запуска, завершения, проверки, расхода, блокировок, ошибок и восстановления; защита чувствительных данных.

## 4. Состояния, сохранение и завершение

Примерный набор **проектных** статусов (проверить по текущему коду перед реализацией):
- `RECEIVED`, `NEEDS_INFO`, `PLANNED`, `QUEUED`, `RUNNING`;
- `PAUSED`, `WAITING_APPROVAL`, `VERIFYING`, `NEEDS_REWORK`;
- `COMPLETED`, `PARTIAL`, `FAILED`, `INCONCLUSIVE`, `CANCELLED`.

`COMPLETED` может поставить только **Quality Gate по ADR-008**, если обязательные критерии и доказательства выполнены. Отмена должна быть безопасной: текущий внешний запрос может завершиться позже, поэтому проверять фактические эффекты и не выдавать мгновенную гарантию отката.

**Checkpoint перед/после рискованных шагов:** сохранять входы, версии, артефакты, подтверждённые результаты, `operation_id`, планы и статусы. После сбоя не считать завершённым то, что только *началось* или что LLM объявила завершённым.

## 5. Восстановление после сбоя

1. Обнаружить отказ worker по heartbeat/lease и определить, какие этапы неопределённы.
2. Читать последнее достоверное состояние и журнал инструментов.
3. Сверить реальный результат операций с внешним сервисом (письмо, платёж, деплой, изменённый файл).
4. **Не делать слепой повтор**: использовать idempotency key там, где API поддерживает, или проверять результат/дубликат; когда надёжно установить итог нельзя — `INCONCLUSIVE` и согласование по риску.
5. Назначить безопасно возобновляемые шаги живому worker; у нетривиальных задач возможен replan.
6. Повторить необходимые проверки Quality Gate; показать владельцу причины рестарта и ограничения.

**Техническая гарантия:** устойчивость к сбою проектируется через at-least-once исполнение с идемпотентной обработкой там, где возможно. Универсальную exactly-once обработку внешних действий **не обещать**.

## 6. Защита и экономика

- Лимиты `max_attempts`, `max_duration`, `max_budget`, `max_parallel_workers`, `allowed_providers`.
- Circuit breaker / backoff для падающих API; не создавать бесконечные задачи или неконтролируемые расходы.
- Права доступа проверяются заново при resume и смене worker; **секреты не упаковываются в контекст LLM** и не копируются на другую машину без защищённой процедуры.
- При смене плана, высоком риске или истекшем разрешении — повторная проверка Policy Engine; A3 согласует только владелец (ADR-009).
- Изолировать падение одного проекта/worker, сохранять независимые задачи.
- Вторая машина или HDD сами по себе не являются disaster recovery; необходимы тесты восстановления, шифрования и целостности.

## 7. Интерфейс управления

**Главный экран задачи:** название, project_id, состояние, прогресс по проверяемым этапам, текущий worker/хост (если доступен), время, бюджет, последнее событие, блокирующие ошибки, необходимые согласования, ссылка на артефакты/trace.

**Команды:** `Pause`, `Resume`, `Cancel`, `View details`, `Approve/Reject A3` — только по полномочиям владельца.

**Уведомления:** начало долгой задачи, существенное изменение плана, ошибочный повтор, блокировка по бюджету/правам, запрос A3, завершение/незавершение, инцидент. Частоту и канал утвердить позднее; не спамить каждым шагом.

## 8. Минимальная проверка перед заявлением о реализации

- [ ] UI закрыт, основной worker активен: задача реально продолжает выполнение, события сохраняются.
- [ ] UI открыт снова: актуальные прогресс, стоимость, ошибки и ссылки на артефакты доступны.
- [ ] Принудительно завершён worker: после перезапуска задача безопасно возобновляется с подтверждённого этапа.
- [ ] Повторной отправки сообщения/платежа/публикации после сбоя нет; неясное состояние помечается `INCONCLUSIVE`.
- [ ] Нет ни одного работающего worker: интерфейс честно показывает ожидание, а не «агент работает».
- [ ] Есть подтверждённый независимый сервер: разрешённая задача действительно продолжается при выключенном основном ПК.
- [ ] `Pause / Cancel` останавливают новые действия, корректно учитывают уже совершённые эффекты.
- [ ] A3 не выполняется без согласования владельца, даже после перезапуска.
- [ ] Неуспешная QA не приводит к `COMPLETED`.
- [ ] Проверены лимиты затрат/времени, fallback, backup/restore и логи.

## 9. Вопросы технического аудита

- Где сейчас физически исполняются worker/оркестратор? Зависят ли они от окна/процесса UI?
- Где хранятся очереди, checkpoints, ключи идемпотентности, логи, история QA?
- Как работают pause/resume/cancel, watchdog, backup и rollback?
- Есть ли реально подключённый второй сервер и доступна ли ему необходимая среда без нарушения прав?
- Какие функции уже проверены, какие заявлены, какие отсутствуют или регрессировали?
- Какой сценарий первым используем для доказательного end-to-end теста?
