## Правила статусов

- **ADR принято:** согласовано как архитектурное решение, **реализация не подтверждена**.
- **Проектная цель / Новое:** сформулировано пользователем, требует спецификации, приоритетов и приёмки.
- **Проверить:** нужен фактический as-is аудит кода, процессов, БД, логов или интеграций.
- **COMPLETED** для функции или задачи — только после воспроизводимых проверок, артефактов и обязательных согласований (ADR-008).

## Критические связи — не потерять

1. **Главный агент ↔ цели:** не только последняя реплика, а текущие приоритеты, проекты, деньги, сроки и решения. Focus Manager не навязывает управление человеку.
2. **Все чаты → постоянный архив → индексы/классификация → Context Engine → LLM:** оригиналы не уничтожать при уплотнении. Системе не нужен весь архив в каждом запросе; поиск должен восстанавливать достаточный проверенный контекст.
3. **64 000 токенов:** пользователь уточнил фактическое наблюдаемое сжатие до 64K, а не 6 400. Проверить, *когда и почему* оно применяется, контекстный лимит модели и что из требований пропадает; не делать вывод о причине плохого качества без trace.
4. **Требования → план → исполнитель → доказательства → независимый Quality Gate:** текст исполнителя «готово» не даёт права ставить COMPLETED.
5. **Единый интерфейс ↔ Studio / Production / Management:** по ADR-009 это пока **личный Workspace владельца**, не общая учётная запись команды. Для Academy с сотрудниками — отдельный контур пользователей, доступов и данных.
6. **Agent Factory:** если не хватает навыка, выбрать между обычным кодом, ботом, workflow, MCP и специализированным агентом; выпускать по тестам.
7. **Дизайн и маркетинг:** проверять не только код, но и визуальное качество, уникальность, продуктовую пользу, продажи и экономику.
8. **Обновления и память:** GitHub/Obsidian — документы и ADR; не подменяют полноценное хранилище чатов, SQL-state, индекс поиска и доказательства.
9. **Закрытие UI:** исполнитель работает только при реально работающем и разрешённом worker. Если все worker выключены, задача не выполняется.
10. **Саморазвитие:** обратная связь → RCA → изменение проверенного правила/теста/компонента; это не означает автоматического изменения весов модели.

## Пробелы / что нужно проверить до обещаний

| ID | Пробел | Состояние | Проверка |
|---|---|---|---|
| N-01 | Сквозной архив разговоров и вложений | **Расширить ADR-007** | Новый чат восстанавливает прошлое решение и источник без повторного интервью |
| N-02 | Межчатовая классификация, кластеризация и контекст | **Проектировать** | Поиск по темам, задачам, версиям; recall на контрольных случаях; поддержка длинных сессий |
| N-03 | Контекст 64K / потери при сжатии | **P0: as-is аудит** | Токены до/после, модель/провайдер, лог summary, поиск пропущенных критических требований |
| N-04 | Визуальная компетенция / сложный 3D | **Проектировать + benchmark** | Видео-референс → уникальная рабочая анимация → браузерные и визуальные тесты |
| N-05 | Full-stack delivery | **Расширить Production** | Полноценный сайт с БД/API, UI, безопасностью, E2E и измеримым продуктовым результатом |
| N-06 | Работа с HH/биржами | **Интеграции не подтверждены** | Разрешённые методы доступа, поиск, фильтры, черновики, без массового автоматического спама |
| N-07 | Персональная Academy для сотрудника | **Отдельный продукт** | Разные роли/память, адаптивное объяснение, учебный прогресс, проверка |
| N-08 | Focus Manager + Goal Ledger | **Новое требование** | Помнит долгосрочную цель, предлагает вернуться, не теряет новую идею |
| N-09 | Market Intelligence / заработок | **Новое требование** | Источник → исследование → финансовая гипотеза → план → показатели |
| N-10 | Авторадар инструментов | **Каталог есть отдельно; непрерывный цикл не внедрён** | Проверка новизны, безопасности, стоимости, совместимости и приёмка кандидатов |
| N-11 | Safe self-update / rollback | **G-02: as-is аудит** | Backup, sandbox, CI, canary, аварийный стоп, проверенный rollback |
| N-12 | Quality Gate для дизайна/кода/продаж | **ADR-008 принят, реализация неизвестна** | Тесты, охват, артефакты и owner sign-off при смене визуального baseline |
| N-13 | Обмен GitHub ↔ локальный Obsidian | **Сейчас Git pull блокируется локальными Canvas** | Сохранить локальные изменения, разрешить конфликт и проверить синхронизацию |
| N-14 | Реальное управление состоянием, памятью и правами | **ADR-007/010; аудит** | Crash/restart, permission isolation, source of truth, отсутствие повторных внешних эффектов |

## Следующий шаг (не исполнен автоматически)

1. Сохранить локальные изменения четырёх старых Canvas и устранить Git merge blocker.
2. Получить ас-is инвентаризацию runtime 0.9.x **без** перезаписи исходников и секретов.
3. Сопоставить N-01–N-14 с кодом и доказательствами: работает / частично / нет / неизвестно.
4. Уточнить, какие новые требования утверждаем как отдельные ADR; затем спроектировать изменённый план работ.
5. Протестировать четыре сквозных сценария: межчатовая память, высококачественная дизайн-разработка, коммерческий результат, адаптивное обучение.

**Принцип:** карта полезна как обзор покрытия требований, но не доказывает, что за пределами неё нет упущений. Для полноты нужна матрица трассировки «требование → компонент → проверка → доказательство».
