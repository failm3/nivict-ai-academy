# ADR-006 — Гибридная маршрутизация моделей

**Утверждено 03.11.2026:** использовать **гибридную модель маршрутизации LLM**. У каждой роли/класса задач есть основная проверенная модель, но **Model Router** может динамически выбрать другую подходящую модель или переключиться на разрешённый резерв при сбое, недоступности, лимите или обоснованном выигрыше в качестве/стоимости/скорости.

> **Статус:** целевая архитектура, не подтверждение того, что динамическое переключение работает в текущем Workspace. Не считать кандидатов на интеграцию фактически подключёнными.

## 1. Базовый принцип

**Роль/класс задачи → проверенная основная модель → проверка требований → при необходимости разрешённая альтернатива → выполнение → объективная проверка результата.**

- **Закреплённая модель:** стартовый профилированный вариант для типовых задач (например, анализ, код, исследование, проверка, краткие ответы).
- **Динамическая маршрутизация:** выбирает из *допущенного* списка по результатам проверок качества, возможностям (включая tools/structured output/контекст), разрешённости данных, доступности, задержке и стоимости.
- **Fallback:** при сбое или превышении лимита — выбрать разрешённый резерв либо честно приостановить задачу, если подходящего резерва нет.
- **Обязательный QA:** переключение между моделями **не снимает требований к результату**. Для чувствительных классов задач качество альтернативы должно быть оценено до допуска, а фактический результат проверен.
- **Единый интерфейс:** выбор модели не создаёт отдельных пользовательских чатов; главный агент организует процесс (ADR-001).

## 2. Контракт Model Router

### Вход

`task_id`, `project_id`, `role`, `task_type`, `quality_tier`, `required_capabilities`, `context_estimate`, `data_classification`, `provider_allowlist`, `latency_target`, `task_budget`, `remaining_budget`, `preferred_model`, `fallback_policy`, `approval_scope`.

### Результат

`selected_model`, `provider`, `model_version`, `selection_reason`, `capabilities_checked`, `estimated_cost`, `expected_latency_tier`, `fallback_candidates`, `policy_verdict`.

**Маршрут выбирает программный механизм с проверяемыми правилами и метриками; LLM может помогать классифицировать неоднозначную задачу, но не может отменить запреты Policy Engine.**

## 3. Приоритет выбора и ограничители

1. **Политика безопасности и приватности:** разрешены ли провайдер, регион/передача данных, проект и категория данных.
2. **Способности модели:** подходит ли размер контекста, поддержка инструментов, структурированных ответов и нужного качества.
3. **Профиль качества:** достаточные результаты на целевом наборе evals; модель не допускается исключительно потому, что дешевле.
4. **Бюджет и лимиты:** hard cap на задачу, сервис и период, контролируемые retries; нет скрытого дорогого fallback.
5. **Latency и доступность:** оптимизация среди **уже допустимых** вариантов, а не вместо минимальных требований.
6. **Наблюдаемость:** версия, выбранная модель, стоимость, токены, длительность, переключения и причины сохраняются в trace.

## 4. Сценарии

| Ситуация | Реакция |
|---|---|
| Типовая задача, основная модель доступна | Использовать её, если соответствует правилам и бюджету |
| Сложная задача, основная модель не достигает нужного качества | Выбрать из проверенных моделей более подходящую, не нарушая стоимость/права |
| Ошибка API, timeout или rate limit | Повтор по политике, затем разрешённый fallback; перед повтором внешнего действия проверить идемпотентность |
| Основная модель поддерживает инструменты, запасная — нет | Не переносить вызовы «как есть»; выбрать совместимый маршрут либо вернуть ограничение |
| Конфиденциальный проект запрещает внешнего провайдера | Локальная разрешённая модель **только если хватает качества**; иначе остановить/согласовать дальнейший маршрут |
| Все допустимые провайдеры недоступны | `BLOCKED` / `INCONCLUSIVE`, checkpoint и уведомление; **не обходить политику** |

## 5. Что важно для NIVICT Workspace

- Профильные исполнители (ADR-004) используют **логическую роль**; физическая модель может меняться без пересоздания роли, если совместимость и качество доказаны.
- По предыдущим обсуждениям кандидаты/существовавшие компоненты: OmniRoute, Router Cheap, локальная Ollama/Qwen, внешние API и резервные провайдеры. **Актуальные подключения, цены, квоты, версии и качество не проверены этим документом**.
- Детерминированные задачи по умолчанию решает код/бот, а не самая дешёвая LLM.
- Независимый проверяющий может использовать отдельную модель, но **вторая LLM не заменяет фактические тесты**.
- При переключении модели в длинной задаче сохранять состояние, ограничения и версии контекста; не пересылать всю память и секреты.
- Предварительные профили: `fast`, `code`, `research`, `review`. Это категории задач, не привязка к конкретным брендам.

## 6. Что проверить при внедрении

- [ ] Для 4 классов задач определены критерии допуска и основная модель, а не только её название.
- [ ] При недоступности первой модели выбирается **разрешённая и совместимая** резервная.
- [ ] Передача чувствительных данных запрещённому провайдеру блокируется независимо от ответа LLM.
- [ ] При превышении лимита задача останавливается или требует явно разрешённого увеличения бюджета.
- [ ] В trace фиксируются основной и резервный маршрут, цена, ошибки, токены и версии.
- [ ] Регрессионные evals подтверждают качество после смены модели.
- [ ] Если совместимой модели нет, система честно сообщает о блокировке, а не симулирует успех.
