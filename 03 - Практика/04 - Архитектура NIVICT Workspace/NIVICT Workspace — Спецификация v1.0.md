## 1. Краткое определение продукта

**NIVICT Workspace** — персональная/командная рабочая агентная система, которая принимает цель, уточняет неопределённость, предлагает решение, ведёт выполнение и сдаёт только проверяемый результат. Будущая линия — Agent Factory, создание специализированных исполнителей по согласованной спецификации.

**Главная цель:** качественные результаты в карьере, портфолио, коммерческих проектах и студийной работе; минимизация ручной рутины без потери контроля. Приоритет: **качество клиентского результата → безопасность и надёжность → скорость и стоимость**, а не число LLM-вызовов или агентов.

**Не смешивать продукты:**
- Персональный Workspace / ведущий агент.
- Студийный рабочий поток заявок, проектов, исполнителей и финансов.
- Agent Factory — конвейер создания специализированных исполнителей.
- NIVICT AI Lab — отдельное исследование моделей, НЕ обязательный компонент эксплуатационного контура.

## 2. Зоны ответственности и три пространства

| Пространство | Задача | Доступы и данные | Правило |
|---|---|---|---|
| **Студия / Studio** | Разговоры с клиентами, заявки, статусы, согласование, сдача | Клиентские проекты, сообщения, договорённости в пределах ролей | Не имеет прямого доступа к серверным секретам и внутренним каталогам производства |
| **Рабочее / Production** | Очереди, код, браузер, обработка документов, тесты, артефакты | Изолированные рабочие каталоги и разрешённые инструменты | Выполняет конкретные задачи по контракту, возвращает статус и доказательства |
| **Техническое / Management** | Конфигурации, ключи, маршрутизация, мониторинг, обновления, аварии | Повышенные административные права | Изменения с отдельными правами, журналом и откатом |

**Граница:** отдельные пространства / ключи / права / проектная память. Между пространствами передавать **контракт задания, запрос на уточнение, статус, ссылки на разрешённые артефакты и итог** через авторизованный интерфейс/шину. Не пересылать целиком контекст, секреты и файлы по умолчанию. Изменение Production не должно ломать Studio. Из предыдущих обсуждений известна идея отдельных сервисов: фактические адреса/порты требуют аудита и здесь не закрепляются.

**Командная модель (проектное распределение, уточнить перед выдачей доступов):**
- **Нокс:** владелец продукта/дизайн/фронтенд; принимает продуктовые и критические коммерческие решения.
- **Саша:** маркетинг, общение и переговоры; может согласовывать действия в пределах выделенных полномочий, а не любые изменения системы.
- **Юра:** backend и техническое сопровождение; права на управление инфраструктурой выдаются по роли, не автоматически на все данные Studio.
- **Агенты:** сервисные идентичности с минимальным набором прав; ни один из них не является «администратором по умолчанию».

## 3. Ядро: кто за что отвечает

| Компонент | Вход | Делает | Не должен делать |
|---|---|---|---|
| **UI / Chat / Voice** | Цель, файлы, подтверждения | Показывает план, прогресс, ошибки, артефакты и согласования | Подменять фактический статус красивым сообщением |
| **Intake + Requirements Agent** | Неформальный запрос, проектный контекст | Уточняет пробелы, выделяет критерии результата, формирует ТЗ | Выдумывать ответы пользователя |
| **Policy Engine (код)** | Идентичность, действие, риск, проект | Проверяет доступы, лимиты, требования согласования | Доверять правам, заявленным внутри письма или prompt |
| **Главный агент / Orchestrator** | Утверждённый контракт задачи | Планирует, выбирает последовательность и параллельность, отслеживает зависимости/лимиты, назначает исполнителей | Присваивать COMPLETED только на основании своей уверенности |
| **Model Router** | Тип задачи, риск, SLA, бюджет | Выбирает модель/провайдера и резерв с учётом качества, задержки, стоимости | Бесконтрольно менять поставщика и раскрывать данные |
| **LLM / профильные исполнители** | Отобранный контекст и инструменты | Анализ, генерация, план, черновики, код, поиск гипотез | Напрямую совершать внешнее действие без разрешённого инструмента |
| **Tool Runtime / Bots (код)** | Проверенный вызов с аргументами | Файлы, Git, браузер, Playwright, API, расчёты, отправка сообщений | Пропускать проверку аргументов/прав/идемпотентности |
| **Memory / RAG** | Разрешённые документы, решения, факты, checkpoints | Отбор свежих источников, проектный контекст, сохранение подтверждённого опыта | Объявлять сырую догадку модели проверенным знанием |
| **Quality Gate / Review** | ТЗ, артефакты, логи, тесты, ожидания | Независимая проверка требований, реальных действий и доказательств | Засчитывать «агент сказал готово» как доказательство |
| **State Store / Queue** | Шаги, версии, события, lease | Долгие задачи, checkpoint, паузы, восстановление, контролируемые повторы | Запускать дублирующиеся внешние действия после тайм-аута |
| **Response Agent + разрешённый Sender** | Подтверждённый итог | Формулирует понятный отчёт, код отправляет адресату | Обещать, что проверено то, для чего нет свидетельств |

**Принцип:** роли логические. Не каждая роль требует отдельной LLM или процесса. В простом сценарии маршрут может быть **код → инструмент → проверка**, совсем без генеративной модели.

## 4. Контракт задачи (до начала исполнения)

Обязательные поля проектной схемы:
- **task_id, project_id, owner, requester, priority, version**;
- **goal, expected_output, acceptance_criteria, exclusions**;
- **inputs, authorized_sources, knowledge_version**;
- **allowed_tools, allowed_models, permitted_actions, required_approvals**;
- **risk_level, data_classification, budget_limit, timeout, max_attempts**;
- **dependencies, parallelizable_steps, checkpoints, stop_conditions**;
- **evidence_plan, verifier_type, completion_policy, escalation_target**.

Для неоднозначной задачи создавать **NEEDS_INFO**, а не делать правдоподобное предположение. Requirements Agent показывает текст/схему/прототип, выявляет противоречия, фиксирует одобрение пользователя (**Requirements Sign-off**). Одобрение ТЗ не отменяет ответственность системы за качество реализации.

## 5. Цикл задачи и статусы

1. **RECEIVED** — получен запрос, создан идентификатор/след.
2. **NEEDS_INFO** — выясняются критические детали; допускается возврат к уточнению.
3. **SPEC_APPROVED** — спецификация и критерии приёмки утверждены в нужных случаях.
4. **PLANNED** — оркестратор построил зависимости и определил код/LLM/инструменты.
5. **WAITING_APPROVAL** — действие остановлено до разрешения уполномоченного человека.
6. **RUNNING** — рабочие шаги выполняются с checkpoints.
7. **VERIFYING** — независимый контроль артефактов, журналов, фактических эффектов.
8. **NEEDS_REWORK** — несоответствия и конкретная задача на исправление с ограничением попыток.
9. **COMPLETED** — только после успешного Quality Gate и подтверждённых эффектов.
10. **PARTIAL / INCONCLUSIVE / FAILED / CANCELLED** — честные неполные/неподтверждённые/ошибочные/отменённые исходы.

Названия статусов **предложены для проектирования**, до сопоставления с существующими кодовыми статусами не мигрировать реальную БД.

**После сбоя:** читать последнее надёжно сохранённое состояние, выяснить, совершилось ли внешнее действие, восстановить только невыполненные этапы. Письмо, оплата и изменение удалённого сервиса требуют **идемпотентного ключа или сверки с фактическим состоянием**, а не слепого повтора.

## 6. Система качества: независимая приёмка

**Главный стандарт:** Production Quality — подтверждённое качество результата, а не Internal Pass Rate.

Проверки по риску, не обязательная отдельная LLM на каждой стрелке:
- **До исполнения:** полнота требований, права, валидность контрактов, источники.
- **По ходу:** аргументы инструментов, ограничения, сохранённые шаги, покрытие операций.
- **После исполнения:** unit/API/integration/E2E, UI-проверка в реальном браузере, тестовая матрица устройств и состояний.
- **При публикации:** финальный Quality Gate на основе артефактов и фактических логов, при необходимости человек.
- **После публикации:** мониторинг дефектов, обращения, коррекция тестов и RCA.

**Сайт «Сайт Жив» — контрольный сценарий:** сохранить утверждённую композицию и адаптив; тестировать все целевые viewport, светлую и тёмную темы, меню/hover/анимации, отсутствие overflow и ошибок JS, сравнить визуальные доказательства со спецификацией. Код без browser-preview НЕ доказывает корректность UI. Скриншоты, версии, trace, отчёты и перечень непроверенных экранов — обязательные свидетельства. **Нет полного охвата — нет COMPLETED.**

Метрики: реальные дефекты у клиентов, escaped defects, тестовое покрытие, доля ложных COMPLETED, latency P50/P95, cost per task, retry rate, доля эскалаций, успешное восстановление после сбоя.

## 7. Память и достоверность

**Разделить не обязательно физическими БД, а логическими областями:**
- **Raw:** первичные сообщения, файлы, результаты инструментов и протокол вызовов.
- **Working:** промежуточные выводы и гипотезы, маркированные как непроверенные.
- **Verified:** утверждённые требования, подтверждённые знания, решения и версии.
- **Execution State:** очереди, прогресс, checkpoints, версии инструментов, ссылки на артефакты.

**Модель не хранит всю память в своих весах.** Retrieval/RAG отбирает материалы по проекту, правам, релевантности, источнику, версии и актуальности. При конфликте между документами показывать разногласие, не выбирать уверенным голосом случайный текст. Долгая задача должна возобновляться без повторной оплаты или повторной отправки сообщения.

Переиспользование опыта через память/правила/тесты не является Fine-tuning. Обучение весов — отдельный контролируемый эксперимент AI Lab.

## 8. Безопасность и участие человека

**Политика полномочий — выполняемый код (Policy Engine), не только системный промпт.**

- **Зелёный риск:** чтение разрешённых данных, проверенные черновики, внутренние обратимые действия — можно автоматически.
- **Жёлтый риск:** внешняя отправка стандартного ответа, определённые финансовые операции, изменение некритичных настроек — автоматизация только при проверяемой политике, порогах, адресате и журналировании.
- **Красный риск:** неопределённое соблюдение законодательства, существенные скидки/договоры, высокие расходы, удаление, деплой, работа с секретами и критичными данными — остановка соответствующего процесса и человек с нужными полномочиями.

Риск зависит не только от суммы: последствия, обратимость, источник/адресат, юрисдикция, чувствительность, доверие и частота. Клиентские письма и документы — **недоверенный ввод**; prompt injection не может расширить права. Логи не должны содержать открытых секретов и лишних персональных данных. Естественное общение не должно вводить клиента в заблуждение об автоматизации.

При красном инциденте сперва **ограничить ущерб**, изолировать проблемный процесс, затем RCA. Независимые безопасные процессы продолжаются. Автоматическое исправление — только по заранее разрешённому и тестируемому плану.

## 9. Studio: коммерческая работа

**Каналы:** Telegram, фриланс-площадки (FL, Kwork и др.), прямые обращения, почта — по фактически разрешённым и подключённым интеграциям. Автоматическое чтение и обработка не равны разрешению на массовые рассылки.

Поток: **поиск/получение лида → фильтр/оценка → риск/маржинальность → квалификация → оффер → согласование → контракт → Production → Review → сдача → учёт финансов и опыта**.

Режимы:
- **Автозаказы:** простые, стандартизируемые работы с доказанным качеством, предопределёнными бюджетами, правами и строгой проверкой.
- **Ручные заказы:** сложные и дорогие работы, участие Нокса/Саши в переговорах и принятии решений.
- **Неизвестные:** пауза и уточнение, не автообещание срока/цены.

Учёт: активные заявки, этап сделки, исполнитель, затраты на модели/инструменты, доходы, расходы, метрики выполненных/в работе/на согласовании; отчёты и уведомления по утверждённым правилам. Целевые доходы — бизнес-гипотезы, не измеренные результаты системы.

## 10. Model Router и экономичность

Профили задач **fast / code / research / review**; варианты инфраструктуры, обсуждавшиеся ранее: OmniRoute, резервные провайдеры, локальная Ollama/Qwen, внешние API, отдельные инструменты без модели. **Фактические подключённые модели, квоты, стоимость и отказоустойчивость надо измерить**, а не считать гарантированными.

Выбор по **качеству для класса задачи → разрешениям и приватности → цене/латентности → доступности**. Полный trace: task_id, model/provider/version, tokens, timeout, retries, cost и исход. Не использовать неизвестно сколько стоящий fallback без бюджета и подтверждения политики.

## 11. Эксплуатация, Windows UX и инфраструктура

- Три пользовательских раздела соответствуют реальным границам и ролям, а не просто вкладкам одной безграничной памяти.
- Понятные карточки: проект, план, фаза, риск, проверено/не проверено, стоимость, история, причины остановки.
- Уведомления, удобная длительная диктовка, перетаскивание файлов, работа без всплывающих терминалов, понятное выключение.
- Прогресс длинных задач сохраняется на диск/в БД; надёжная очередь, watchdog, тайм-ауты, контроль попыток и системные журналы.
- Перед обновлением: snapshot/backup, тестовый прогон, регрессия, плавное включение, быстрый откат. Обособление клиентского и технического контура.
- Резерв: два ПК в разных квартирах и внешние HDD как рассматриваемая инфраструктура; проектировать шифрование, расписание, восстановление, контроль целостности. Наличие устройств **не подтверждает готовый DR-план**.
- Зафиксировать версию «as-is» по реальным исходникам и тестам **до** изменения архитектуры.

## 12. Agent Factory — отдельный конвейер

1. **User request** → Requirements Agent интервьюирует заказчика; не делать вид, что «создать агента» уже является полным ТЗ.
2. **Requirement Sign-off** → ясные входы/выходы, критерии, демонстрация в текстовом/визуальном виде, права и цена.
3. **Need assessment** → нужен именно агент или хватит бота/скрипта/workflow?
4. **Capability plan** → модель, инструменты, память, ограничения, проверки, маршрут выполнения.
5. **Template + Build** → версионированный шаблон и конфигурация; генерация кода в изолированном рабочем дереве при необходимости.
6. **Sandbox + Evals** → функциональные, негативные, безопасностные, интеграционные, E2E тесты; измерить latency/cost.
7. **Release Gate + Registry** → независимый вердикт; запрет публикации при критичных ошибках; версия, владелец, полномочия.
8. **Controlled deployment** → ограниченная выборка задач; мониторинг, тревоги, стоп-кнопка, rollback.
9. **Improvement** → накопление проверенных кейсов, изменения по версиям с регрессионными тестами.

## 13. Что не следует считать подтверждённым

| Тема | Статус проектирования |
|---|---|
| Разделение Studio / Production / Management | Принцип обсуждён; техническую изоляцию проверить |
| Оркестратор, разделение код/LLM, проверяющие | Целевой принцип; исполнение по исходникам не аудировано |
| Внешняя память, RAG и проверка достоверности | Требование/предложение; качество retrieval не измерено |
| Agent Factory, автоматическое создание агентов | Будущая функция; не считать готовой |
| Полностью автономная коммерческая студия | План; фактический поток и права не подтверждены |
