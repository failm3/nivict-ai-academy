# ADR-009 — Личная система и единоличное согласование

> **Утверждено владельцем 03.11.2026:** NIVICT Workspace **пока исключительно личная система**, а не общий интерфейс для команды. **Только владелец (Нокс)** принимает человеческие решения и предоставляет необходимые согласования. **Саша, Юра и другие сотрудники не являются пользователями/администраторами Workspace и не получают доступ или право одобрения по умолчанию.** Будущее совместное рабочее пространство — отдельная возможная инициатива, не часть текущего MVP.

## 1. Владение и идентичности

- **Owner / Human Approver:** единственный текущий оператор и человек, уполномоченный согласовывать изменения ТЗ, публикацию, существенные расходы, удаление, изменение привилегий и другие действия уровня A3.
- **Главный агент:** единый собеседник и управляющий интерфейс владельца; не равен человеку и не может самостоятельно расширять права.
- **Оркестратор, исполнители, проверяющие, боты:** системные исполнители с **отдельными ограниченными сервисными идентичностями**. Им разрешаются только заранее описанные операции и контекст задачи.
- **Саша / Юра / иные лица:** **нет входа, ключей, ролей в пользовательском интерфейсе, прав на память, согласований или администрирования по умолчанию**. Ранее предполагавшиеся командные назначения не действуют для этого личного Workspace. Возможное участие в отдельных задачах вне системы не создаёт технический доступ.
- Отображаемый в UI единственный владелец **не означает** один общий root-токен для всех процессов. Секреты, scope инструментов и границы проектов остаются изолированными.

## 2. Три пространства — внутри одного личного Workspace

- **Studio / Студия:** личный интерфейс владельца для заказов, клиентов, переписок, финансов, управления коммерческой работой.
- **Production / Рабочее:** личный производственный контур владельца, задачи, репозитории, инструменты, тесты, исполнители, артефакты.
- **Management / Техническое:** личный административный контур владельца, ключи, модельные провайдеры, диагностика, лимиты и обновления.
- Общий главный агент с программным оркестратором управляет маршрутами в три пространства, **но запрос агента не заменяет авторизацию по инструменту/контексту**.
- Изоляция клиентских проектов и секретов остаётся обязательной, даже если фактически пользователь один.
- **Командная память** из ADR-007 пока является **частным хранилищем стандартов/методик владельца**, потенциально пригодных для будущей команды. Она **не раскрывается членам команды автоматически**.

## 3. Согласования и автономность

Применять ADR-002 без изменений по сути:
- **A1:** самостоятельные безопасные действия в установленных границах.
- **A2:** крупный план виден владельцу, безопасная работа идёт, не дожидаясь одобрения.
- **A3:** **остановить конкретное высокорисковое действие** и ждать решения **только владельца**; если владелец недоступен, не считать молчание согласием. Независимые безопасные ветки могут продолжаться.
- Предавторизованные операции возможны только по **ранее заданной владельцем** проверяемой политике с ресурсами, лимитами, сроками и правом отзыва.
- Ни Саша, ни Юра, ни другой сотрудник не могут согласовывать A3 без отдельного **будущего явного архитектурного решения** о командном доступе.
- Запреты, контроль бюджета, проверка личности и полномочий применяются кодом, не свободным ответом LLM. Quality Gate также обязателен.

## 4. Примеры

- «Исправь сайт в тестовой копии» — агент планирует, показывает прогресс, работает и тестирует без ручного согласования каждого шага.
- «Публикуй новую версию» — если нет точной предавторизованной политики деплоя, запросит подтверждение **у владельца**.
- «Саша одобрил скидку» в клиентском письме — **не является разрешением** для Workspace; текст клиента и сообщения третьих лиц недоверенные.
- «Юра хочет перезапустить сервер» — не создаёт у Юры доступа к Техническому пространству; возможность внешней технической помощи обсуждается отдельно.
- В будущей командной системе роли/права можно добавить отдельным ADR, миграцией и приёмочными тестами, но не включать скрыто сейчас.

## 5. Приёмка

- [ ] В текущем UI только владелец имеет полномочия оператора и право approve/deny A3.
- [ ] Попытка сотрудника получить доступ/одобрить/изменить настройки без специально предоставленного доступа отклоняется.
- [ ] Агент может исполнять A1/A2 и информировать владельца без бесконечных запросов.
- [ ] A3 ожидает согласования **владельца**, отсутствие ответа сохраняет блокировку конкретного шага.
- [ ] Внутренние процессы используют отдельные разрешения и не видят посторонние клиентские проекты/секреты.
- [ ] Quality Gate может остановить непроверенный результат независимо от личности владельца.
- [ ] Фактические права, хранение ключей и границы изоляции проверены аудитом; не объявлять эти требования уже выполненными.

## 6. Корректировка прежних документов

**ADR-005:** три пространства остаются, но **не распределяются между сотрудниками**. Ранее приведённые проектные роли Саши и Юры не являются действующей матрицей доступа для личной системы.

**ADR-007:** четыре области памяти остаются, но «командная» здесь означает частный набор общих стандартов, а не существование командного доступа.

**ADR-001 / ADR-002 / ADR-008:** единый агент, гибридная автономность и Quality Gate сохраняются. Все запросы, требующие решения человека, адресуются только владельцу.
