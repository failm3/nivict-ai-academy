# ADR-005 — Три пространства и единое управление

**Принято 03.11.2026:** NIVICT Workspace организован в **три пространства** — Студия, Рабочее, Техническое. Ими управляет **один главный пользовательский агент**, поддержанный общим программным оркестратором. **Разделение гибридное:** общие базовые сервисы можно переиспользовать, данные/полномочия/контексты разделять по роли, проекту и контуру.

**Статус:** архитектурное решение, а не утверждение о выполненной технической изоляции текущей версии.

## 1. Пространства

| Пространство | Главная обязанность | Типовые данные / сервисы | Запрещённый доступ по умолчанию |
|---|---|---|---|
| **Studio / Студия** | Лиды, клиентские переговоры, квалификация, коммерческие решения, проекты, финансы, согласования и сдача | Клиентские чаты, заявки, сметы, статус заказа, утверждённые документы | Серверные секреты, административные конфигурации, чужие проекты |
| **Production / Рабочее** | Техническое выполнение задач, код, дизайн, автоматизация, инструменты, тесты и артефакты | Изолированные каталоги проектов, исполнительные задания, инструменты, тестовые логи, проверенные результаты | Неограниченная история всех клиентов, общие ключи администрирования |
| **Management / Техническое** | Подключения, модели, роутинг, инфраструктура, бюджет, наблюдаемость, инциденты, обновления, откат | Мониторинг, защищённое хранение ключей, service registry, конфигурация провайдеров, операции обслуживания | Клиентские переговоры вне конкретной необходимости и прав |

## 2. Единый пользовательский контур

- **Один главный агент** — собеседник пользователя для задач любого пространства (ADR-001). Он не равен одному процессу с неограниченными правами.
- **Оркестратор** планирует и маршрутизирует работу в соответствующие сервисы/исполнители через авторизованные контракты.
- **Policy Engine** проверяет субъект, проект, ресурс, действие, лимиты и согласование **на момент каждого вызова**. Информация о задаче не является правом доступа.
- Сервисы возвращают **статус, вопросы, ссылки на доступные артефакты, доказательства выполнения**. Главный агент собирает единый ответ, не создавая отдельные чаты исполнителей.
- План крупной безопасной задачи отображается, пока работа продолжается (ADR-002); высокорисковые действия ждут согласования по политике.

## 3. Границы и обмен

**Предлагаемый межконтурный контракт**:
`task_id`, `project_id`, `requester`, `action`, `scope`, `access_context`, `budget_limit`, `risk_level`, `correlation_id`, `input_refs`, `expected_output`, `evidence_required`.

**Ответ сервиса**:
`status`, `output_refs`, `evidence_refs`, `metrics`, `errors`, `needs_approval`, `next_step`.

- Между пространствами передавать **минимально необходимые данные по защищённому и авторизованному интерфейсу**, а не копировать весь контекст и ключи.
- Клиентские проекты и память отделять по `project_id` и полномочиям. Для разных клиентов явно отделять их наборы данных; одного поля `project_id` недостаточно без enforcement на уровне сервисов/БД/доступов.
- Общие сервисы (маршрутизация моделей, очереди, наблюдаемость) допустимы при технической изоляции секретов, данных и логов; при необходимости выделять отдельные процессы.
- Не определять физическое количество приложений, серверов, баз, БД и портов на бумаге до аудита текущих исходников и инфраструктуры.

## 4. Последовательность на примере клиентского сайта

1. **Studio:** клиент ставит задачу; главный агент помогает понять требования и фиксирует согласование.
2. **Production:** оркестратор даёт изолированное задание исполнителям, инструменты создают результат; QA проверяет код, визуал, взаимодействия и заданные размеры.
3. **Management:** обслуживает разрешённые модели, ключи, трассировку, лимиты; при необходимости выполняет обновления/откат с отдельными правами.
4. **Studio:** главный агент возвращает проверенный артефакт, статус, ограничения, финансовые показатели; отправка клиенту в рамках полномочий.

## 5. Правила ответственности

- Нокс — продукт/дизайн/фронтенд и критические продуктовые решения (проектная роль).
- Саша — переговоры, маркетинг и коммуникации; конкретные коммерческие лимиты ещё не утверждены.
- Юра — backend/техническая поддержка; административные права назначаются отдельно.
- Каждый исполнитель/агент — собственная ограниченная сервисная идентичность, а не обладатель единого root-токена.
- Недоступность Технического пространства не должна автоматически разрешать обход контроля; деградировать только в безопасные режимы.

## 6. Архитектурные последствия

**Преимущества:** один понятный интерфейс; общие сервисы без бессмысленного дублирования; изоляция клиентов, секретов и рабочих процессов; проще независимая приёмка и аудит.

**Риски:** единый оркестратор может стать точкой отказа; межконтурная авторизация и консистентность данных усложняются; ошибка в конфигурации общей памяти создаёт риск утечки. Нужны журналирование, тесты изоляции, резервные процедуры.

## 7. Критерии приёмки решения

- [ ] Главный агент маршрутизирует клиентскую заявку из Studio в Production без отдельного чата исполнителя.
- [ ] Исполнитель работает только в допустимом проекте и не видит файлы другого клиента.
- [ ] Studio не может извлечь технические ключи, а Production — получить все клиентские переговоры.
- [ ] Оркестратор получает статусы, доказательства и корректно отображает в едином диалоге.
- [ ] Действие с правами Management требует соответствующей авторизации; отсутствие ответа не равно разрешению.
- [ ] Отказ одного исполнителя не повреждает другие независимые проекты.
- [ ] Реальная структура текущего Workspace документирована: подтверждено / частично / отсутствует / сломано.

## Открыто, не утверждено

Физические сервисные границы, стек и фреймворки, число БД, формат шины, перенос существующей памяти и ролевая матрица для всех операций. Уточнить на техническом аудите.
