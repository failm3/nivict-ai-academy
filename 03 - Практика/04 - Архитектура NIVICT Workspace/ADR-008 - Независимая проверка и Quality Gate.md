# ADR-008 — Независимая проверка и обязательный Quality Gate

> **Утверждено 03.11.2026:** исполнитель не может объявить задачу успешно завершённой только на основании собственного отчёта. **Статус `COMPLETED` выдаёт программный Quality Gate** после предусмотренных контрактом фактических проверок. Это **архитектурное решение**, а не подтверждение того, что текущий Workspace уже умеет исполнять все проверки.

## 1. Разделение ответственности

| Роль | Обязанность | Ограничение |
|---|---|---|
| **Исполнитель** | Выполняет работу, создаёт артефакты, запускает разрешённые инструменты, прикладывает trace и результаты | Не выдаёт себе окончательный статус `COMPLETED` |
| **Автоматические проверки** | Валидируют схемы, сборки, тесты, безопасность вызовов, API, браузер, состояние после операции | Успех отдельного теста не равен общему завершению |
| **Профильные проверяющие** | Оценивают технический, визуальный, продуктовый, финансовый или иной результат согласно типу задачи | Их текстовый вывод **сам по себе** не является фактом внешнего эффекта |
| **Quality Gate (код / правила)** | Сопоставляет критерии ТЗ с проверками и доказательствами, решает PASS / FAIL / INCONCLUSIVE | Не разрешает PASS при отсутствии обязательной проверки |
| **Главный агент** | Сообщает пользователю статус, замечания, ссылки и дальнейшие шаги в едином диалоге | Не переопределяет вердикт Quality Gate произвольной репликой |

**Независимость** означает достаточное отделение проверки от самоотчёта исполнителя: отдельные тесты и фактические результаты инструментов, при необходимости отдельный проверяющий/человек. Вторая LLM не гарантирует независимость и точность автоматически.

## 2. Проверки по сложности

- **Простая детерминированная операция:** проверяемый результат скрипта, значение/файл/статус операции, схема ответа и при необходимости фактическая проверка внешней системы. Не нужно создавать отдельного дорогостоящего LLM-проверяющего.
- **Документ или исследование:** фактические источники, актуальность, точность цитирования/формата, полнота критериев, отметка о непроверяемых выводах.
- **Сайт, интерфейс, дизайн:** тесты сборки, функциональный browser/E2E, проверка responsive, тем оформления, взаимодействий, визуальные артефакты и сопоставление с утверждённым baseline. Текст «всё исправлено» не считается доказательством.
- **Высокорисковое действие:** проверка полномочий/разрешений и фактического эффекта; Quality Gate не заменяет отдельное согласование по ADR-002.

## 3. Контракт сдачи

На каждую задачу до начала работы определить:
- `task_id`, `project_id`, `spec_version`, `acceptance_criteria`;
- `verification_plan` (какие проверки обязательны), `verifier_roles`;
- `evidence_refs` (код, логи, скриншоты, тесты, API-состояние), `coverage`;
- `risk_level`, `required_approvals`, `max_rework_attempts`, `budget`.

**Quality Gate возвращает:** `PASS`, `FAIL` либо `INCONCLUSIVE` с перечислением проверенных критериев, дефектов, недостающих доказательств и ссылок. Это предшествует переходу к итоговому статусу задачи.

## 4. Правила вердикта

- **PASS → COMPLETED:** каждый обязательный критерий удовлетворён, доказательства действительны, разрешения получены, нет блокирующих дефектов.
- **FAIL → NEEDS_REWORK:** зафиксированы конкретные несоответствия, исполнитель получает адресное задание на исправление. Число циклов ограничено.
- **INCONCLUSIVE → PARTIAL / INCONCLUSIVE / BLOCKED:** нельзя проверить нужный аспект (например, нет доступа к браузеру, отсутствует исходное ТЗ или упал тестовый стенд). Не заявлять `COMPLETED`.
- **CRITICAL ISSUE:** при угрозе данных/безопасности приостановить опасный шаг и эскалировать, не ждать полной проверки.
- **Правило честности:** `tool_called` ≠ `effect_confirmed` ≠ `quality_passed`.

## 5. Пример — сайт «Сайт Жив»

1. Требование: не менять утверждённую композицию, поведение, визуальный стиль и структуру без отдельного согласования.
2. Исполнитель создаёт изолированную версию, журнал изменений и проверяемую ссылку/сборку.
3. Проверяющие сверяют адаптив по утверждённым viewport, темы, hover/анимации, содержимое, console errors и overflow.
4. Quality Gate принимает **только подтверждённые тестами и артефактами** результаты; незакрытый экран или непроверенная анимация остаётся замечанием.
5. При FAIL исполнитель повторяет исправление с регрессией; при PASS главный агент сообщает проверенный итог и ограничения.
6. Публикация в production дополнительно управляется разрешениями из ADR-002 и не подразумевается одним PASS.

## 6. Защита от ложных завершений

- Конечный статус выдаёт **кодовый state transition**, а не свободный текст LLM.
- В журнале есть версии исходников, критериев, скриншоты/ссылки, фактические вызовы инструментов и проверенные эффекты.
- Проверяющий не должен слепо доверять тестам/логам, сгенерированным тем же исполнителем, без валидации источника и целостности.
- Покрытие проверок должно быть явным (например, проверено 8 из 10 страниц → не полный PASS).
- После реальных клиентских дефектов проводить RCA и добавлять регрессионные сценарии.
- Использовать метрики `false_completed_rate`, `escaped_defect_rate`, `verification_coverage`, `rework_rate`, `cost_per_verified_task`.

## 7. Приёмочные испытания

- [ ] Исполнитель пишет «готово», но тест не выполнялся — статус **не `COMPLETED`**.
- [ ] Все обязательные проверки PASS — итог `COMPLETED` с документированными доказательствами.
- [ ] Выявлен overflow на 320 px — конкретный дефект и `NEEDS_REWORK`.
- [ ] Нет доступа к тестовому браузеру — `INCONCLUSIVE` вместо ложного PASS.
- [ ] После правки работает регрессия связанных экранов и состояний.
- [ ] Повторные исправления имеют лимит стоимости/попыток и возможность передачи человеку.
- [ ] Независимая проверка не может тайно обойти Policy Engine или разрешить production deployment.

## 8. Открытые технические детали

Выбор тестовых фреймворков, контрактов QA и хранилища доказательств; эталоны визуального сравнения и метрики по конкретным типам задач; число проверяющих по риску; права на принудительный override — на отдельный аудит. **Не считать это уже реализованным.**
