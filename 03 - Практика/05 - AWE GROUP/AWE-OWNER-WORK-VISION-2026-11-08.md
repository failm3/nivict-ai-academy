## 1. Большая задача AWE GROUP

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Создать универсальную агентную организацию на одном расширяемом ядре: владелец ставит цель, система понимает задачу, планирует, выбирает LLM/агентов/ботов/скрипты/сервисы, создаёт и испытывает недостающие специализированные инструменты и агентов, выполняет действия в рамках выданных прав, проверяет результат и сохраняет прогресс. Пример с торговым ботом использовался только для иллюстрации универсальности, а не как утверждённый первый проект.

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Особо важен переход от разработки AWE силами Codex к тому, чтобы работающая AWE могла брать техническую задачу из GitHub, разрабатывать код через Coding Executor в отдельной ветке/worktree, тестировать, проходить независимый QA и готовить PR. Не путать создание PR с разрешением на автоматический merge в защищённое ядро.

**[СОГЛАСОВАНО КАК НАПРАВЛЕНИЕ]** Первым делом нужен *реально работающий автономный агент*. Далее его последовательно расширяют до универсальной группы. Не откладывать использование ограниченного, проверенного контура до завершения всех будущих направлений.

Технический источник: [Единая архитектура и A/B](ASTRA-AUTONOMY-AUDIT-2026-11-08/08-e1-unified-plan.md), [Capability registry](ASTRA-AUTONOMY-AUDIT-2026-11-08/11-executor-capability-architecture.md), [Runtime/learning](ASTRA-AUTONOMY-AUDIT-2026-11-08/12-agent-runtime-and-learning.md).

## 2. Прикладная миссия: трудоустройство / HeadHunter / портфолио

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Адаптировать общее AWE-ядро для трудоустройства, а не строить отдельный жёстко прошитый «бот для HH»:

1. Проверять достоверные факты опыта, резюме и существующие портфолио-кейсы.
2. Формировать две разные версии CV под согласованные карьерные направления, не выдумывать метрики или опыт.
3. Искать и сопоставлять релевантные вакансии в доступных разрешённых источниках, включая HeadHunter там, где реальный механизм работы и права подтверждены; учитывать дубликаты, устаревание, охват и причины блокировки.
4. Подготавливать персонализированные первичные отклики; отправлять автоматически только через отдельно разрешённый доступный канал с фиксированным мандатом; подтверждать реальную отправку внешним readback.
5. Мониторить ответы/приглашения, сообщать владельцу; дальнейшее общение и переговоры с работодателем остаются за владельцем.
6. Создавать **реальные работающие цифровые продукты** для портфолио по заданным владельцем briefs, а не только статические красивые страницы. Проводить независимую функциональную, UX, visual и browser-приёмку; публиковать только при разрешении.
7. Использовать тот же универсальный core для отдельной продуктовой миссии B и карьерной миссии A; не доказывать «универсальность ко всему» по двум тестовым классам.

**Важно:** прямая подача через API HH не объявлена доступной/реализованной. Email/B3 и дальнейшие платформенные интеграции имеют разные разрешения. Профиль для пилота — отдельный проверяемый путь, не обещание «откликнуться на все вакансии».

ТЗ: [B1/B2](E1-CODEX-DELIVERY-2026-11-08/05-CAREER-RESEARCH-AND-PACKAGE.md), [B3](E1-CODEX-DELIVERY-2026-11-08/06-LIVE-EFFECT-AND-MONITOR.md), [Full](E1-CODEX-DELIVERY-2026-11-08/08-E1-FULL-AND-OPERATIONS.md).

## 3. Дизайн: профессиональная ДНК, а не фиксированный стиль

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Агент должен обладать очень высоким уровнем понимания продуктового дизайна и владеть профессиональным производством интерфейсов, в том числе сложным 3D, motion, анимацией, компонентами, состояниями и полноценной web-реализацией. Владелец хочет уйти из низкоуровневой технической рутины в творческое руководство: видеть целую картину, чувствовать характер продукта, критиковать, выбирать и корректировать направления.

**[СОГЛАСОВАНО КАК НАПРАВЛЕНИЕ]**
- Не путать новаторство, мастерство и продуктовую эффективность. Смелый дизайн не автоматически хороший; привычный дизайн не автоматически плохой.
- У каждой работы есть контекст, аудитория, пользовательская задача и допустимая степень эксперимента.
- Условные режимы для обсуждения: `Product` (ясность, UX, надёжность), `Premium` (высокое мастерство и арт-дирекция), `Experimental` (осмысленные нестандартные визуальные решения). Это **предложенные названия**, не принятая классификация.
- Экспериментальная свобода особенно уместна в собственном портфолио и там, где заказчик понимает и принимает соответствующий риск. Привязка визуального решения к проверяемому сценарию остаётся обязательной.
- Качество оценивать по отдельным дисциплинам: продуктовая ценность, информационная архитектура/UX, визуальная иерархия, арт-дирекция, craft/motion, дизайн-система, доступность, адаптивность и реальная инженерная реализация.
- Качество не сводится к одному числу и не подтверждается только автором. Нужен независимый визуальный reviewer, browser QA, воспроизведение пользовательского сценария и аргументированная обратная связь.
- Творческие комментарии владельца («слишком резко», «продукт не дышит», «элементы спорят за внимание») агент должен переводить в проверяемые дизайн-гипотезы, изменения композиции/ритма/движения и видимые варианты, не подменяя замысел субъективным автоматическим баллом.

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Огромная библиотека проверенных инструментов и готовых компонентов: прежде чем рисовать или программировать с нуля, искать подходящие существующие решения, проверять лицензию, качество, актуальность, интеграцию и ограничения. Примеры для ориентира: Tailwind CSS как слой стилизации, Gravity UI/Radix UI как варианты библиотек/примитивов, Three.js/React Three Fiber, Spline, GSAP, Rive для 3D/motion. Перечень **не является обязательным стеком для всех проектов**. Каталог из тысяч обнаруженных записей не означает их установку и допуск в runtime.

**[НЕ УТВЕРЖДЕНО]** Окончательное универсальное определение «выдающегося дизайна», эталонные референсы, пороги визуальной приёмки и метод накопления/калибровки художественной обратной связи. Прорабатывать на реальных проектах с владельцем.

## 4. Профессиональные стандарты для всей организации

**[ПРЕДЛОЖЕНИЕ ДЛЯ СОВМЕСТНОЙ ФИКСАЦИИ]** Сформировать отдельные, версионируемые политики:
- `Product Philosophy`: понимание людей, продукта, целей и компромиссов.
- `Design Excellence`: UX, визуал, 3D/motion, арт-дирекция и уровни экспериментальности.
- `Production Standards`: reuse vs build, зависимости/лицензии, функциональность, accessibility, QA/performance и сопровождение.
- `Professional Review`: независимость reviewer, доказательства и причины отказа.
- `Working Culture`: работа с критикой, ошибками, исследованиями, клиентами.
- `Verified Knowledge`: происхождение знаний, практические тесты, обновление навыков, границы памяти и реального дообучения моделей.

**Не утверждать эти документы как действующие корпоративные регламенты без отдельного обсуждения и принятия.** Они должны направлять профессиональные линии AWE, но не ограничивать творческую свободу единым шаблоном.

## 5. Коммерческая модель: два параллельных контура

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Приоритет AWE — приносить **реальные деньги и устойчивую экономическую ценность**, а не максимальное число агентов, моделей или эффектных демонстраций.

**Контур A — активные крупные сделки:** владелец лично развивает бизнес, переговоры, партнёрства, продаёт большие проекты; студия и команда производят результат.

**Контур B — Revenue Engine:** AWE на постоянной основе в рамках лимитов исследует рыночные возможности, создаёт и сопровождает цифровые активы, помогает с дистрибуцией, анализирует продажи, затраты и прибыль, а люди курируют направления. Цель — повторяемый доход, не требующий личных переговоров с каждым покупателем. Владелец **не против продажи продуктов**; он хочет избежать обязательной ручной продажи каждой небольшой единицы.

### Коммерческие направления — кандидаты, не принятые запуски

| Направление | Модель денег | Примечание |
|---|---|---|
| Студия: сайты, дизайн, разработка, внедрение ИИ | Разовые крупные контракты | Активный контур владельца, приоритет первых коммерческих результатов |
| Цифровые шаблоны, компоненты, плагины, 3D/motion assets | Повторные покупки/лицензии | Площадки и каналы выплат проверять отдельно |
| Micro-SaaS / приложения / API | Регулярные подписки или usage | Требует платящих пользователей, качества, поддержки и удержания |
| Автоматизация для бизнеса / support | Внедрение + recurring support | Возможны более стабильные платежи, но договоры и клиентская работа остаются |
| Контент/медиа и YouTube | Реклама, спонсорство, партнёрки, аудитория для продуктов | Рост аудитории и допуск к монетизации не гарантированы |
| Партнёрские программы, контентные ресурсы | Комиссия за разрешённое действие/покупку | Контроль качества и правил платформ |
| Bounties и конкурсы | Оплата за принятый результат | Не recurring в строгом смысле; принятие/выплата не гарантированы |
| Акции/трейдинг | Нестабильный инвестиционный результат | Не основа стабильного денежного потока; нет гарантии новостного преимущества LLM, нужны отдельный риск-мандат, paper trading и контроль реальных потерь |

**[СОГЛАСОВАНО КАК НАПРАВЛЕНИЕ]** Лучше начинать с ограниченного портфеля проверяемых гипотез, а не массово запускать десятки направлений без спроса. Один проект не считать доходным по числу произведённых файлов, просмотров или регистраций.

### Финансовые критерии

Отдельно измерять: опубликованный продукт → первая настоящая покупка/платёж → повторная покупка или продление → фактически полученные средства → маржинальность/чистый результат после расходов → устойчивость к падению одного канала.

Учитывать стоимость LLM/API, хостинга, комиссии маркетплейсов/платежей, возвраты, налоги, поддержку, работу людей и исправления. Никакие ранее приведённые числовые примеры дохода не являются прогнозом или согласованным финансовым планом.

**[ПРЕДЛОЖЕНИЕ]** Возможная продуктовая функция `AWE Revenue Engine`/направление `AWE Ventures`: discovery → оценка спроса и рисков → ограниченный эксперимент → QA → публикация по допуску → мониторинг продаж и себестоимости → решение о масштабировании/закрытии. Названия и организационное выделение пока не утверждены.

## 6. Гибридная команда и роль владельца

**[ЦЕЛЬ ВЛАДЕЛЬЦА]** Есть люди, которым можно делегировать *полноценное оперативное управление* отдельными направлениями, а не только наблюдение за статистикой. Владелец сохраняет стратегический и итоговый контроль. Это даёт AWE возможность работать как гибридной организации, не только как автономному ПО.

Предлагаемое разделение функций:
- **Владелец:** стратегия, продуктовый/творческий вектор, крупные сделки, допустимые бюджеты, итоговые бизнес-решения.
- **Люди-кураторы направлений:** операционное управление, анализ метрик, контроль качества, принятие решений в выданных полномочиях.
- **AWE coordinator и исполнители:** исследование, планирование, производство, тестирование, мониторинг, отчёты, предложение корректировок.
- **Независимый QA:** техническая и профессиональная проверка с воспроизводимыми основаниями.

Конкретных людей, структуру юридических лиц, права сотрудников и KPI пока не назначали. Наличие команды не доказывает коммерческий успех — он измеряется выручкой и экономикой.

## 8. Не путать архитектуру и поэтапную готовность

Обсуждалась поясняющая **семиступенчатая схема** (рабочая интерпретация, не официальный release numbering):

1. C1 Live: изолированные source/database ресурсы.
2. A2: durable coordinator, параллельные leased tasks и recovery.
3. A3: real LLM/model capability broker и исполняемые инструменты.
4. Первый реально выполненный автономный цикл.
5. Coding Executor: issue → branch/worktree → code → tests → QA → PR.
6. Проверенная переносимость: разные домены, создание специализированных решений/агентов по запросу.
7. Многопроектная профессиональная организация AWE с человеческими кураторами, проверяемыми линиями и надёжной эксплуатацией.

Это **не семь завершённых инженерных этапов** и не гарантированное расписание. Ближайшая практическая цель — шаг 4, затем шаг 5. Для карьерной миссии требуется также B1–B5/C2; для коммерческой Revenue-миссии нужны отдельно интегрированные платежи, рынок, права и метрики.
