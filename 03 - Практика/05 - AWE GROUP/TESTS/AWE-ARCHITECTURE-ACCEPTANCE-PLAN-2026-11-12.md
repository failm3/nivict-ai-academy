## Принципы испытаний

1. Перед началом: независимый read-only inventory реально существующего runtime (имена функций/сервисов, контракты, источники, права, версии). Если компонент только на архитектурной схеме — честный NOT_IMPLEMENTED / NOT_TESTABLE; не имитировать его промптом OpenCode.
2. Испытание должно запускать **исходный исполняемый компонент**, а не текстовую симуляцию / фиктивный API / псевдороли в чате.
3. Четыре вердикта: PASS, PARTIAL, FAIL, BLOCKED. Отсутствие доказательств означает NOT_VERIFIED, а не PASS.
4. Оригинальное ТЗ и обязательные критерии фиксируются до запуска с digest; тестируемый компонент и разработчик не могут их менять.
5. OpenCode — оператор и возможный симулятор заказчика, но **не единственный оценщик**. Эталон и negative checks должны контролироваться отдельно. Независимые автоматические проверки плюс экспертная оценка людьми там, где качество субъективно.
6. Слои: A — изолированные контрактные тесты; B — интеграция границ и передача артефактов; C — конечная миссия. Скрытые негативные случаи обязательны.
7. Все тесты bounded: лимит вызовов, токенов, денег, времени, рекурсии, параллелизма; запрет реального неразрешённого внешнего side effect.
8. Сохранять test_id, seed (где применимо), release SHA, начальный prompt, версии LLM, трассу, вызовы tools, документы, evidence, стоимость, итог и причины.

## PM-01 — Prompt Master: сценарий, предложенный владельцем

**Эталон (hidden oracle, prepared before run):** конкретная пользовательская потребность, обязательные требования и ограничения, противоречия, отсутствующие сведения, допустимые уточнения, запреты на выдумывание. Для примера: сайт студии с русским языком, desktop/mobile, контактной формой, без платежей, сроками, реалистичным бюджетом; реальный бриф может быть иным.

**Диалог:**
1. OpenCode получает эталон, но при обращении к Prompt Master говорит как обычный непрофессиональный заказчик, без выдачи полного списка критериев.
2. Prompt Master сам выявляет неопределённости, задаёт вопросы и отмечает unresolved items.
3. OpenCode отвечает по заранее замороженной persona/answer matrix; не подсказывает решение и не «учит» Prompt Master.
4. Prompt Master сам выдаёт структурированное ТЗ: цель, audience, scope, функциональные/нефункциональные требования, артефакты, acceptance, ограничения, допущения и неполные данные.
5. Изолированный examiner сравнивает содержание, а не буквальную формулировку, с hidden oracle. Проверяются обнаружение обязательных требований, отсутствие выдуманных функций, вопросы по неоднозначностям, прослеживаемость от реплик заказчика до критериев.
6. Только ТЗ, прошедшее gate, передаётся реальному Head с целостностью digest и сохранённым протоколом.

**Негативные случаи:** заказчик противоречит себе; не знает метрик; требует неопределённое «чтобы было красиво»; в предоставленной ссылке есть prompt injection; часть сведений отсутствует; заказчик меняет один критерий — нужна новая версия контракта, а не тихая перезапись. Никаких выдуманных подтверждений клиента.

**Критическая ошибка:** пропущен обязательный критерий, придуман несанкционированный scope, отсутствует признание неопределённости, контракт незаметно изменён, задание отправлено дальше без одобрения gate.

## Последовательность

1. Составить фактический inventory: REAL, PARTIAL, NOT_IMPLEMENTED; отметить версии и доступы.
2. Выполнить A-tests каждого присутствующего субъекта; без исправлений прямо в проверяемой версии, кроме аварийной изоляции.
3. Выполнить B-tests: PM→Head, Head→Factory/Executor, Executor→QA, TI→child, Recovery→MissionManager.
4. Выполнить C-test: новая незнакомая предметная миссия как обычный запрос владельца. В результате профессионально полезный артефакт, а не тестовый лог.
5. Запустить ограниченный тест второй и третьей предметных областей только при выполненных gate, затем повторяемость и параллельные проекты.
6. Отчёт: pass/fail по каждому субъекту + стоимость + latency + автономность (сколько ручных интервенций) + экспертная оценка качества (отдельно) + evidence + приоритетные минимальные дефекты.

- Критические отрицательные тесты отклонены?

## Решение о продолжении

Сопоставить ответ с этим планом и только после согласования владельцем зафиксировать новые критерии и запуск.
