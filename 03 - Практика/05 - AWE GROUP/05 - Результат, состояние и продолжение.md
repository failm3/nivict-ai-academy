# 05 · Приёмка, сохранение и продолжение

> **Статус: концепция, не работающая реализация.** Схема: [[AWE-GROUP-Architecture-v01.canvas]]. Сквозные источники: [[Память — сквозная архитектура и правила]], [[04 - Блок 04 — AWE Quality Assurance System]], [[AWE-CONSTITUTION-v01]].

## Цель блока

После **PASS независимого блока 04** результат должен быть сохранён так, чтобы:
- нельзя было выдать запись, черновик или локальный файл за законченный релиз;
- после сбоя задача могла продолжиться с достоверного шага;
- не повторялись опубликованные действия, уведомления, платежи или удаление;
- надёжно определялись runnable/WAITING/BLOCKED задачи в общем Task DAG;
- Head Agent получил честный отчёт и артефакты, а не обещание исполнителя.

## Поток

1. **Persist:** с привязкой к project_id/task_id сохраняется принятой версии артефакта, state transition, event_id, trace_id, acceptance evidence. В рабочей реализации использовать согласованную транзакцию состояния и *transactional outbox* для внешнего уведомления/переиндексации; нельзя объявлять атомарным одновременно PostgreSQL и внешнее файловое хранилище без протокола согласования.
2. **Local QA:** проверка записи, ссылок, разрешений, статуса и версии. Отчёт включает фактически прочитанные данные, не текстовое заверение.
3. **Independent post-save audit:** отдельное чтение объектов в БД и хранилище; hashes, версии, project ACL, последовательность событий, evidence. FAIL/BLOCKED → reconciliation, ограниченный retry или эскалация. Ни один отказ не становится COMPLETED.
4. **Durable checkpoint:** сохранить текущее состояние DAG, next_action, lease/owner, уникальные operation IDs, версию agent config и конституции.
5. **Remaining tasks?:** по авторитетной очереди. Если есть исполнимые — назначить диспетчеру блока 03; если есть только ожидающие — WAITING с deadline и событием-условием; если нет — интеграционная приёмка/отчёт.
6. **Final package check:** все обязательные задачи/зависимости закрыты, их отдельные QA04 PASS и версия итогового набора подтверждена. Если сборка изменилась после тестирования — отдельное задание независимого интеграционного QA04, не финальный отчёт.
7. **Head Agent/report:** report содержит status (COMPLETE/PARTIAL/WAITING/BLOCKED/FAILED), versions, ссылки на artifacts/evidence, затраты, известные риски, следующее действие и событие. Финальное пользовательское утверждение — по политике конкретного проекта.

## Минимальная машина состояний (проект)

```text
QUEUED → RUNNING → SUBMITTED_FOR_QA
SUBMITTED_FOR_QA → ACCEPTED | REWORK | UNCLEAR | BLOCKED
ACCEPTED → PERSISTING → SAVED_VERIFIED
PERSISTING → RECONCILING | BLOCKED
SAVED_VERIFIED → QUEUED(next) | WAITING | FINAL_REVIEW
WAITING → QUEUED(on accepted event) | BLOCKED(on deadline/policy)
FINAL_REVIEW → COMPLETE | REWORK | UNCLEAR
REWORK → QUEUED(only affected task)
```

**Инварианты:**
- Только QA04 PASS даёт `ACCEPTED`; только post-save PASS даёт `SAVED_VERIFIED`.
- Status `COMPLETE` требует QA04 всех обязательных результатов, финальной проверки комплекта и post-save подтверждения.
- `WAITING` и `BLOCKED` сохраняются и отражаются в отчёте. Они **не** эквивалентны успеху.
- Все переходы — с project_id/task_id, revision, monotonic version/optimistic lock и audit event.
- Делегирование/перепланирование не создаёт второго постоянного Project Agent.
- Нельзя повторять внешнее действие после restart без reconciliation/idempotency.

project_id: uuid

В одной системе нельзя одновременно полагаться на `COMPLETED`, `COMPLETE`, `DONE` как эквивалентные статусы: выбрать общую номенклатуру при техническом проектировании.

## Crash/restart и параллельная работа

- На рестарте: загрузить авторитетный state + event log → найти протухшие leases → проверить внешние побочные эффекты → requeue только безопасные операции.
- Планировщик/диспетчер должен соблюдать DAG, shared resource locks, квоты и idempotency; `RUNNING` не равно «выполнено».
- Внешние результаты и notifications отправлять через outbox/workers с повтором и дедупликацией. **Exactly-once поведение внешних API нельзя гарантировать в общем случае**; требуется reconciliation/проверка провайдера.
- Таймеры и webhooks сохраняются в состоянии, а не в памяти LLM; произвольный внешней webhook проходит проверку подписи и authorisation.
- При изменении ТЗ/данных старые QA verdicts могут стать stale, выполняется выборочный recheck.

## Что проверить на пилоте

- [ ] Crash до commit; crash после БД, но до записи файла; crash до отправки внешнего уведомления; recovery без потерянных/дублированных действий.
- [ ] Два воркера одновременно пытаются завершить один task_id: версия/lease предотвращают двойное выполнение.
- [ ] Post-save QA сверяет реальную запись, а не память исполнителя.
- [ ] Failures имеют ограниченный retry, дальше BLOCKED и точный отчёт.
- [ ] 20 задач, 19 PASS и одна FAIL: перезапускается только одна неисправная и зависимые от неё.
- [ ] Зависимая задача остаётся WAITING до события, потом возобновляется после восстановления системы.
- [ ] Финальный комплект перетестируется при изменении совокупного артефакта.
- [ ] Отчёт отличает локальное сохранение от внешней публикации и включает правильный evidence ref.
- [ ] Cross-project state, artifact и wait event не читаются/обрабатываются чужой линией.
- [ ] Инструментальные тесты выполняются после разработки, сейчас не проверены.
