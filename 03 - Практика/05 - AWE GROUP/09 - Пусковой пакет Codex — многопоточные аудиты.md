## 2. Среда и изоляция

**Codex A:** исходное дерево NIVICT Workspace/Hermes на компьютере владельца. **Не считать известным местоположение** — пользователь должен указать точную папку/репозиторий. Codex A останавливается со статусом BLOCKED, если source не найден. На этапе аудита ничего в рабочей кодовой базе не изменять.

**Codex B и C:** Github `failm3/nivict-ai-academy` (`main`), существующая локальная папка `C:\Users\1\nivict-ai-academy`. Если доступна функция worktree в Codex, назначить отдельные worktree/ветки `codex/awe-audit-b` и `codex/awe-audit-c`, чтобы не трогать рабочую локальную Obsidian-копию.

Для результатов:
- A: `Codex Audits/A/` (в собственном review worktree/ветке; для не-Git Workspace — отдельная безопасная папка результатов);
- B: `Codex Audits/B/`;
- C: `Codex Audits/C/`;
- D: `Codex Audits/D/`.

**Не сливать одновременно** B/C в одну ветку, не менять их исходные файлы, не давать задачам write-access к областям друг друга. D работает с доступными результатами/PR после завершения трёх аудитов. Если аудиты в отдельных репозиториях/ветках — D получает конкретные ссылки, SHA и изменения.

## 3. Порядок пользователя в Codex (Windows)

1. Открыть [Codex](https://chatgpt.com/codex) или установленное приложение Codex, если доступно; для локального Workspace использовать клиент с доступом к нужным файлам.
2. Создать **три отдельных потока/сеанса**, не три разговора внутри одного контекста.
3. В каждом потоке выбрать соответствующую папку/репозиторий и отдельный worktree/ветку, если поддерживается клиентом.
4. Вставить в каждую задачу краткую установку: **«Выполни GitHub issue #N в репозитории failm3/nivict-ai-academy. Прочитай полное ТЗ и источники. Работай read-only с исходным кодом, отчёт положи в свою папку/ветку, без реализации и деплоя. Все выводы подтверждай evidence.»**
5. Передавать по запросу только недостающие пути/разрешения, не секреты. Проверять результаты, диффы и состав отчётов.
6. После готовности A/B/C и наличия ссылок/PR запускать D по Issue #4. D обязан остановиться на согласовании плана, до разработки.

**Если в клиенте не видно GitHub Issues:** открыть соответствующую ссылку на Issue и целиком скопировать его текст в Codex. Не предполагать, что ссылка гарантирует автоматическую загрузку.

## 4. Общие ограничители и приёмка аудитов

- **Read-only исходники**. Допускается запись только отчётов в собственный рабочий каталог/ветку.
- Ни npm/pip install, ни миграций БД, ни продакшен-деплоя/платежей/публикации и обращений к закрытым сервисам без отдельного разрешения.
- Секреты/токены никогда не вставляются в чат, логи и отчёты.
- Подтверждение: `VERIFIED` (файл/строка, команда, exit code/реальный тест), `INFERRED`, `UNKNOWN`; не выдумывать.
- Если source/возможность/модель недоступны — `BLOCKED`, назвать конкретный blocker.
- Не запускать высокорисковые скрипты из каталога инструментов.
- Включить Context Engine и крайние случаи: лимиты контекстного окна, compaction, retry, output reserve, model switching, восстановление, утечка памяти.
- Русский язык — обязательный для финальной AWE GROUP UI; дизайн из чата — визуальный референс, **демо-цифры не относятся к настоящей системе**.
- Не менять текущую архитектурную Canvas и черновую Конституцию без поручения владельца.

## 6. Точки контроля прогресса

От каждого аудита получать краткую сводку: `status`, `files inspected`, `evidence count`, `P0/P1`, `BLOCKED questions`, `changed files`. Отчёты конечны, проверяемы и сохранены в файлах/PR, а не только в контексте долгого чата.

**Следующее действие:** открыть три потока Codex и поручить issues #1/#2/#3. Если физическая папка Workspace неизвестна, **B и C могут стартовать без A**, а A откладывается до указания источников. D в любом случае ждёт все три отчёта.
