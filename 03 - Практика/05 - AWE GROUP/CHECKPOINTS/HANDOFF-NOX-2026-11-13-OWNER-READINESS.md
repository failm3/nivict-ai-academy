## 1. История и обязательные архитектурные цели

AWE GROUP — универсальная агентная платформа: пользователь → Prompt Master → Head → динамические специализированные агенты/подкоманды → интеллектуальный выбор моделей и инструментов → независимый QA по неизменяемому контракту → артефакты, отчёт, память, продолжение. Работы ведутся в локальной Windows WSL2 Ubuntu, Node/TypeScript/Mastra, PostgreSQL; инженером выступает OpenCode. Подсистемы Tool Intelligence, роли и multi-model routing находятся в разной степени готовности. Код текущего cleanroom НЕ подтверждён как опубликованный в удалённом runtime.

Владелец требует при переходе между чатами фиксировать решения, промпты, результаты, статус и значимые обсуждения в GitHub с проверенным readback, а не обещания.

## 4. Tool Intelligence — ключевой открытый разрыв

Исследовательские каталоги: около **4504** кандидатов NIVICT из прошлой работы; **3415** записей Manus в PostgreSQL поисковой базе, есть `manus_search` и существующий `ti_search`. Эти цифры **не означают** 4504/3415 устанавливаемых или реально разрешённых инструментов. Нужно подтвердить цепочку:
`Head/child обнаружил capability → оценил provenance/совместимость → определил конкретный рабочий MCP/HTTP/OpenAPI/CLI adapter → прошёл policy/grant и наличие credentials → подключил/зарегистрировал разрешённый tool → исполнитель действительно вызвал tool → сохранил результат, стоимость и аудит.`
Наблюдались shell/file_read/file_write/file_list, search и локальный Chromium; универсальное подключение найденного каталожного инструмента сквозным runtime-тестом не доказано.
**Критический вопрос:** при попытке writer сделать README наблюдались инструменты `file_list` и `shell`, отсутствие `file_write` в явном списке — гипотеза о grant/capability mismatch, не окончательный root cause.
**Правило:** безопасное самостоятельное подключение только заранее разрешённых/изолированно протестированных инструментов. Никакого безусловного скачивания и запуска недоверенного кода с правами владельца. Новые пакеты/расширение прав требуют approval/risk gates. Использовать существующую Tool Intelligence, не создавать новый оркестратор.

- Security: ранее исследователь в Recorder находил потенциально раскрытые service/API credentials. Не воспроизводить секреты. Проверить статус/ротацию/редактирование до расширения прав.

## 6. Намеченная программа стресс-тестирования (ПРЕДЛОЖЕНИЕ, НЕ ЗАПУЩЕНО)

Сначала freeze конкретного release SHA и oracle; диагностика текущего кода без исправлений внутри baseline. Далее:
A. unit/contract/negative tests всех реально имеющихся агентов; `NOT_IMPLEMENTED` отмечать честно.
B. Integration: Prompt Master→Head, Head→Factory, Factory→Model/Tool grants, child→real tool→artifact, Memory→QA, kill→reconcile→resume; permission-denied/unknown-tool/adaptor failure/invalid results. 
C. stress/chaos: ориентир 100+ синтетических проверок и параллелизм 1→3→5 миссий; network faults 429/5xx, SSE interrupted, provider change, timeout before/after request acceptance, crash/restart, lock contention, incomplete artifact, injection/secret leak, fake success, budget exhaustion. Числа ориентировочные, подлежат согласованию лимитов.
D. после исправлений и отдельного разрешения бюджета — 5–10 новых задач разного типа, непосредственно `owner → Nox`; OpenCode в read-only supervision, не производит результат и не ослабляет acceptance. Пометка ошибки `FAIL/PARTIAL/BLOCKED` обязательна.
Отдельно замерять p50/p95 и variability, cost/token usage, resource utilization, reliability by gates, долю ручных интервенций, false-pass rate, recovery correctness. Нельзя утверждать готовность на основании одного хорошего прогона или только mock tests.
Платные API в массовом стресс-тесте без отдельного разрешения запрещены. Макеты/mock/local first; явно согласовать потолок бюджета и аварийный stop.
