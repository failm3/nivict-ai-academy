# NOX — обязательные профессиональные плагины / Capability Packs

Дата: 2026-11-13. Статус: **IDEA / обсуждение, НЕ утверждено и НЕ внедрено**.

## Дословное раскрытие идеи владельца

> «Ну, что я подразумеваю под обязательной мультистемой обязательных плагинов. Допустим, по дизайну проще всего объяснить там. Допустим, обязательные плагины: Unslop, то же самое там, какие-нибудь ещё профессиональные моменты, типа там плагин, который проводит, помогает создавать там шаблонные сайты, вот профессиональные шаблонные сайты. Что там ещё, типа. Ну, в общем вот, типа, исходя из Unslop, потому что Unslop — это такой один из главных, как по мне, плагинов, который должен быть присутствовать, дабы избавляться от нейросетевых слопов, которые может создавать агент. И переходить из уже генерации обычной уже к профессиональному моменту. Вот, как бы, вот что я имею в виду, типа под обязательные плагины, к которым всегда обращается агент.»

**Точное намерение:** не только технические инструменты файлов/памяти, а **профессионально обязательные способы работы и проверки качества**, к которым агент действительно обращается в подходящей задаче. Для дизайна Unslop — показательный кандидат, плюс инструменты для профессиональных шаблонов/стартеров сайтов.

## Вывод ассистента — ГИПОТЕЗА для дальнейшего обсуждения

Предложение: профессиональные, привязанные к домену **Capability Packs / Quality Contracts** поверх **существующих** Tool Intelligence, Agent Factory и QA. Не второй каталог, не второй оркестратор. Пакет может содержать skills (инструкции), реально вызываемые tools (MCP/API/CLI), библиотеки, исходные starter kits, проверочные процедуры и критерии качества.

Типы пакетов как пример, не фиксированный scope:
- DESIGN: anti-slop skill/аудит, дизайн-конвенции, библиотека проверенных компонентов, браузерный визуальный QA, семантика/accessibility, сверка с продуктовым брифом. Шаблоны = исходный материал с проверкой соответствия, не универсальная замена решения.
- CODING: форматирование, unit/integration tests, security/static checks, независимое code review.
- MARKETING: проверка фактов, источники и методики анализа, прозрачные расчёты метрик.

**Механизм обязательности:** Runtime назначает версионированный пакет по domain/task, выдаёт минимально необходимые rights, фиксирует checkpoints «до генерации / после артефакта / финальная приёмка». Агент не может просто игнорировать skill. Этапы с реальным tool вызовом имеют лог/доказательство, в случае неуспеха — корректный FAIL/BLOCKED или запрос разрешения, а не фиктивный COMPLETE. Профессиональное качество нельзя приравнивать к «анти-slop правила пройдены»: отдельная оценка назначенной задачи и human expert QA, если необходимо.

**Важно:** различать skills (набор инструкций, без гарантии исполняемого действия) и plugins/tools (код, сети, артефакты). Для тех и других нужна проверка происхождения, лицензии, версии, воспроизводимости, безопасности и совместимости перед подключением. Автоматическое подключение разрешённых capabilities ≠ бесконтрольный install со случайного GitHub.

## Проверенные примеры из открытых источников (2026-11-13)

- https://github.com/heydamir/unslop — Claude/Codex agent skill для анализа и исправления AI-looking UI, задаёт направление и passes; может вызывать инструменты скриншотов/проектные правки. Не считать автономной гарантией профессионального качества.
- https://github.com/0design/unslop-skill — отдельный аудит для Claude Code/Codex; детектор, canon-правила и plans, с использованием canon MCP; read-only audit без автоматического изменения исходников. Потенциальный QA слой, а не подтверждённая текущая интеграция с Nox.
- Существуют **разные** Unslop/unslop проекты, включая writing-only. Установку конкретного проекта пользователь не утверждал. Сначала определить, какой имелся в виду, и протестировать в изолированной копии.

## Связь с текущим приоритетом автономности

По последней NIVICT миссии локальный сайт создан, технический QA 13/14 FAIL из-за отсутствия manifest; owner оценил дизайн субъективно 2/10. Нельзя объявлять профессиональный результат на основе одного deterministic QA. Новый capability-pack может помочь, но не решит сам по себе Tool Intelligence discovery→adapter→grant→tool invocation и manager recovery, которые остаются P0.

## Открытые вопросы, обсуждать с владельцем

1. Что считать «обязательным»: всегда для всех миссий, всегда для задач домена, только на определённом этапе или когда pack применим?
2. Должен ли Unslop запускаться как **генерационная методика**, **обязательный независимый аудит**, или оба этапа? Нельзя выдавать рейтинг качества только по отлавливанию шаблонных паттернов.
3. Кто создаёт и утверждает профессиональный pack: владелец/руководитель линии/уполномоченный QA? Как обновлять и отзывать, не меняя поведение миссии посередине?
4. Как определить профессиональный барьер качества, измерить реальный прирост до/после и стоимость/tokens/latency?
5. Нужно ли связывать pack с ролью агента, задачей, типом deliverable или сочетанием признаков?
