# 04 — AWE Quality Assurance System

> **Статус:** утверждённое архитектурное направление после обсуждения с пользователем 2026-11-05. **Не реализация:** инструменты, среды, роли и политики ниже пока не установлены и не прошли пилот. Источник визуальной архитектуры: [[AWE-GROUP-Architecture-v01.canvas]].

## Решение

**Каждый блок 01–03 и 05 имеет локальный контроль (Local QA).** Проверяющий знает состояние и ход работы своего блока, обеспечивает минимальные проверки и записывает доказательства. **Блок 04 независимо проверяет конечные результаты и добросовестность внутренних проверок.** Общие корпоративные сервисы QA, но профили тестов, область доступа и данные строго привязаны к project_id/task_id. Схема: **Local QA → слепой Independent Examiner → собственные испытания → Verification Auditor → кодовый Quality Gate**.

### 1. Local QA на границах блоков

| Блок | Локальный контроль | Условие выхода |
| --- | --- | --- |
| 01 · Управление | Соответствие намерению пользователя, полнота ТЗ, авторизация, критерии приёмки; семантическая проверка только когда нужна | PASS → 02; FAIL/UNCLEAR → пересмотр |
| 02 · Проектные линии | project_id, шаблон Project Agent, изоляция БД/Storage Workers, доступы, состояние, восстановление | PASS → 03; иначе остановка и восстановление |
| 03 · Планирование и исполнение | Task DAG, зависимости, границы инструментов, фактические результаты каждой операции, ограничение повторов, evidence по task_id | PASS → 04; FAIL → точечная доработка |
| 04 · Независимый контроль | Слепой экзамен, собственные тесты, аудит локальных тестов и доказательств | Только PASS → 05 |
| 05 · Сохранение и отчёт | Совпадение принятых артефактов и сохранённых объектов, hashes, БД, статусы, итоговый отчёт | **Дополнительный независимый программный post-save audit** до финального отчёта |

Проверка внутри этапа не равна выпуску результата наружу. Проверки могут выполняться параллельно с безопасными шагами, но переходы состояния блокируются обязательными gate.

### 2. Independent Examiner — честный преподаватель

- Получает **подлинное зафиксированное ТЗ**, критерии приёмки, конечный артефакт, минимальный проектный контекст и безопасную тестовую среду.
- Не получает предварительную оценку исполнителя, его самообъяснения и оценки Local QA, пока не выполнил собственный независимый экзамен.
- Собирает собственные test cases из критериев и профиля риска; часть испытаний может быть скрыта от исполнителя.
- Имеет права чтения оригинальных артефактов и право работы **только в тестовом sandbox**, без возможности изменять ТЗ, результаты или рабочую инфраструктуру.
- Сочетает кодовые assertions и реальные испытания; LLM необходима **только** для смысловых/неоднозначных задач и не является единственным доказательством.

### 3. Verification Auditor — проверка проверок

После фиксации независимого вердикта раскрываются локальные отчёты. Аудитор сравнивает:
- независимые результаты с утверждениями Local QA;
- наличие и качество evidence для каждого обязательного критерия;
- действительно ли запускался указанный тест и использовался конкретный артефакт;
- возможные «зелёные тесты ни о чём»: неполное покрытие, заглушки, слабые assertions, неверная среда;
- риск тестового сговора/общего промпта, подмены свидетельств, утечку закрытых тестов исполнителю;
- при необходимости **mutation testing / adversarial testing**: способны ли испытания выявить намеренно внесённые дефекты.

**Аудитор может отклонить как Local QA, так и Independent Examiner.** Согласие двух LLM не заменяет реальные испытания.

### 4. Quality Gate — детерминированное решение

| Вердикт | Условие | Действие |
| --- | --- | --- |
| PASS | Все обязательные критерии доказаны, аудит валиден, ограничения соблюдены | Передать Project Agent и блоку 05 |
| FAIL | Есть воспроизводимый дефект или нарушение критерия | Отправить `task_id` и evidence в диспетчер блока 03 на точечную доработку |
| UNCLEAR | Недостаточно доказательств, конфликт оценок, неопределённость требования | Запросить доказательства/уточнение; не считать завершённым |
| BLOCKED | Проверка невозможна, среда недоступна, нет разрешения, проверка небезопасна | Приостановить и эскалировать, не обходить gate |

Никакой блок не может автоматически менять PASS на основании уверенности модели, числа токенов или количества «успешных» собственных тестов. Правила пропуска тестов фиксируются до исполнения и привязаны к профилю риска. Даже при PASS дополнительная публикация/удаление/финансовые действия подчиняются отдельной политике прав и подтверждений.

### 5. Evidence contract / структура записи

Каждая проверка оставляет машинно-читаемый объект (проектная целевая схема, не внедрено):

```yaml
project_id: string
task_id: string
requirement_id: string
criterion_version: string
artifact_ref: string
artifact_sha256: string
test_id: string
test_profile_version: string
runner_name: string
runner_version: string
environment_id: string
executed_at: ISO8601
actual_result: structured
expected_result: structured
status: PASS | FAIL | UNCLEAR | BLOCKED
evidence_refs: [artifact_or_log_ref]
examiner_role: local | independent | auditor | post_save
trace_id: string
```

**Контроль доверия:** права scoped по project_id; артефакты и доказательства — по content hash, желательно версионированное write-once/append-only хранилище и журналы доступа. Критерии приёмки заранее закреплены и их изменения аудитируются. Отделить запуск теста от его описания и отчёта. Обычный лог или запись Langfuse — вспомогательное свидетельство, не гарантия истинности.

### 6. Кандидаты инструментов (выбор после пилота)

| Профиль | Кандидаты | Что реально доказывают |
| --- | --- | --- |
| Web / UI / API | [Playwright](https://github.com/microsoft/playwright), контрактные API-тесты | Результат выполнения сценариев в браузере / API |
| Python / JS | pytest, [Hypothesis](https://hypothesis.readthedocs.io/), Vitest / Jest | Функции и инварианты на известных/генерируемых входах |
| Веб-безопасность | [Trivy](https://github.com/aquasecurity/trivy), [Semgrep](https://github.com/semgrep/semgrep), [OWASP ZAP](https://www.zaproxy.org/) | Уязвимости, секреты, опасные паттерны, HTTP-риски |
| Агентные / LLM | [Inspect AI](https://inspect.aisi.org.uk/), [DeepEval](https://github.com/confident-ai/deepeval) | Сценарные evals, использование инструментов, смысловые критерии |
| Атакующие испытания | [Promptfoo](https://github.com/promptfoo/promptfoo) | Prompt injection, обход правил, adversarial-входы |
| Сила тестов | [Stryker Mutator](https://stryker-mutator.io/) для JS/TS, негативные тесты | Обнаружение искусственно внесённых ошибок; не универсальная оценка качества |
| Наблюдаемость | [Langfuse](https://github.com/langfuse/langfuse) + проектное хранилище evidence | Трейсы, промпты, история запусков, стоимость, ссылки на доказательства |

**Примечание:** это кандидаты на архитектурном уровне. Существование библиотеки не означает её совместимость с NIVICT Workspace/Hermes, установку, успешный прогон или пригодность для всех типов задач.

### 7. Профили риска и бюджет

- **Базовый:** обязательные детерминированные assertions и проверка evidence. Низкорисковые рутинные операции не требуют отдельного LLM.
- **Стандартный:** фактические функциональные и смысловые испытания + независимая выборка и проверка отчётов.
- **Повышенный:** более полное покрытие, негативные/мутационные и атакующие тесты, расширенный аудит и ручное разрешение для опасных или необратимых действий.
- По умолчанию не подменять недостающие проверки оценкой LLM; невозможность выполнить обязательный тест → BLOCKED/UNCLEAR, не PASS.

### 8. Пример «Сайт Жив»

1. Сайтовый агент создаёт страницу и показывает **30 PASS** локальных проверок.
2. Independent Examiner **не видит этих 30 PASS**; по ТЗ запускает собственные Playwright-сценарии: адаптивность, тему, форму заказа, ошибки сервера.
3. Examiner находит проблему с мобильной формой.
4. Auditor читает 30 локальных проверок и выясняет, что тесты покрывали только открытие главной. При необходимости запускает негативные/мутационные тесты.
5. Quality Gate → FAIL с конкретными шагами воспроизведения → диспетчер исправляет мобильную форму, не пересоздавая весь сайт.
6. После PASS артефакты сохраняются; **post-save verifier** перечитывает запись с диска/БД и сверяет хеши и статусы до итогового отчёта.

### 9. Условия готовности будущей реализации

- [ ] Local QA каждого блока 01/02/03/05 с отдельными evidence records
- [ ] Independent Examiner не может прочитать локальный вердикт до фиксации собственного отчёта
- [ ] Auditor умеет воспроизводимо отвергнуть «зелёный отчёт», не проверяющий дефект
- [ ] Quality Gate воспроизводим кодом и не допускает PASS без обязательных доказательств
- [ ] Проверка не может изменить рабочий артефакт/ТЗ
- [ ] Отказ инструмента даёт BLOCKED/UNCLEAR, а не PASS
- [ ] Повторные ошибки возвращаются по task_id, без бесконечных циклов
- [ ] Post-save audit ловит разрыв между принятым результатом, БД и файлом
- [ ] Инструментальные пилоты: результат, цена, ограничения, отказоустойчивость, логи
