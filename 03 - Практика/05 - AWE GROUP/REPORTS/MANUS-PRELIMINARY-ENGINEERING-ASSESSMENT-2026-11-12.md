# AWE GROUP — предварительное инженерное заключение

**Ответ: частично — практически реализуемую AWE с ограниченной автономностью я готов реализовывать по этапам. Но гарантировать универсальную «цифровую организацию», которая без человека надёжно выполняет любые миссии, нельзя.**

На вашем оборудовании реалистична система, которая принимает миссию, формирует ограниченную команду, использует облачные LLM, выполняет программы и браузерные действия локально, сохраняет результаты и передаёт их независимому проверяющему. Для этого не требуется зависимость от Manus во время эксплуатации.

**Предварительный выбор основы — Agent Zero.** Однако готовыми компонентами закрывается прежде всего агентная рабочая среда. Жёсткие бюджеты, принудительные ограничения доступа, обязательная независимая приёмка и надёжное восстановление придётся интегрировать или разрабатывать.

Заключение основано на публичных исходниках и документации, проверенных 12 ноября 2026 года. Установка, практические испытания и платные вызовы LLM не выполнялись. Функции из документации ниже не приравниваются к проверенной работоспособности на вашем компьютере.

## 1. Основная платформа и альтернативы

### Рекомендую Agent Zero

Он наиболее близок вашему принципу переиспользования готового продукта: есть работающий Web UI, проекты, задания, память, инструменты, браузер, терминал, профили агентов и динамическое делегирование подчинённым агентам. Подтверждены настройка OpenAI-compatible провайдера, подключение MCP и внешние HTTP/A2A-интерфейсы. [Agent Zero](https://github.com/agent0ai/agent-zero), [документация интерфейса](https://github.com/agent0ai/agent-zero/blob/main/docs/guides/usage.md), [внешние интерфейсы](https://github.com/agent0ai/agent-zero/blob/main/docs/developer/connectivity.md).

Почему именно он:

- Универсальные задания ближе к его назначению, чем к преимущественно программной специализации OpenHands.
- Иерархическое делегирование уже существует, а не должно создаваться с нуля.
- Есть собственное рабочее пространство, поэтому не требуется сначала разрабатывать интерфейс.
- Локальный Linux-runtime не предполагает обязательной платной облачной песочницы.
- MIT-лицензия удобна для модификаций и коммерческого использования с соблюдением уведомлений.

**Ограничение выбора:** наличие подчинённых агентов не доказывает надёжную параллельную работу большой команды. Это один из первых вопросов будущего разрешённого испытания.

### Eigent — резервный выбор для desktop-ориентированной AWE

Eigent — готовое Electron-приложение поверх CAMEL. В официальном релизе есть Windows EXE; документированы координатор, планировщик, workers, параллельное исполнение, повторные попытки, история и approvals. Это серьёзная альтернатива, а не просто демонстрационный интерфейс. [Релиз Eigent v1.0.7](https://github.com/eigent-ai/eigent/releases/tag/v1.0.7), [Workforce](https://docs.eigent.ai/core/workforce.md).

Но standalone-развёртывание имеет отдельный backend и зависимости. Бесшовная работа Windows↔WSL2, полный контракт внешнего управления заданиями и устойчивость восстановления пока не подтверждены.

Если Agent Zero не пройдёт проверку нужного параллелизма или его интерфейс окажется неудобным для управления командами, **следует заменить основу на Eigent, а не запускать оба продукта как равноправные оркестраторы**.

### OpenHands — предпочтительный специализированный coding-исполнитель

У OpenHands есть SDK, Agent Server, сохранение бесед и Software Factory с developer/reviewer/watchdog. Опубликован Windows Agent Canvas EXE, но desktop-вариант официально обозначен как early preview. [Agent Canvas](https://docs.openhands.dev/openhands/usage/agent-canvas/setup), [Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory).

Если AWE будет преимущественно заниматься разработкой ПО, OpenHands может стать основной платформой. Для универсальной AWE я пока выбираю его **не центром управления, а опциональным исполнителем ограниченных coding-заданий**.

## 3. Рекомендуемая архитектура

**Один агентный центр управления — Agent Zero.** Он принимает миссию, управляет ролями и представляет результат пользователю.

Предлагаемый состав:

1. **Существующий UI Agent Zero и A0 Launcher.** Расширять их только для отсутствующих функций.
2. **Prompt Master → Head Agent → ограниченные исполнители.** Роли на базе профилей; создание новых агентов подчиняется лимитам.
3. **Локальные рабочие среды в WSL2.** Браузеры, программы и тесты выполняются локально, с отдельными рабочими каталогами и ограниченными правами.
4. **Один путь обращения к LLM.** Через него проходят маршрутизация, резервирование бюджета, учёт usage и обработка ошибок.
5. **Локальный реестр миссий и результатов.** PostgreSQL можно использовать для заданий, зависимостей, попыток и событий. Штатную память Agent Zero не нужно сразу переписывать.
6. **Отдельный QA-контур.** Исполнитель не получает права принимать собственный результат.
7. **Git и GitHub.** Код, решения и проверяемые результаты сохраняются без секретов; объёмные логи и персональные данные не отправляются автоматически.

Это **предлагаемая архитектура**, а не описание уже собранной системы. PostgreSQL и слой контроля не должны становиться вторым агентным планировщиком: они обеспечивают состояние и ограничения, а не самостоятельно распределяют миссии.

### Что брать из остальных проектов

| Компонент | Что можно переиспользовать | Решение |
|---|---|---|
| OpenHands | SDK/Agent Server для coding-заданий, события, артефакты, шаблоны reviewer | Подключать при доказанной пользе через адаптер |
| CAMEL | Отдельные toolkits или агента через SDK/MCP | Не добавлять второй Workforce по умолчанию |
| Microsoft Agent Framework | Изолированного специализированного исполнителя через SDK | Сейчас не необходим |
| LangGraph | Локальный граф для конкретного сложного процесса | Не добавлять как второй главный оркестратор |
| Eigent | Готовое приложение как альтернативную основу | Не вырезать UI для Agent Zero: связь с backend делает это отдельным проектом |
| OpenManus | Отдельные инструменты; есть stdio MCP-сервер инструментов | Сейчас мало дополнительной пользы |
| Kortix | Концепции интерфейса и процессов | Не включать в обязательный стек |

Для OpenHands внешний интерфейс документирован. Для CAMEL есть экспорт агента в MCP. Это снижает необходимость переписывать внутреннюю архитектуру, **но не устраняет работу над контрактом задания, отменой, правами и результатами**. [OpenHands Agent Server](https://docs.openhands.dev/sdk/guides/agent-server/overview), [CAMEL MCP export](https://docs.camel-ai.org/mcp/export_camel_agent_as_mcp_server.md).

## 4. Windows UI и EXE

Предлагаю **сначала переиспользовать A0 Launcher и существующий Web UI**, а не создавать новый Electron/Tauri-интерфейс.

A0 Launcher имеет Windows x64 EXE и управляет контейнерными экземплярами Agent Zero. Это desktop-точка входа в реальную систему, но не полностью нативный Windows-runtime. [A0 Launcher v1.9](https://github.com/agent0ai/a0-launcher/releases/tag/v1.9).

Для итогового AWE понадобится установщик или установочная обвязка, которая проверяет зависимости, подключает локальный backend, создаёт ярлыки и обеспечивает диагностику. Использовать готовый механизм упаковки предпочтительнее, чем писать собственный установщик.

**Важно:** EXE не устраняет WSL2, контейнерные образы, браузерные зависимости и необходимость обновлений. Если потребуется «один EXE без Linux и дополнительных компонентов», выбранная архитектура этому условию не соответствует.

## 6. Хватит ли оборудования

**Для облачных LLM и умеренного локального исполнения — предварительно да. Для нескольких мощных локальных LLM одновременно — нет оснований обещать достаточную производительность.**

Стартовая конфигурация, которую считаю разумной:

- 3–4 логических исполнителя, но не обязательно столько одновременно работающих процессов;
- 1–2 активных браузера;
- одна тяжёлая сборка или тестовый процесс;
- остальные задания ожидают в очереди.

Ориентиры памяти — инженерные предположения, не измерения:

| Нагрузка | Ориентир RAM |
|---|---:|
| Windows и обычные фоновые программы | 5–8 ГБ |
| WSL2, Agent Zero, БД и службы | 3–6 ГБ |
| Активный браузер | 0,5–2 ГБ; тяжёлые сайты могут потреблять больше |
| Сборка, тесты или рабочая среда | 1–4 ГБ; крупные проекты — больше |

32 ГБ выглядят достаточными для такого старта. Ограничивать нагрузку будут также CPU, скорость накопителя и охлаждение ноутбука. Десятки агентов, одновременно запускающих браузеры и сборки, — неподходящая цель для этой машины.

Объём VRAM вашей GTX 1650 не проверен. При типичных 4 ГБ рассчитывать на комфортный запуск большой локальной модели с длинным контекстом нельзя. Небольшие модели возможны, но для сложного Head Agent и QA разумнее облачные LLM.

M4 Pro с 24 ГБ — перспективнее для локальной инференции. Его можно позднее использовать как отдельный model server, но объединение компьютеров требует сетевой интеграции. RAM и GPU двух машин автоматически не складываются.

Ollama прямо указывает, что параллельные запросы увеличивают потребность в памяти контекста. На Mac GPU-инференцию следует рассматривать нативно, а не предполагать GPU passthrough через Docker Desktop. [Ollama FAQ](https://docs.ollama.com/faq).

## 7. Router.Cheap, vision и MCP

Router.Cheap документирует OpenAI-compatible базовый URL **`https://router.cheap/v1`**, Chat Completions, Responses, streaming, usage и получение списка моделей для конкретного ключа. [API reference](https://router.cheap/docs/api).

Публичный каталог сейчас показывает **73 позиции**, а не около 49. Это включает разные типы моделей и не доказывает доступность всех позиций вашему ключу. [Каталог цен](https://router.cheap/pricing).

Предлагаемая интеграция:

- Настроить совместимого провайдера в Agent Zero.
- Начать с небольшого разрешённого набора моделей, а не автоматически включать весь каталог.
- Проверить tool calling, streaming, структурированные ответы, usage и ошибки каждого выбранного маршрута.
- Для vision отдельно проверить передачу скриншотов и совместимость с инструментами браузера.
- Для MCP подключать только проверенные серверы с минимальными credentials и ограниченными инструментами.
- Хранить ключи вне UI-бандла, Git и агентных логов.

**Выбор дешёвой модели должен выполнять AWE по своей политике.** Возможность шлюза обслуживать разные модели не означает, что он сам оптимально выбирает исполнителя миссии.

Router.Cheap не публикует фиксированные численные rate limits. Документация описывает ограничения коротких запросов и ошибки `429`; поэтому обещать заданный параллелизм без тестирования нельзя. Совместимость протокола также не доказывает качество модели, стабильность маршрута или условия хранения данных. [Лимиты и ошибки](https://router.cheap/docs/api), [безопасность](https://router.cheap/security).

## 8. QA, состояние и настоящая автономность

### Независимый QA

Нужны три элемента одновременно:

1. Проверяющий получает критерии миссии и фактические артефакты, а не только отчёт исполнителя.
2. Проверяющий использует отдельный контекст и не позволяет исполнителю изменить результат приёмки.
3. Где возможно, итог определяется воспроизводимыми тестами, а не мнением второй LLM.

Для разработки это тесты, сборка и проверка конкретного commit. Для исследований — проверка источников и вычислений. Для браузера — подтверждение фактического состояния страницы.

Другая модель снижает часть коррелированных ошибок, но **не гарантирует объективность**. Число исправлений ограничивается бюджетом и попытками; при исчерпании система останавливается.

### Состояние и восстановление

Следует сохранять задания, зависимости, исполнителя, попытки, бюджет, события инструментов и артефакты. После аварии система должна различать «не начиналось», «выполнялось», «эффект неизвестен», «выполнено» и «принято QA».

**История чата — не checkpoint внешнего мира.** Нельзя автоматически повторять отправку письма, публикацию или другое действие с неизвестным результатом. Нужны идемпотентность, проверка фактического эффекта либо ручная сверка.

### Независимость от Manus

AWE должна работать собственными локальными процессами, с собственными ключами и инструментами. Сессионные возможности Manus не становятся автоматически частью AWE.

Для WSL2 недостаточно просто включить systemd: Microsoft предупреждает, что systemd-сервисы сами по себе не удерживают WSL-инстанс активным. Нужны проверенный запуск со стороны Windows, контроль процесса и испытание закрытия UI. При сне или выключении компьютера локальная работа прекращается. [Microsoft WSL systemd](https://learn.microsoft.com/en-us/windows/wsl/systemd).

## 9. Этапы и расходы

Ниже — **план будущей работы, не разрешение на её запуск**.

| Этап | Результат и условие перехода | Оценка инженерных часов |
|---|---|---:|
| 1. Проверка основы | Локальный запуск, Router.Cheap, MCP, vision, делегирование; решение Agent Zero или Eigent | 16–32 |

Это оценка трудоёмкости, не длительности сессии Manus и не фиксированная смета. Совместимость готовых компонентов может существенно изменить объём работ.

### Кредиты Manus

**Достоверную абсолютную оценку кредитов сейчас дать не могу.** Нет измеренного расхода на репрезентативную интеграцию, а инженерные часы не конвертируются в кредиты по постоянному коэффициенту.

Правильный порядок — отдельно ограничить первый разрешённый этап, измерить расход и получить новую оценку оставшихся работ. Устанавливать сейчас обещание вроде «весь проект за 10 000 кредитов» было бы неподтверждённым.

### Что лучше выполнить через локальный Codex

Локальному Codex разумно передать ограниченные изменения адаптеров, тесты, упаковку, CI и исправления, найденные QA. Каждая работа должна иметь отдельную ветку или worktree, критерии приёмки и ревью.

Manus полезнее оставить для выбора архитектуры, исследования совместимости и проверки этапов. **Codex локально выполняет инструменты, но используемая им LLM не обязательно локальна или бесплатна.** Наличие Codex на вашем компьютере не подтверждено; в ТЗ указано наличие OpenCode.

### Эксплуатационные расходы

Обязательная аренда облачных песочниц и подписка Manus для работы итоговой AWE — **$0 в предлагаемой архитектуре**. Облачные LLM оплачиваются отдельно.

Это арифметические сценарии, **не прогноз среднего задания AWE**. Объёмы должны включать всех исполнителей, QA, исправления и повторно переданный контекст. Изображения, tier pricing, reasoning и другие услуги могут увеличить счёт.

Для первого будущего теста разумен отдельный небольшой лимит API, например $20–50, без автоматического пополнения. Дополнительно возможны расходы на подпись EXE, резервное хранилище, лицензии сторонних сервисов и Docker Desktop, если бизнес не соответствует бесплатным условиям.

## 10. Риски и пределы гарантий

Главный риск — принять наличие ролей и красивого мониторинга за надёжную организацию работы. Агенты могут повторять ошибки друг друга, неверно декомпозировать миссию, расходовать контекст и объявлять успех без проверяемого результата.

Другие существенные риски:

- Prompt injection через сайты, документы и MCP-ответы.
- Обход ограничений через разрешённый shell.
- Утечки ключей, данных и приватных материалов.
- Повторение внешних действий после сбоя.
- Изменения API, моделей, лицензий и upstream-проектов.
- CAPTCHA, MFA, антибот-защита и ограничения сайтов.
- Конфликты Windows/WSL-путей и браузерных профилей.
- Превышение бюджета из-за параллельных уже запущенных запросов.
- Уязвимые зависимости и чрезмерные права контейнеров.

Я не могу гарантировать неограниченную автономность, отсутствие галлюцинаций, безошибочную QA-оценку, универсальное управление любым Windows-приложением, строгое exactly-once для любого внешнего сервиса или абсолютную безопасность контейнерной среды.

## 11. Как отличить систему от прототипа

Приёмка должна опираться на фактические результаты:

| Проверка | Признак работающей системы |
|---|---|
| Несколько типов миссий | Выполняются разработка, исследование и локальный браузерный сценарий, а не один заранее подготовленный пример |
| Динамическое делегирование | Видно создание исполнителей, назначение задач и получение артефактов |
| Независимый QA | Намеренно испорченный результат отклоняется |
| Контроль расходов | Новые вызовы блокируются с учётом зарезервированных средств |
| Контроль прав | Запрещённое действие блокируется технически, а не только инструкцией |
| Авария исполнителя | Нет ложного «успеха»; задача корректно восстанавливается или останавливается |
| Перезапуск компьютера | Сохраняются миссия, история и результаты; неизвестные эффекты не повторяются вслепую |
| Закрытие Manus | Задание продолжается без Manus-процессов и credentials |
| Проверка установщика | Установка и удаление проходят на отдельной Windows-среде с документированными зависимостями |
| Повторяемость | Есть заранее выбранный набор испытаний, результаты, расходы и доля неудач |

Необратимые действия, платежи, публикации и чувствительные операции должны оставаться за подтверждением человека, если отдельно не согласована более узкая безопасная политика.
