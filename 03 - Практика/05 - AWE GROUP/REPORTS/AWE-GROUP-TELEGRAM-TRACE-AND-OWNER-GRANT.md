# AWE GROUP — аудит последовательности OpenCode по экспорту Telegram и согласие владельца

**Источник:** пользовательский архив `ChatExport_2026-11-10.zip`, SHA-256 `bacae8dc25d43c129d3348643054abc748731d492d860cf1b8ac9564b7d7ba7e`. Извлечён `messages.html`: **480 переписных сообщений**, примерно 19 исходящих от владельца и 461 сообщений/событий бота, плюс **160 текстовых файлов с выгрузками edit/patch**. Экспорт охватывает начальные подключения до начала offline cloud-envelope checkpoint, но не содержит доказательств последующей real LLM вертикали. Сырой ZIP не опубликован в GitHub.

**Метод:** прочитаны текст, хронология и выборочные прикреплённые patch-фрагменты (включая CLOUD-ENVELOPE.md и CHECKPOINT). Изображения Router.Cheap, переданные владельцем отдельно, дают имена и ограничения ключей. Исполнение кода в пользовательском WSL не выполнялось.

## Процесс от первого сообщения до текущего результата

1. **Бот и модель.** Telegram-подключение показывает OpenCode 2.2.6 и Telegram Bot 0.27.0; выбран проект `/home/nox/awe-e1-live-runtime`; первоначально модель `opencode/big-pickle`, затем `routercheap/gpt-6.1-sol` (high). Два `ROUTE_OK` подтвердили только соединение инженерной модели, не готовность платной LLM внутри AWE.
2. **Задание.** В истории виден ранний вариант большого /goal, затем окончательный и принятый текст `AWE GROUP — E1-LIVE AUTONOMOUS LAUNCH` (то самое каноническое задание из Academy GitHub). Финальный текст авторизует аудит/сохранение/разработку E1→CAREER-01 и бюджет USD 20 при ограничениях, не определяя key path/model ID.
3. **Сохранение и worktree.** OpenCode запускает аудит Git/тестов/доступов, резервное копирование, создаёт `awe/e1-autonomous-launch-20261110` и переносит сессию из исходного проекта в `/home/nox/awe-e1-launch-20261110`. При переходе Telegram bridge сначала отображает исходный проект/иную ветку; `/detach` и `/recent` снова выбирают прежнюю выполняемую сессию. Это важный источник путаницы при API-диагностике: **название сессии осталось «Проверка подключения Router.Cheap», даже когда её цель стала большой AWE /goal**.
4. **Durable execution.** Фиксируются native bridge, file journal, cursors, atomic plan/start, task admission и ограничения повторов. Отдельные доклады и проверочные evidence созданы в локальном worktree.
5. **Independent QA.** Последовательно введены отдельный read-only reviewer PID, `bubblewrap` sandbox, host-reviewed RPC, проверка полного poststate, прочная запись FAIL/BLOCKED, защита от поддельных receipts/артефактов. Это по-прежнему технический контур, не доказанная смысловая точность настоящего LLM-reviewer.
6. **Атакующие/holdout тесты.** Выявлены три неправильных смысловых `PASS`, прошедших RPC/hash-gate; их обнаружил дополнительный evaluator. Экспорт подтверждает сознательное разделение «хеш верен» и «решение по существу верно».
7. **Terminal lifecycle.** Изучен существующий native `cancel`; затем реализован опциональный host-only receipt и атомарное завершение точного root+children набора при FAIL/BLOCKED. `307/307 PASS` + baseline `442/442 PASS`, 14 SIGKILL/lost-ACK окон в тестах. Не боевой auto-completion.
8. **Route/budget.** Инженер обнаружил mismatch: live runner выбирал разные модели ролей и считал деньги через legacy-проекцию; cloud broker был strict-JSON без live tool-loop; D09 production migration привязана к защищённой PG 5433. Создан zero-cost route/budget dry-run: `96/96 PASS` вместе с cloud controls, модели и расходы **синтетические**.
9. **Cloud envelope.** Реализован `E1/live/cloud-envelope.mjs` с ограничением UTF-8, длины, аргументов, call IDs, предопределённых tools и fixed host-route. Из прикреплённого `CLOUD-ENVELOPE.md`: используется `createOfflineCloudModelBrokerForTests`, `OFFLINE_TEST_DOUBLE`, `OFFLINE_ENVELOPE_JOURNAL`, **не установлен в native production runner/D09**. `162/162 PASS` для offline/cold-process, `307/307` native-regression, `442/442` baseline, по последнему сообщению OpenCode. Реальный interpreter и файловые инструменты вызывались на scripted responses, не на paid provider.
10. **Последнее сообщение владельцу.** Отдельно подтверждён архив 292 файлов и CHECKPOINT по докладу инженера. Первая точка `NOT MET`; дальше инженер планирует atomic adapter receipt ↔ native cursor ↔ D09 reservation. **Все эти проверки заявлены самим исполнителем**, сырые финальные архивы и живую БД данный Telegram ZIP не заменяет.

## Роль процессов
```text
Owner → Telegram Bot bridge → OpenCode + его GPT-6.1 Sol
                                    │
                          изменяет код, тестирует
                                    ↓
                       AWE E1 test runtime
           Head/worker/tools/reviewer + native PG fixture
```
**Telegram Awe Agent — название интерфейса, а не доказательство, что сам Head AWE уже управляет реальными задачами.** OpenCode сейчас инженер-разработчик; AWE — создаваемая исполнительная платформа. Изолированные модельные сценарии не заменяют live product capability.

## Связь и сессии
В экспорте несколько `ECONNRESET` во время инструментальных операций. После сообщений об этих ошибках инженер неоднократно продолжал публикацию результатов и редактирование модулей. Переименование/перенос рабочей директории и отстыковка/повторный выбор чата могут объяснить различие между Telegram и прямыми API-запросами. **Не объявлять сессию потерянной из-за одного 404 или `active={}`**, не делать слепой `/abort` или повторное задание.

## Состояние расходов и разрешений
Скриншот Router.Cheap владельца: отдельный ключ OpenCode показан с limit около USD 25.31 и remaining USD 18.97, `awe-e1-staging` с USD 10/10 на момент снимка. Это не live balance, не бюджет проекта AWE. Telegram `routercheap/gpt-6.1-sol` относится к инженерной сессии. `new_paid_generations_initiated_by_tools=0` в E1 CHECKPOINT означает отсутствие **новых платных генераций самой разрабатываемой системы**, а не бесплатность работы OpenCode.

**Владелец явно разрешил начало контролируемых платных LLM-тестов E1 в пределах исходного USD 20.** Ссылка на документ согласия: `OWNER-AUTHORIZATION-E1-PAID-LLM-2026-11-10.md`. Для первого теста рекомендованы staging-key и одноимённый проверенный engineer model route, но конкретизацию модели/ключа нужно зафиксировать у host. Не изменять hard cap существующего ключа или использовать OpenCode key для E1 без подтверждения. Продолжать provider actual debit + D09 reconciliation, не устраивать direct bypass.

## Остаётся
- Закончить live, не mock, границу adapter ↔ D09 ↔ provider actual debit/ACK и native cursor с verified permission/credential binding.
- Выполнить **одну** реальную Head→worker→file tool→independent semantic reviewer→cold persisted readback миссию. Зафиксировать bill/receipts и контрпример смысловых ошибок QA. Только после этого checkpoint 1 может стать `MET`.
- Далее динамическое формирование команд, параллельность, выбор моделей/инструментов, самодоработка, реальные тесты и CAREER-01 в утверждённом полном масштабе.
- Worktree огромен (неотслеживаемые файлы); безопасно настроить Git author в локальном scope и зафиксировать изменения по allowlist без секретов/PGDATA.

## Инженерная оценка
**Путь OpenCode осмыслен, последовательность в Telegram реальна:** он встраивает безопасность и долговременное состояние, а затем готовит модельный контур. Но функция ради которой проект существует — автономное выполнение сложных задач — не проверена. Теперь при наличии owner grant нельзя бесконечно откладывать реальную вертикаль только ради расширения offline фикстур; её запуск зависит от безопасной технической интеграции, не от повторного согласия на бюджет.
