# H–J. Передача Sol и исполнителям

## H. Критический путь и стоимость работ

**Целевая демонстрация:** владелец один раз задаёт миссию и подтверждает мандат. Система из двух разрешённых источников находит реально подходящую вакансию, сверяет её с подтверждённым опытом, формирует персональный пакет, самостоятельно выполняет один разрешённый первичный отклик, независимо читает результат и начинает мониторинг. Если канал вернул неопределённый исход, правильный результат пилота — HOLD до сверки. Считать такой опыт успешной подачей нельзя.

| Работа | Зависимости | Оценка, чел.-дни | Принимаемый выход |
|---|---|---:|---|
| 01. E1-профиль, контракт миссии и политика | Изолированное дерево, проверенные исходники | 0,75–1,25 | Версионный `MissionSpec` и `MissionGrant`, отдельный scope E1, test principal без личных данных |
| 02. Durable worker, DAG, admission и outbox | Контракт 01 | 1,25–2 | Два независимых read jobs перекрываются. После рестарта новый fence, budget и business key сохранены |
| 03. Ingest двух источников, profile и дедупликация | Параллельно 01/02 по интерфейсу | 1–1,5 | Карточки вакансий с provenance/freshness, canonical opening, причины пропуска и реестр покрытия |
| 04. Живая модель, head и QA пакета | Контракты 01, fixtures 03 | 1–2 | Локальная модель выдаёт валидные решения, версии двух CV и адресное письмо проверены. Облачный маршрут опционален |
| 05. Начальная отправка и сверка | Контракт 01, интерфейс outbox из 02, fixtures 03/04 | 1,25–2 | Первый изолированный send adapter с readback, потеря ACK и запрет ответа работодателю проверены |
| 06. Сборка, мониторинг и ограниченный live run | 02–05, отдельно предоставленный доступ к E1 и мандат | 0,75–1,25 | Remote ID, readback и версия пакета на реальной вакансии либо точный блокер, затем первое чтение мониторинга |
| **Итого до одного отклика** | С параллельной работой по общим контрактам | **6–10** | При двух инженерах ориентир **4–7 рабочих дней**, при одном — 6–10. Сроки регистрации приложений, выдачи прав и подготовки отсутствующих материалов сверх этой оценки |
| 07. Портфолио с нуля и дополнительные реальные проекты | Подтверждённые материалы, доступ к публикации отдельно | 4–10+ | Работающие сайты с независимым browser QA, версии для CV и проверка публичных ссылок |
| 08. Полный CAREER, long-run, знания и updater | 02–06, присоединение 07 по готовности | 3–6 плюс 24 ч наблюдения | Полный обнаруженный пул, новые sources/markets, ограниченный параллелизм, отчёт, сигнал приглашения, проверенный restart/rollback |

Если владелец не имеет пригодного для выбранной вакансии CV/кейса, подготовка такого материала входит в критический путь. Если нет разрешённой почты или явного канала работодателя, продолжить проектирование, поиск и подготовку пакетов. Только наблюдаемая отправка засчитывается в live milestone. Расширенный сайт и конкретный HH applicant endpoint не блокируют вакансию, принимающую подтверждённые существующие материалы по email.

## I. Рабочие задания

Общее распоряжение для всех задач: новый project_id и новые ресурсы E1. Путь 92ef — эталон чтения, не рабочая песочница. Использовать commit c53 для runtime-происхождения и HEAD 3579aee для evidence. Проверить необходимый subset источников по review pins, определить, какие нужны в build, не импортировать всю историю незакоммиченных журналов. Приёмка через нормальный entrypoint, включая restart. Обязательные записи каждого прогона: build/manifest hash, policy/mission ID, inputs, границы сети, счётчики реальных и mock эффектов, обычная и негативная ветви, время, результаты, ограничения.

### 01 · Sol / runtime. Вход миссии и полномочия

В существующем `createInt04OfflineHost`/composition family добавить явный E1 entry и typed ports модели, queue, policy, store и effects. Использовать `AUTO-01/contracts.mjs`, `draft.schema.json` и валидатор DAG. Развести E1 и старые режимы по имени профиля, не снимать проверки `AUTO01_MOCK_ONLY` и `LOOPBACK_MOCK` с исторических путей. Вход `mission.create(goal, project, owner, criteria, facts_refs)`. Выход `mission_id, spec_hash, plan_revision, unresolved_owner_decisions`. До начала live нужен immutable grant по схеме [полномочий](03-architecture.md). Пример политики для теста ниже **не является допуском**.

```json
{
  "profile": "CAREER_E1",
  "owner_id": "owner_fixture",
  "project_id": "career_fixture",
  "mission_id": "career_pilot_01",
  "operations": ["vacancy.read", "profile.match", "package.build", "initial_application", "status.read", "owner.notify"],
  "destinations": ["verified_application_address_in_current_opening"],
  "max_submissions": 1,
  "max_parallel_reads": 2,
  "max_paid_spend_micros": 0,
  "currency": "RUB",
  "subsequent_employer_messages": false
}
```

При реализации `destinations` компилируется broker в разрешённые адреса по достоверному первоисточнику, а не проверяется как произвольная строка из плана. Политика дополняется issued_at, expiry, version, data classes, attachment hashes, revocation epoch и аутентифицированным решением владельца. При изменении expiry/адресата/резюме сверяются версии. Истёкший grant не возобновляется записью из старого checkpoint. Приёмка: неверная подпись/actor, expired, другая миссия и попытка самостоятельно повысить бюджет отвергнуты. Черновик остаётся доступным без grant.

### 02 · Sol / storage. Один координатор и долговечное исполнение

В новой схеме E1 того же логического authority завести `mission, job_dependency, job_lease, source_cursor, vacancy, vacancy_alias, application_intent, inbox_event` и связи с D03/D09. Schema additive, per-project ACL, индексы для claim и внешнего ID, FK для версии артефакта. Маппинг: D03 отвечает за состояние задач и принятый результат, D09 — reserve/attempt/settle, `application_intent` — таблица эффекта **внутри той же транзакционной границы**. При проектировании исключить dual-write между двумя DB. Все большие payload и исторические web snapshots хранить вне одного D03 body.

Принимаются `plan.propose` → проверка capability/dependencies → `claim(node, capability, fence, lease_until)` → `finish(lease, artifact_ref, evidence)`. Очередь обслуживает независимые ветви параллельно, защищает ресурсы по task/source/account и поддерживает backpressure, bounded replans, deadline, cancellation и фоновый monitor poll. Сбой read job допускает повтор, отправка следует протоколу [outbox](05-career-integrations.md). Критерий: при двух worker и одной вакансии создаётся одна первичная операция даже в разных mission и при иной версии CV. Устаревший worker не отправляет и не завершает task после takeover. Показать timings двух независимых задач, задержку зависимой и сохранность бюджетов после crash.

### 03 · Исполнитель интеграций. Получение вакансий и профиль

Сначала два адаптера `listOpenings(cursor, since, bounds)` / `readOpening(external_id)`: разрешённый карьерный сайт/официальный feed и ATS либо HH со специально разрешённым чтением. В offline fixtures — две копии одного requisition, две похожие разные роли, устаревшая вакансия, вакансия с анкетой, вакансия с разрешённым email, 429 и redirect на private IP. Результат `{source, external_id, canonical_url, employer, role, location, fetched_at, content_ref, terms_class, apply_channel, next_cursor}`. Закрепить критерий свежести и reread перед send. Не сохранять исходную HTML в общую память по умолчанию. Проверка: идемпотентный повтор страниц даёт те же canonical keys, закрытая позиция не поступает в outbox, сомнительный alias не отправляется автоматически. Из реестра понятно, какие рынки ещё не прочитаны.

### 04 · Исполнитель моделей и независимый QA. Head и пакет

Реализовать `proposeSpec / proposePlan / classify / draft / repair` поверх подготовленного model port и выбранного local endpoint. Host выбирает материал для каждого обращения. Из `AUTO-01/context.mjs` взять компактный handoff, из `llm02/protocol.mjs` — кодирование/декодирование там, где оно совместимо. Отдельно bind E1 transport через SEC/D09, запретить автоматические вызовы tools внутри model SDK. Task class, features, регион, quote, timeout, input/output cap, reserve, idempotency и validation обязательны до отдачи результата.

Head создаёт 0..N исполнителей из разрешённых role profiles, назначает минимум достаточных. При отсутствии capability выдаёт запрос на разработку/PR. Первая задача «найти и подготовить»: read-ветви работают параллельно, local analyst выдаёт match + evidence refs, writer создаёт две версии резюме и один персонализированный пакет для выбранной вакансии. Экзаменатор отдельно читает факты и артефакты. Тесты: запрещённый cloud destination, подложная ссылка, ложный факт, модель, вернувшая tool call вне allowlist, outage одного route. Критерий на реальном согласованном запуске — хотя бы одно зафиксированное модельное решение с model digest/ID и принятым независимым QA. Статический шаблон с mock-ответом в этот критерий не засчитывать.

### 05 · Исполнитель внешних действий. Первый отправитель

API адаптера — `preflight(intent)`, `sendInitial(permit, frozen_packet_ref)` и `lookupReceipt(correlation)`. Получатель выводится из поля, извлечённого из проверенного работодателем канала, пересверяется непосредственно перед отправкой, Post/SMTP-код отсутствует у head и analyst. Разрешить одну вакансию, один recipient, фиксированный sender, content hash, одну версию вложений. Восстановление: `SENDING → CONFIRMED | UNKNOWN`, убрать автоповтор transport SDK, сохранять provider status и receipt; последующая переписка заблокирована broker независимо от роли модели. Истекшая сессия оставляет job в reauth, предусмотрена ручная остановка.

Условия сдачи: при потере ACK и повторном запуске после эффекта — максимум один внешний message; при двух источниках/новой кампании — одна заявка; при ответе рекрутера повторная исходящая операция отклонена. `SENT` устанавливать только после достаточного подтверждения канала, `INVITED` — только по входящему evidence. [Готовые модельные случаи падения](career-crash-fixture.mjs) — переносить на PG + HTTP test double, не включать SQLite-демо в действующий runtime.

### 06 · Интегратор и QA. Первый live и наблюдение

Сначала выполнить реальную связку с fixtures и локальным transport, затем предоставить владельцу policy с конечным сроком, лимитом 1, scope OAuth и примером пакета. Получить один допуск на миссию. Внешнее действие выполняет система в рамках выданного мандата. Повторный показ той же вакансии на ручное согласование в штатном режиме не требуется.

В отчёте `LIVE_APPLICATION_01`: URL и актуальность источника, основание пригодности, sealed packet refs, grant hash, reservation/attempt, внешний message/job ID, подтверждение отдельным чтением, D03 transition, фактическая цена, момент следующей проверки и ручная возможность отменить миссию. Владелец получает подходящий артефакт и сообщение о статусе. При UNKNOWN автоматически сверять, не выдавать receipt за доставку. Критерий E1-пилота включает работу мониторинга после первого действия. Анонимизированный отчёт публикуется в проектной линии, приватные материалы — только в ограниченном хранилище.

### 07 · Frontend/backend и QA. Полноценное портфолио

Из утверждённых фактов составить карту кейсов для двух направлений. Дизайнер задаёт структуру, типографику, адаптивные состояния и сценарии, разработчик поставляет работающий сайт и отдельные проекты, reviewer проверяет URL каждого кейса. Реализовать фактический backend для заявленных функций. Демо должно быть явно маркировано там, где действительно является демо. Не добавлять коммерческие результаты, клиентов и метрики без источника. Согласованная публикация выполняется отдельным узким deploy credential. Доказательства — commit/build, unit/integration/E2E, accessibility, performance, screenshots, structured visual review и независимый публичный readback. [Рубрика](06-resilience-updates.md)

### 08 · Runtime/QA/release. Миссия на сутки и дальнейшее развитие

Расширить однократный мандат до серии разрешённых заявок и фиксированной стоимости, включить coverage отчёт, входящие статусы и приоритетные сигналы. Подготовить базу навыков, пробное интервью и brief по каждой заинтересованной компании. Контрольная миссия переживает рестарт и пропадание worker, независимый QA повторно использует утверждённый skill на новой вакансии. Один безопасный versioned worker update проходит staging и откат без потери сообщений. Готовность к другим линиям подтвердить переносом **того же** профиля исполнения на задачу другого типа, например «исследовать библиотеку и построить сайт», с отдельными критериями и ролями. При этом первая полноценная CAREER не объявляется универсальной production-квалификацией.

### Контракт команд для следующей поставки

Первую команду можно выполнить сейчас. Путь `e1/cli.mjs` ниже — **обязательный предлагаемый интерфейс для разработчика**, пока отсутствует. Будущий runner принимает только явные инфраструктурные профили, выводит redacted JSON. Credentials и send grants в аргументы не передаются.

```sh
node ASTRA-AUTONOMY-AUDIT-2026-11-08/career-crash-fixture.mjs
node e1/cli.mjs verify --profile fixture --case duplicate-cross-source
node e1/cli.mjs verify --profile fixture --case crash-after-provider-accept
node e1/cli.mjs verify --profile fixture --case denied-followup
node e1/cli.mjs verify --profile fixture --case privacy-route-denied
node e1/cli.mjs verify --profile fixture --case concurrent-budget
node e1/cli.mjs verify --profile isolated-staging --case resume-after-reboot
node e1/cli.mjs verify --profile isolated-staging --case restore-and-reconcile
node e1/cli.mjs report --mission career_pilot_01
```

Ожидания по порядку: один business key и эффект; восстановленный receipt с одним send; ноль исходящих follow-up; ноль байтов в cloud transport; сумма settle+reserve ≤ cap; текущий fence и сохранённый cursor; прежние действия не воспроизведены при restore; финальный отчёт разделяет submitted, confirmed, invited, unknown и показывает следующее действие. Для staging нужны отдельные ресурсы E1. Ни одна команда не должна выбирать `92ef`, сохранённый PGDATA, production account или внешнюю отправку по умолчанию.

## J. Решения, которые действительно остаются владельцу
