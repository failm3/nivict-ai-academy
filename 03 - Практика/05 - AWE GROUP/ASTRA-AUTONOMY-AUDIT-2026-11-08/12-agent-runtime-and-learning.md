## Ответственность и обычный ход задачи

| Кто | Решает | К чему имеет доступ |
|---|---|---|
| Владелец | Бизнес-цель, личные факты, права, средства, качество результата по назначению | Одна подписанная policy для ограниченной миссии, stop/revoke, отдельное утверждение домена и публикации |
| Мастер требований | Предлагает критерии из цели, отличает обязательное от гипотез, обнаруживает конфликт | Цель, ссылки на политику и входные материалы. Блокирующий вопрос задаёт только при существенном выборе владельца |
| Главный агент | Предлагает DAG, роли и аргументы, меняет план по результатам, запрашивает QA | Краткая сводка миссии, основания и разрешённый модельный broker. Возвращает данные по схеме |
| Менеджер проекта | Отслеживает scope, сроки, очередь решений, blockers и итог | В Pilot это роль/проекция coordinator. Отдельный агент нужен только при измеренном перегрузе head |
| Программный координатор | Валидирует spec/plan, запускает готовые задачи, лимитирует, проверяет fence, фиксирует переходы | Единственный владелец lifecycle D03 через проверенный storage port; D09 владеет попыткой/резервом/settlement |
| Registry, model broker, effect broker | Версии и допуски, конкретный маршрут, выдача одного права на действие и readback | Адрес/метод/данные, hard cap и мандат. Только credential adapter имеет доступ к секрету своего origin |
| Worker и QA | Worker выполняет ограниченное задание; QA независимо проверяет frozen artifact и внешний результат | Разные principals и рабочие каталоги, signing key и oracle недоступны producer. Самоотчёт DONE открывает экзамен |

`Goal → MissionSpec → PlanRevision → ReadySet → claim + reserve → execute → ArtifactRef → QAResult → accept/repair/wait → monitor`. У новой версии spec есть parent digest и причина, выполненные результаты переиспользуются только при совпадении требований, актуальных inputs и policy. Каждая смена цели пересчитывает затронутые зависимости и бюджет, предыдущая история сохраняется. За повторяющийся FAIL после одного локального repair head выбирает смену проверенной стратегии, уменьшение scope в рамках цели или WAIT. Просрочка, отзыв и неизвестный результат видны в сводке. UI/CLI показывают принятые факты, узлы DAG, spend/reserve, receipts и что ожидается дальше.

## Durable state и граница эффекта

Использовать одну PostgreSQL E1, новую БД/project, без связи с PGDATA исторического E0. D03 — spec, task, revision, dependencies, state и evidence refs; D09 — мандат/резерв/attempt, `outbox` рядом с транзакцией эффекта. Большие blobs вне project snapshot. Источник вакансий и версии продукта хранятся в своих доменных таблицах под ACL. Не удерживать SQL-транзакцию во время HTTP/LLM. Очередь `FOR UPDATE SKIP LOCKED`, heartbeat и монотонный fencing token в БД. Проверка доступного бюджета, уникального бизнес-ключа и записи intent — в одной транзакции; dispatch broker проверяет текущий fence и мандат непосредственно перед выходом.

| Класс | Стабильная идентичность | После crash |
|---|---|---|
| Read/compute | `project, task, input_hash, executor_version` | Повтор разрешён после lease expiry, сохранение через CAS, результат старого owner отвергнут |
| A · initial application | `owner, canonical_opening_id, initial_application` сквозь миссии и каналы | Переход READY→SENDING durable до сети, ACK/UNKNOWN удерживают intent. Lookup первоисточника/почты; отрицательный поиск с eventual consistency не разрешает повтор |
| B · staging/release | `project, target_slot, release_digest`, expected previous release | Независимо прочитать digest активного слота и выполнить smoke. Не менять более новую версию при позднем completion. Новая сборка или rollback — новая явно разрешённая операция |
| Модельный вызов | `mission, logical_request, attempt, quoted_route` | Доказанный pre-send сбой освобождает резерв; possible billed timeout → UNKNOWN с пределом дальнейших расходов. Восстановление чата не выдаёт новый бюджет |

Начальный scope — два параллельных read/compute, один sender на владельца, один writer на release slot, отдельный QA. При просадке p95, конкуренции CAS и давлении RAM уменьшать число workers. После пропадания сети продолжаются локальные QA/build/индексирование, сетевые операции ждут. Оплата, время и действующие grants ограничены и после рестарта.

## Сравнение runtime и размещения

| Вариант | Затраты / риск | Решение |
|---|---|---|
| AWE coordinator + простые workers | Минимальный новый claim loop, live ports, повторное использование D03/D09 и QA. Риск горячего project snapshot и недостаточной изоляции | **Выбрать.** Разгрузить snapshot, проверить две независимые задачи и реальные процессы |
| Hermes subagent lifecycle | Есть специализации и делегация. В локальном binding `REAL_HERMES_NOT_RUN`, reconnect ограничен, наследование tools требует canary. Дополнительные retries/crons расходуют бюджет без ведома AWE | Допустить как leaf, если все tool/model calls идут через broker и общий fence. Не ставить на путь первого отклика. [Upstream Hermes](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/delegation.md) |
| Agno Team/Workflow/AgentOS | Даёт durable jobs, approvals и teams. Потребуются Python bridge, миграция lifecycle/readback и повторная проверка бюджета | Только если AWE не выдерживает согласованную нагрузку или стоимость поддержки выше. Для проверки — одинаковый A/B replay в disposable staging, измерить cost/accepted, restart, duplicate count и effort. Сначала shadow без effects, переключение единственного writer после drain и rollback rehearsal. [Agno](https://docs.agno.com/) |
| Отдельный durable workflow engine | Подходит при большом числе workflows/таймеров, но дублирует очередность, recovery и observability уже в Pilot | Пересматривать при замеренном backlog с нарушением deadline после оптимизации единственного PG. До измерения не брать зависимость |

**Минимум.** Один постоянно включённый authority на Windows/WSL с отдельным service identity, PG E1, очередью, broker, локальными артефактами и одним worker. Для закрытых данных либо локальная модель на этом ПК после проверки, либо доступный Mac с Qwen. Минимум для непрерывного закрытого inference — один работающий узел, который реально выдержал canary; если модель лишь на Mac, в расписании два узла или явный WAIT. Центральный Windows ранее измерен как i5-10300H, ~32 GiB, GTX 1650. Наличие бинарей и кэша не подтверждает p95.

**Расширение.** Mac M4 Pro 24 GB — локальный inference/vision, PC1 — authority/queue/broker, PC2 — отдельные browser/build/QA workers и зашифрованный backup после подтверждения его диска, RAM, CPU и uptime. Защищённый LAN/WireGuard, индивидуальные ключи, workers обращаются к gateway, DB не выставлять в интернет. Роль центрального узла выбрать по uptime и восстановлению. Active-active DB и автоматическое избрание sender пока не окупаются. ОС Keychain/DPAPI либо vault под отдельной учётной записью, refresh и выдача коротких scoped handles. В логах только ID, хеши, тайминги и стоимость. Работоспособность после перезагрузки проверить с заблокированным и с доступным vault.

## Память и обучение

| Слой | Запись и чтение | Проверка |
|---|---|---|
| Task state, действия, деньги | D03/D09, CAS, проектные ACL; восстановление от последнего durable commit | После kill восстановить тот же job/intent и остаток лимита |
| Исходники и артефакты | Content-addressed bytes + version/provenance/retention; запись объекта до публикации ref, сбор orphan после grace | Независимый QA перечитывает digest; несовпадение даёт HOLD |
| Проектные знания | DATA-02 record со scope, source, validity, supersedes; retrieval фильтрует по доступу до поиска | Межпроектный запрос B не возвращает резюме A; удаление/архив исключает текст из выдачи |
| Корпоративные практики и навыки | После независимой проверки и разрешения на reuse — очищенный skill/pattern, версия и rollback | Второй агент решает новую задачу по карточке без истории автора |
| Ошибки/качество исполнителей | Append-only outcome, класс отказа, исправление, оценка QA, runtime/model version, дата, размер выборки | Health и selector не применяют чужие доменные результаты к другому классу без canary |
| Рабочий контекст | Временно: цель, критерии, несколько refs, разрешённые tools; итог до ~1 KiB с refs, стоимостью и неопределённостью | После очистки контекста head восстанавливает следующий шаг по state + refs. Тексты вакансий/секреты в head другой линии не попадают |

Начать с SQL/FTS и версионированных объектов. Добавить pgvector/Supermemory при воспроизводимом росте recall@5 и проверенных ACL/deletion/latency. Источник сведений, retrieval, навыки и изменение весов имеют разные циклы жизни.

**Пример «освой технологию».** Агент читает официальную спецификацию web component, фиксирует версии и ограничения → делает небольшой feature в песочнице → другой QA проверяет клавиатуру, фокус и поведение после переподключения → из принятого результата выделяется скрипт/regression и skill card → другой агент применяет её на отличном компоненте и сравнивает результат. Неудача означает candidate, запись ошибки и исправление. Память хранит ссылку на источник; skill — воспроизводимый порядок и экзамен; LoRA оправдана только на повторяющемся измеренном классе ошибок при наличии лицензированного набора, чистого holdout и выигрыша над шаблоном/retrieval. Исходные CV, переписка и закрытые данные по умолчанию исключены из training.

**Изменение собственного runtime.** Issue с redacted reproducer → изолированная ветка → sandbox → fail-before/pass-after → независимый QA → PR → отдельный staging → подписанный release и canary → проверка/rollback. Раздельные версии core, agent, capability adapter, model/quant, prompt, skill, policy, UI и DB schema в release manifest. Обновление Windows service/WSL systemd/macOS launchd переключает версию после drain; данные вне каталога приложения, миграции expand/contract. Нельзя откатывать outbox восстановлением старого бинарника. Автор правки не подписывает себе новый grant, не читает release key и не снимает protection. Создание отдельного private runtime repo — решение владельца, в Academy только проектные решения и ссылки.

## Испытания, которые нужны до утверждения свойств

| Свойство | Реальный эксперимент и достаточное свидетельство |
|---|---|
| Живой head, registry и broker | Запуск из обычного ingress, recorded actual model ID/digest и usage, выбор двух разных executor kinds на общих schema, независимый QA отклоняет намеренно неверный результат |
| Минимальные права | Worker пытается прочитать чужую project memory, отправить follow-up, повысить лимит или получить секрет. Нулевые egress/изменения у заблокированных операций; разрешённый путь остаётся работоспособным |
| Суточная работа | ≥24 ч на staging E1, ≥12 циклов мониторинга, restart central, исчезновение worker, outage upstream ≥30 минут. Задания возобновились ≤10 мин после возвращения ресурсов, ноль повторных внешних эффектов и превышений бюджета; каждый UNKNOWN виден и имеет расписанную сверку |
| Потеря state/узла | Восстановить свежую БД + объекты на другом узле из backup, оградить прежние writer/sender и увеличить epoch. Цель RPO ≤15 мин, RTO ≤1 ч. Сравнить с внешним журналом после точки backup, при расхождении удерживать отправку |
| QA, обучение и релиз | Контрольный дефект в B ловится браузером/экспертом; skill проходит перенос на другую задачу. Испорченная worker-версия откатывается, предыдущие receipts и пользовательская запись доступны после rollback |

Приёмочный пакет содержит release/policy hash, интервал, входы и класс данных, expected/actual, raw refs в закрытом хранилище, метрики и нерешённые gaps. Термины статуса: `IMPLEMENTED` — доступно из нормального entrypoint; `TESTED_OFFLINE` — испытано в заявленной изоляции; `VERIFIED_LIVE` — фактический разрешённый результат прочитан независимо; `PARTIAL` — известна работающая часть; `UNKNOWN` — evidence недостаточно; `BLOCKED` — конкретная зависимость остановила работу. Сохранять статус **на свойство и среду**, никогда не сводить шесть признаков в общий процент готовности. [Экзамен A/B и смета](13-delivery-handoff-to-sol.md)
