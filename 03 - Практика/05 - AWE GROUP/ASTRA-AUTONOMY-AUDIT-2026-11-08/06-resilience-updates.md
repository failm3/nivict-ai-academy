# F. Надёжность длинной миссии

**Принимать устойчивость нужно по сохранённым действиям и восстановленному результату.** E0 дал достоверное доказательство для одной задачи и корректного shutdown. Восьмой интервал PostgreSQL длился 39,123 с, все восемь вместе — 302,407 с. Это сильный исходный материал для recovery protocol, короткий период наблюдения для 24×7. В owner-finalization Windows host ключ Ed25519 генерируется при запуске, роли работают в одной композиции. Это подтверждает раздельные роли/proof для E0. В E1 изоляция недоверенного producer требует отдельного OS principal и недоступного ему QA signing key. [Отчёт E0](../MASTER-INTEGRATION-01/MASTER02/FINALIZATION/OWNER-FINALIZATION-REPORT-04.md) · [Host](../MASTER-INTEGRATION-01/owner-finalization-host.mjs)

Late result старого worker отвергается. |

Проверить 429 с Retry-After, timeout, обрезанный stream, отсутствие usage и закрытый privacy route. |

Два независимых задания действительно перекрываются по времени, зависимое не стартует раньше. Сумма резервов + затрат никогда не превышает cap. |
| База/диск переполнены, object потерян, digest расходится | Hash chain, object refs и сохранённый readback. | Нельзя подтвердить deliverable без readback. Fixture: удалить объект, испортить digest, инъецировать ENOSPC в журнал. Ожидается HOLD, подтверждение отсутствует. |

Подмена цитаты, запрещённый ref и инструкция из вакансии → отказ в инструменте, QA фиксирует расхождение. Не расширять секреты или scope после ошибки. |

Сомнительные vacancy IDs держать в quarantine. |

### Что действительно испытать

**До первой внешней отправки** — test double канала со стабильной квитанцией, гонка двух worker, потеря ACK, отзыв мандата перед отправкой, budget cap, forbidden reply и PII в egress/log. Затем на отдельной E1 БД и разрешённом почтовом канале проверить rollback/restart и независимый readback. При неподтверждённом результате считать отклик UNKNOWN. Одного наличия расписания или «здорового процесса» недостаточно.

В этом аудите три межпроцессных сценария выполнены командой ниже. Временная SQLite нужна только воспроизводимой fixture, её файлы удаляются при завершении. Имитируется независимая почта, у которой нет собственной уникальности на vacancy ID. Доказанный результат — отсутствие повторного эффекта при данных окнах падения и повторном старте процессов. Политика прав, реальные сети, PG locking и восстановление сервера этим примером не испытывались.

```powershell
node ASTRA-AUTONOMY-AUDIT-2026-11-08/career-crash-fixture.mjs
```

| Вход | Выход фактического запуска |
|---|---|
| Два отправителя на одну вакансию | `race / PROVIDER_CONFIRMED / effects=1` |
| Аварийный exit 77 после записи в почте и до локального ACK | `after-effect / PROVIDER_CONFIRMED / effects=1` |
| Аварийный exit 77 после локального SENDING и до сети | `before-effect / OUTCOME_UNKNOWN / effects=0` |

**До увеличения объёма** — 24-часовой staging-прогон с новым наполнением, как минимум одним рестартом central, выключением одного worker, 30-минутной потерей upstream и восстановлением backup в отдельный namespace. Начальные цели: потеря подтверждённых действий 0, повторных внешних действий 0, отрицательных бюджетов 0, восстановление полезной работы ≤10 мин после доступности узла; RTO central ≤1 ч, целевой RPO данных ≤15 мин. Сверка эффектов после restore обязательна даже при выполненном RPO. Для работы дольше суток — неделя наблюдения уже в ограниченной кампании; сверять показатели по дням без искусственного ожидания недели до первого результата.

**Наблюдаемость.** Хранить длительность очереди и старейший WAIT по причине, heartbeat каждого узла, время до истечения grants, backlog UNKNOWN, число подтверждённых действий, cost/accepted, долю rejected QA, свежесть источников, свободный диск и дату последнего успешного restore. Сигнал владельцу при приглашении, исчерпании бюджета, необходимости reauth и неразрешимой неопределённости. Повторяющийся 429 автоматически регулирует worker, ежедневный отчёт агрегирует обычные отклонения.

Backup на независимый узел: согласованный PG base backup + WAL и зашифрованные immutable объекты, manifest с DB head/LSN и refs. Ключ восстановления хранится отдельно. Восстановление всегда сначала в новом пустом staging namespace с отключённым egress, затем verify ACL, hashes, счётчиков и внешних квитанций. Снимок ОС без восстановления и сверки не служит подтверждением RTO/RPO. [PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)

## G. Обучение и проверяемая разработка

Поручение «изучи технологию» превращается в наблюдаемый результат: исследовать первичные спецификации → решить новую практическую задачу → приложить код, команды и артефакт → запустить независимый экзамен → устранить ошибки → повторно выполнить отличающуюся задачу по сохранённому навыку.

| Что сохраняется | Входной порог | Как применять и отзывать |
|---|---|---|
| Факт/решение | Источник, дата, область действия, владелец, hash и срок пересмотра | Project memory, при retrieval проверять ACL и expiry. Исправление создаёт следующую версию. |
| Программа/инструмент | Схемы входа/выхода, capability, license, pin, signed manifest и отрицательный test | Исполнитель получает точный tool ID/revision. При отзыве новые claims останавливаются. |
| Навык/шаблон | `skill_id, version, prerequisites, steps, allowed_tools, example_refs, failure_modes, acceptance_suite, reviewer, rollback_to` | Хранить в Git, закрепить в журнале миссии. Второй агент получает только skill card и input, воспроизводит на новой задаче. Провал отводит skill в candidate. |
| Обучающий пример/adapter | Разрешение на обучение, очищенные исходные данные, независимая метка, отсутствие пересечения train/holdout | Только для устойчивой повторяющейся ошибки, которую не решают программа, prompt или retrieval. Версии dataset/base/adapter записывать раздельно. [LoRA и eval](04-models.md) |

**Экзамен frontend/backend для портфолио.** Зафиксировать сценарии ТЗ и ссылки на реальные утверждения владельца. Frontend: сборка и typecheck, тест форм, клавиатура/focus/labels, адаптивность 320/768/1440, screenshot на одинаковых browser/fonts/viewport, независимая оценка визуальной иерархии и контраста, reduced motion. Backend: validation, AuthN/AuthZ, защита повторов, обработка зависимостей/timeout, миграции, интеграционный тест API и доступа, SAST/dependency scan по реально добавленным библиотекам. Проверить вход, сохранение данных и ошибочный сценарий из браузера. Производительность: сценарий на эмуляции мобильного устройства, фиксированные условия, бюджет согласован с ТЗ (предложение LCP ≤2,5 с, CLS ≤0,1). Различать лабораторную и полевую метрику.

Первая сдача содержит commit, build hash, работающий URL для reviewer, тестовый отчёт, screenshots, проверенные переходы/формы и список ограничений. Чтобы считать сайт публично опубликованным, дополнительно получить отдельный разрешённый deploy, проверить доступ с независимого клиента и версию. QA видит ТЗ и артефакт, verifier работает в изолированном процессе без секретов исполнителя. Замена текста кнопки, сломанная форма или горизонтальный overflow должны дать FAIL. Сложную композицию и движение оценивает человек или независимый visual reviewer с рубрикой, image diff остаётся одним измерением. Пропустить unit-тест для статического текста возможно, пропустить работоспособность формы на заявленном сайте нельзя. [Существующий WEB экзамен](../tests/qa02/browser.test.mjs)

### Самоулучшение и выпуск

**Рекомендация** — отдельный приватный GitHub-репозиторий кода AWE. Academy сохраняет архитектурные решения, обучение и ссылки на принятый release. При переносе брать allowlist исходников и очищенные fixtures, сделать сравнение с c53 и 607-pin manifest. Рыночные данные, приватные receipts, raw PGDATA, профили браузера, модели/ключи и домашние каталоги не импортировать в Git. Базовые доказательства E0 остаются по своим адресам.

Предлагаемая структура: `core/` — координатор и общие типы, `adapters/` — модели/источники/effects, `agents/` — роли, `prompts/`, `skills/`, `policy/` — версионированные декларации, `db/migrations/`, `ui/`, `tests/contracts/` и `release/`. Начать с существующих путей в рабочей ветке, физическое перемещение каталогов не является условием первой подачи. Release manifest связывает независимые версии kernel, adapter, agent, prompt, skill, model+quant+adapter SHA, db_schema, policy, UI, min/max protocol и SBOM. Миссия закрепляет этот manifest при старте.

1. Зафиксировать проблему issue с ожидаемым и фактическим поведением, минимальным redacted fixture и влиянием. Агент создаёт изолированную ветку/worktree с ограниченным token.
2. Воспроизвести дефект, исправить его, запустить тесты на соответствующей ОС. Для UI приложить фактические browser/screenshot evidence. Для capability/миграции нужны regression до/после плюс отрицательный сценарий.
3. Независимый QA получает чистый checkout, pinned dependencies, fixture и ожидаемый контракт. Автор не может принять собственную правку в protected main, выдать себе секрет или изменить CI/signing policy. PR содержит scope, migration compatibility, rollback и доказательства. Для private repo проверить поддержку rulesets на тарифе. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
4. Staging на отдельной E1 БД и синтетических/разрешённых данных. Expand→migrate→contract, никаких необратимых drop до окна совместимости и проверенного backup. Для grant/policy changes требуются отдельный владелец ключа и подписанная новая версия. Self-improvement bot может предложить их.
5. Доставка pull-based по подписанному manifest с pinned public root. Windows service под отдельным пользователем использует версионные каталоги и атомарный указатель после остановки worker. WSL/Linux — systemd, release directories/OCI digest, PG volume вне образа. macOS — launchd worker, отдельные model cache и Keychain. На всех трёх узлах проверить подпись/платформу, свободное место, совместимость protocol/schema; выполнить health check до выдачи нового lease.
6. Canary на одном worker и синтетическом job. Drain новых claims для затронутой версии, дождаться завершения или reconcile IN_FLIGHT, обновить, выполнить smoke. При провале вернуться на предыдущий подписанный бинарник/adapter/prompt/model, сохранить outbox и immutable business keys. При несовместимой БД сначала roll-forward или проверенная процедура restore с ограждением sender; автоматический downgrade данных недопустим.
7. Зачесть улучшение по метрике: меньше повторных ошибок или cost/accepted при том же качестве. Сохранить негативный пример в skill suite. Агент без release credentials не может попасть в рабочую среду через собственный PR. Автоматическим может быть принятый низкорисковый worker, расширение полномочий остаётся у владельца.
