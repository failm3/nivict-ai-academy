Маркетинговые кейсы оставить отдельным маршрутом; подтягивать их в product-design CV при конкретном пересечении требований.

## Два продукта-кандидата

**Рекомендация для независимой B — журнал передачи смены «Смена».** Диспетчеру и следующему дежурному нужно видеть открытые инциденты и понимать, кто принял ответственность. Продукт не зависит от данных вакансий или email-адаптера. Это проверяет перенос ядра на данные, права и UI другой предметной области.

| | «Смена» · B2B Operations, сначала | «Эксперимент» · продуктовая аналитика, после первой приёмки |
|---|---|---|
| Пользователь и проблема | Дежурные и руководитель теряют контекст между сменами | Product manager и аналитик теряют связь между гипотезой, событием и решением о запуске |
| Почему в портфолио | Сложная очередь, две роли, доступность, audit trail, frontend/backend | Аналитика, сегментация, целевое действие, объяснение ограничений данных, продуктовый маркетинг |
| Обязательный сценарий | Дежурный создаёт инцидент → передаёт → второй подтверждает → видна история после перезагрузки. Старая версия при конкурентном редактировании даёт конфликт с путём восстановления | Загрузить синтетический CSV → проверить схему и дубликаты → выбрать сегмент → сравнить конверсию → сохранить решение; при нулевом знаменателе показать недостаток данных |
| Интерфейсы | Очередь с фильтром и сохранённым видом, карточка, назначение, журнал, роли reader/operator, mobile summary | Импорт с preview/error rows, метрики и график, таблица знаменателей, карточка решения, экспорт |
| Что работает | Backend с durable storage, server-side авторизация, версионирование записи, API, две независимые browser sessions | Настоящий parser и расчёт, контрольная выборка с известным ответом, сохранение/экспорт с версии данных |
| Граница MVP | Только синтетические инциденты и sandbox, без управления реальными серверами, персоналом или аварийной диспетчеризацией | Синтетика или лицензированный dataset, без стороннего рекламного кабинета, заявлений о causal uplift и настоящей выручке |
| Ввод владельца | Один выбор концепции, целевого пользователя и обязательного пути; по желанию обезличенные примеры процесса | После B — выбор сегмента и события активации, права на данные при использовании реального примера |

Оба продукта сейчас гипотезы. Для «Смены» persona и целесообразность требуют проверки. Если владельцу ближе реальная предметная область с доступными пользователями, заменить сам product brief и оставить критерий общей платформы. Не начинать одновременно два больших продукта.

## Производственный цикл

1. **Инвентаризация и исследование, параллельно Core.** Аналитик и дизайнер строят матрицу skill→evidence по двум CV и одному продукту. Зафиксировать URL и release, права показа, mobile/desktop снимок и проверенные сценарии. Владелец подтверждает только исходные факты и приоритетную концепцию.
2. **Продукт и UX.** Согласовать outcome, цели/нецели, happy path и критическую ошибку. Провести 2–3 коротких сценарных сессии с представителями роли, если доступны. При отсутствии пользователей записать экспертную проверку как экспертную. Сравнить два решения на одной задаче, приложить первую ошибку пользователя и исправление.
3. **Дизайн и контракты.** Карта состояний, prototype, типографика, contrast/focus/touch, component tokens. Параллельно архитектор фиксирует API/error model, data/schema и isolation. Для дешёвых итераций использовать fixtures с тем же контрактом.
4. **Разработка.** Frontend и backend могут идти независимо после согласованного API. Интегратор собирает работающий продукт в изолированном staging, создаёт две тестовые роли и воспроизводимые данные. Портфолио ведёт на работающую функцию, отдельно даёт рассказ о решениях и ограничения.
5. **Экзамен, исправление, публикация.** Предъявить сборку независимому reviewer. Раздельно фиксировать functionality, accessibility, performance и visual/product verdict. Подтверждение владельцем внешнего домена и состава публичных данных привязано к версии. После разрешённой публикации независимый клиент перечитывает release и проходит основной сценарий. В этом задании сайты не публиковались.

### Рубрика приёмки

Функциональные стоп-условия: потеря сохранённой записи; запись от чужой роли; основной сценарий недоступен мышью или клавиатурой; утечка данных; ссылка на неработающий продукт; выдуманные результаты. Один такой дефект блокирует приёмку при любом визуальном балле.

| Критерий | Экзамен и артефакт |
|---|---|
| Задача + ценность, 25 баллов | Reviewer без подсказки выполняет главный маршрут, объясняет для кого и почему; помечает первую ошибку и время. Две тестовые роли реально различаются. |
| Визуальная иерархия, 20 | Слепое A/B двух версий на одном наборе данных и размерах. Оценка читабельности, акцента, композиции, маркировки ошибок, медиа/fallback. Хранить screenshots и обоснование. |
| Взаимодействия и состояния, 20 | Loading/empty/error/offline/conflict/success, сохранение введённого, Tab/Escape, retry с идемпотентностью. Отдельный тест ломает ответ API, затем восстанавливает. |
| Адаптивность и доступность, 15 | 320/390/768/1440, 200% zoom, клавиатура, labels/focus и выборочный screen reader. Axe плюс ручная проверка. Кнопки и таблицы должны быть реально доступны. |
| Техническое качество, 10 | Typecheck, unit критического расчёта, интеграционный API-тест, browser E2E, JS console/network errors. Три одинаковых mobile lab запуска, ориентиры LCP ≤2,5 с, CLS ≤0,1. Фиксировать профиль сети/устройства. |
| Качество самого кейса, 10 | Problem → constraints → решения → работающий продукт → вклад → evidence/ограничения. Reviewer открывает ссылки без внутреннего доступа; сверяет каждое утверждение с источником. |

Предлагаемый порог — ≥80/100 у независимого reviewer и отсутствие стоп-условий. Расхождение экспертов >15 баллов требует разбора конкретного экрана/сценария. Метрика поддерживает решение о качестве, публикация требует действующего права. Работы дизайнера/Sol, сделанные вручную до запуска E1, отмечать `HUMAN_OR_CODEX_ASSISTED`. Для `AWE_EXECUTED` нужны ссылочные записи AWE от цели до accepted artifact, включая реальные модельные решения, исправления и внешнюю проверку.
