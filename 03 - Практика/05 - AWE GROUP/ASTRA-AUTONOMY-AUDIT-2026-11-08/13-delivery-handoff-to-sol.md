**Последовательность по решениям**: A1/C1/B1 → A2 и A3 плюс B2/B4 → B3 и независимая приёмка A → приёмка B и переносимости A4 → B5/C2 и приёмка Full. Один руководитель интеграции контролирует общие schema и branch dependencies. Не создавать отдельные очереди для дизайнеров и откликов. Дробить PR по вертикальным наблюдаемым результатам: например, «один worker восстановил одно задание» раньше «поддержаны все типы агентов».

**Оценка.** До первого A с готовой почтой и фактами ориентир порядка **6–11 чел.-дней**, до принятой пары A+B **9–16 чел.-дней** (сумма строк A1–A4, B1–B4, C1 составляет 8,75–15,75). B5/C2 добавляют 6–14+ и календарные сутки. Это диапазоны, а не дата обещанного запуска. Ожидание OAuth/доступа, новых материалов, участников UX-теста и решения о публикации учитывается отдельно. Когда работают двое, узкие места — выдача мандата и интеграция A2/A3; параллельные задачи сокращают календарь, а не оплаченные часы.

## Наблюдаемый первый запуск

В UI либо CLI owner видит goal, scope, expiry, max_submissions=1, допустимые attachments, model spend cap и кнопку stop. Однажды выданное разрешение действует для штатных действий из мандата. Подготовленная, но не подписанная политика не является таким разрешением.

| Момент демонстрации | Что показывает система | Независимая проверка |
|---|---|---|
| Intake | Исходная цель, spec_hash, требования и пробелы. Видно, какое решение сделала модель, что проверил код | Сравнить spec с целью, проверить факт каждого допустимого утверждения. Отдельная проверка scope |
| Планирование | Готовый DAG, выбранные executor/model IDs, причины исключения альтернатив, time/cost reserve | Два источника читаются независимо. Экран состояния и логи не содержат персональных материалов |
| Исполнение A | Найдена актуальная вакансия, адрес взят из первоисточника, CV и письмо привязаны к хешам. Собственный QA дал право продолжить в пределах grant | В канале найдена та же отправка по provider ID, получателю и корреляции. Владелец не подтверждал каждую штатную операцию |
| Возобновление | Сверка SENDING/UNKNOWN, cursor после перезапуска и план следующего чтения | Fault инъецируется в отдельном staging с test mailbox, после перезапуска один эффект. Получатель настоящего первого отклика не участвует в fault injection |
| B на том же ядре | Другой primary goal, общие версии, зарегистрированные UX/code/browser роли, build ref, staging target и QA | Второй клиент воспроизводит операцию продукта, после restart запись доступна, permissions соблюдены. Сохранить снимки и verdict по рубрике |
| Закрытие | Линия A уходит в мониторинг, B выпускает версию, фиксируются стоимость принятого результата и реальные ограничения | На одном выпуске сверены шесть общих механизмов, ни один субъективный отчёт worker не считается внешней квитанцией |

Обязательная детализация A: выделить происхождение рынка и лимиты, регулярно перечитывать доступные разрешённые вакансии, dedupe до ранжирования, gap analysis → две версии резюме и корректировки портфолио, downstream — ограниченная подача и readback. Email только на явно опубликованный канал вакансии. HH/OAuth, ATS, карьерный сайт или browser разрешать после проверки текущей документированной операции и прав конкретного приложения. У HH публичное описание и ранее проверенный OpenAPI расходились. Не подменять отсутствие прав скрытым browser submit; CAPTCHA/MFA требует остановки в этом канале. Источник Radar требует подтверждённого адреса. Сигналы приглашений передавать сразу, сводка по источникам/закрытиям/расходам регулярно, изменения стратегии связывать с объективными событиями и прежними лимитами. ## Готовый критерий управленческой сдачи

- Первый наблюдаемый эффект A, проверка A/B и Full имеют отдельные записи со scope, статусом, датой, release SHA и ссылкой на закрытые evidence. Положительный readback отправленного сообщения доказывает отправку через сервис. Прочтение, приглашение, интервью и оффер фиксируются только по соответствующему событию.
- Для E1 Full показать очередь обнаруженных подходящих позиций с outcome каждой, минимум две различные разрешённые первичные подачи (предлагаемый нижний порог для проверки серии), актуальные CV и portfolio URLs, обработку реального/контрольного входящего с маркировкой, отчёт за сутки и восстановление. Исчерпанный мандат штатно останавливает новые sends. Квантификатор относится к покрытому окну источников.
- Отчёт для code/design — commit + immutable build hash, ссылка и работающий сценарий с качеством по rubric. Для исследовательской задачи — исходные ссылки/даты, охват, ограничения, проверка ложных утверждений. Для обучения — перенос навыка с независимым экзаменом. Общая grade на всю платформу из этих результатов не выводится.

## Что требуется от владельца и как продолжать

1. Выбрать концепцию B либо дать другой самостоятельный product brief, определить аудиторию и границу внешней публикации. Инженерные детали и кнопки выбирает команда.
2. Подтвердить факты и материалы двух CV, права на публичные кейсы, допустимые поля облака, исключения работодателей/рынков.
3. Перед live указать допустимый sender, каналы, срок, дневной/общий лимит и конкретный capped бюджет. Для staging выбрать разрешённый узел/хранилище, для публикации — домен и состав данных. Пароли и токены в Markdown или чат не помещать.

**Рабочий обмен.** Перед этапом Astra/Sol/ChatGPT читают [AWE-CURRENT-STATE](../AWE-CURRENT-STATE.md) из удалённого main и названную редакцию задания. В конце добавляют компактный outcome с evidence refs, commit и blockers, меняют current-state только после сравнения с актуальным HEAD. Astra проектирует и проверяет, Sol реализует и испытывает, ChatGPT обсуждает с владельцем и фиксирует решения. Канал между чатами — опубликованная версия GitHub. Владельцу достаточно одной постоянной ссылки на current-state и ссылок на commit/PR. Подписка Watch/Custom на PR/releases удобна для таких событий; для каждого push при необходимости использовать commit Atom feed в поддерживаемом приватном клиенте, не помещая токен в документы. Для каждого milestone достаточно PR или release notification. Webhook/Actions и бот-рассылки не нужны для этого перехода.
