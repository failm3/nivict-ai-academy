# AWE GROUP — Архитектура: решения и открытые вопросы

## Важные разграничения

- **Организационная иерархия** (AWE GROUP → линии) ≠ **обработка запроса** (пользователь → валидатор → головной агент).
- **Создать проектную линию** ≠ **создать новый LLM-агент**.
- **Память проекта** ≠ модель, её веса или контекстное окно.
- **Проверить качество ТЗ** ≠ гарантировать корректность будущего результата.
- **Схема Canvas и спецификация** ≠ действующая реализация.

## Открытые вопросы — НЕ решать без следующей команды пользователя

- Дальнейшие уточнения корпоративных сервисов и полномочий проектных линий (корень и уровень линий уже отражены на схеме).
- Является ли входной Мастер промптов также сервисом генерации системных инструкций внутренних агентов или нужны отдельные логические роли.
- Условия, при которых валидатор отправляет задачу на уточнение, а не пропускает дальше.
- Точные права/политики управления проектами, доступов, рисков и расходов.
- Технологии исполнения, схемы данных, бюджет и MVP; детали откладываются до соответствующего этапа.

## Блок 02 — новые решения о хранении (2026-11-05)

- **Базы данных не создаются заранее в фиксированном количестве.** Каждая проектная линия получает собственную логическую изоляцию; число реальных БД, индексов, файловых и объектных хранилищ может динамически расти по требованиям.
- **Для каждого хранилища — свой контролируемый Storage Worker / адаптер**: доступ, чтение/запись, миграции, проверка целостности, резервные копии, восстановление, статус и аудит действий. Прежде всего детерминированные программы, скрипты и задания очередей; отдельный постоянно активный LLM-агент не нужен.
- **LLM — только если нужно смысловое решение**, например неоднозначная классификация файлов/папок или извлечение метаданных. Любой LLM-вывод проходит независимую проверку по правилам, исходникам, правам и ограничениям; выдуманные факты не повышаются до подтверждённых.
- Project Provisioner подготавливает инфраструктуру новой линии и подключает адаптеры, а при возобновлении восстанавливает существующее состояние, не пересоздавая его.
- Это **концептуальное архитектурное решение**, не реализованный механизм. До изменения Canvas требуется проверить согласованность расположения и сохранить локальные пользовательские правки.

## Блок 02 — итог согласованной схемы (2026-11-05)

Фиксируем минимальный промежуточный процесс: программный менеджер идентифицирует линию в корпоративном реестре по project_id → существующую открывает с восстановлением контекста/состояния/прав, новую создаёт из шаблона через Project Provisioner → передаёт агенту проекта. У каждой линии логически изолированные данные и конфигурация, число хранилищ определяется нуждами. Storage Workers — программные адаптеры, LLM только для смысловой классификации с проверкой результата. **Концепция блока 02 закрыта**, но внедрение/тесты инструментов ещё нет. Правка внесена в тот же Canvas; переход к блоку 03 — только по указанию пользователя.

## Блок 03 — правила планировщика и параллельной работы (2026-11-05)

- **Решение пользователя:** планировщик не показывает планы на согласование только из-за размера проекта. Если информация достаточна, план выполняется самостоятельно. В случае существенной неопределённости запрашивается конкретное уточнение.
- **Безопасное уточнение:** отдельные действия с высоким риском (публичная публикация, необратимые изменения и неподтверждённые профессиональные сведения) требуют проверки прав/источников и при необходимости подтверждения независимо от субъективной уверенности LLM.
- **Структура:** цель/инициатива → проекты/потоки → задачи → подзадачи/операции; программа управления зависимостями (DAG) и статусами отдельно от LLM-планировщика.
- **Параллельность:** независимые проекты/этапы исполняются параллельно с изоляцией рабочих пространств, бюджетами и блокировками общих ресурсов. Исследование рынка вакансий → обновление резюме и релевантных кейсов; работа над «Сайт Жив» может идти независимо. Окончательные публикации после достоверной проверки.
- **Честность портфолио:** реальные коммерческие кейсы, учебные/концептуальные проекты и новые демо должны быть явно различимы; нельзя создавать 20–40 выдуманных прошлых проектов и приписывать им произвольные годы/метрики/клиентов.
- **Статус доказательств по каталогу:** все 4504 записи прошли автоматический первичный скрининг, но не индивидуальную техническую экспертизу. 473 записи получили тематические сигналы классов A/B/C; 3302 требуют ручной проверки. Для блока 03 нужны профилированные инструменты поиска вакансий, web-extraction, coding, browser QA, GitHub, orchestration; выбирать экспериментально и учитывать ещё не проверенный NIVICT Workspace/Hermes.
- **Canvas блока 03 переписан:** принят Project Agent + Task Planner/DAG + детерминированный диспетчер/Task Supervisor + реестр исполнителей и evidence. Результат передаётся в независимый блок 04.

## Решение по контролю качества: локальная проверка + «честный экзаменатор» (2026-11-05)

- **Утверждено пользователем и внесено в Canvas:** каждый блок 01/02/03/05 выпускает доказательства локальной проверки. Блок 04 выполняет независимый экзамен по первичному ТЗ и артефакту, **без доступа к локальной оценке до собственного испытания**, после чего отдельный Verification Auditor сравнивает результаты и проверяет состоятельность тестов, включая негативные/мутационные/атакующие сценарии по риску.
- **Quality Gate — код**, а не решение LLM на веру: PASS/FAIL/UNCLEAR/BLOCKED; отсутствие evidence не PASS; критические проверки обязательны. Проверяющий не меняет исходные требования, продуктивные файлы или права исполнителя.
- **Блок 05:** дополнительный независимый post-save audit повторно читает сохранённые файлы/БД и проверяет локальный отчёт, до итогового сообщения о завершении.
- **Инструментальный набор на карте:** QA profiles — Playwright, pytest/Hypothesis, Vitest/Jest, Trivy, Semgrep, OWASP ZAP, Inspect AI, DeepEval, Promptfoo, Stryker, Langfuse. Это **кандидаты**, статус интеграции — НЕ ПРОВЕРЕН/НЕ ВНЕДРЁН.
- Подробная спецификация: [[04 - Блок 04 — AWE Quality Assurance System]]. В Canvas **107 узлов / 95 связей**, JSON и ссылки проверены, визуальный рендер в Obsidian пользователем ещё не подтверждён.

## Сквозная память + Конституция (2026-11-05)

- **Нужна безусловно:** корпоративный registry и журнал состояний, project-scoped память, производный семантический индекс, отдельное хранилище артефактов/evidence, общие знания только после проверки. Source-of-truth — утверждённое ТЗ + версионированное авторитетное состояние; embeddings/summary LLM не определяют правду.
- **Обязательные механизмы:** проверка перед записью (provenance, ACL, quarantine), read ACL до semantic search, versioning/TTL, проверенное продвижение shared knowledge, согласованные backups и тестовые restores, checkpoints/idempotency, работа с удалением и stale данным. PostgreSQL, Supermemory и backup tools — пока кандидаты, нужны пилоты.
- **Конституция AWE GROUP предложена пользователем:** подготовлен **проект v0.1** из 12 норм (в Canvas 10 кратких принципов): цели/полномочия, least privilege, внешние данные ≠ команды, доказательность фактов, честная память, проектная изоляция, независимый QA, автономия по риску, ограничение ресурсов, recovery, фактические статусы, управление версиями политик. Ключевые запреты реализуются программным Policy Enforcement Point и авторизацией, не «силой промпта».
- **Статус:** Canvas обновлена, полные документы [[Память — сквозная архитектура и правила]] и [[AWE-CONSTITUTION-v01]] созданы. **Пользователь ещё не утвердил финальную конституцию** и не назначил пороги рисков, сроки хранения, роли команды и бюджеты. Реальные тесты и интеграции ещё не выполнены.

## Блок 05 и сквозной аудит — решение 2026-11-05

- **Блок 05 доработан в Canvas:** persist с контролем версии/хеша/outbox → LocalQA05 и independent read-back → checkpoint и state → DAG (continue/wait/final) → Head Agent отчёт. Нельзя приравнивать WAITING/BLOCKED к COMPLETE, нельзя повторять внешние побочные действия без reconciliation. См. [[05 - Результат, состояние и продолжение]].
- **Архитектурный аудит завершён**, см. [[AWE-GROUP-AUDIT-2026-11-05]]. Граф проходит структурные и маршрутные проверки; поправлены QA fail branches и тексты, добавлена секция аудита 07. Сейчас Canvas: **134 узла, 121 связь, 10 групп**.
- **Не закрыты перед боевым использованием:** реальный PEP/authorization, физическая cross-project изоляция, independent QA evidence, crash/recovery/idempotency. **До полноценной разработки:** state/config contracts, конечная интеграционная QA, уведомления и approvals, пилот tool/runtime.
- **Статус:** архитектурный аудит/документация, не факт успешной установки, интеграции, запуска, рендеринга Obsidian или приёмки владельцем. Пользователь пока не ратифицировал Constitution v0.1 и не назначил numerical budget/retention permissions.

## Решение по визуальному стилю и Codex (2026-11-05)

- **Утверждён концепт Dashboard v1**, визуальный референс изображён в чате: двухступенчатая навигация, светлый soft-glass интерфейс, выбор Project Line, KPI, ход работы Goal → Project Agent → Task Supervisor → Execution → QA → Result, таблица задач, System Insights, артефакты. На макете статистика **демонстрационная**, не реальные результаты агента. Для Codex оригинальное изображение нужно отдельно приложить/сохранить как доступный ресурс.
- **Согласованная логика подготовки:** Audit A — текущий NIVICT Workspace/Hermes; Audit B — наша Obsidian/GitHub архитектура AWE GROUP; Audit C — инструментальный каталог 4 504 кандидатов и реальные tool gaps; затем единый synthesis с reuse/adapt/replace, целевой runtime, контрактами/рисками и планом MVP; только после одобрения — реализация.
- **Безопасный старт:** первые три аудита read-only, без установок/deploy, без изменений продуктивного Workspace, без реальных секретов в отчётах; tests/sandbox/бюджет/сетевые права требуют отдельного допуска. Полные задания и открытые параметры: [[08 - Codex — план обследования и допуска к разработке]].
- **Ещё не определено:** точный git/path актуального Workspace, где работает Codex (local/cloud), критерии MVP и бюджет пилота, матрица полномочий команды, контракты состояния и версионирования, доступность картинки в Codex. До получения этих вводных не утверждать реализацию.
