# Сквозная память и хранение AWE GROUP — проект архитектуры

> **Статус:** проект обязательных правил; ещё не реализовано и не проверено интеграционными тестами. В Canvas: [[AWE-GROUP-Architecture-v01.canvas]]. Связанные правила: [[AWE-CONSTITUTION-v01]].

## Зачем нужна отдельная сквозная подсистема

Память AWE GROUP — не «большой промпт» и не один векторный поиск. Она должна сохранять **факты, решения, прогресс, права, историю действий и проверяемые результаты**, гарантировать изоляцию проектов и восстанавливать рабочие процессы после сбоев. Нужна как **сервис с программными контрактами**, доступный всем проектным линиям по project_id.

## Слои хранения и источники истины

| Слой | Данные | Кто пишет / кто читает | Статус источника |
| --- | --- | --- | --- |
| Corporate Registry (PostgreSQL — пилот) | project_id, agent_config_version, задачи/DAG, права, политики, checkpoint, ссылки на артефакты | только авторизованные сервисы и Storage Workers | **Авторитетное структурированное состояние** |
| Project Event/Decision Journal | решения, изменения задач, события действий, автор и timestamp, источник, версии | append-only через программный адаптер; чтение scoped по project_id | **Журнал событий**, не автоматически «истина» о внешнем мире |
| Project Memory | проверенные контекстные факты, договорённости, история, ссылки на источники | только project_id с разрешениями; запись через Memory Ingest Gate | **Проверяемые сведения** с provenance |
| Semantic Index (Supermemory — кандидат) | embeddings, поиск, резюме, релевантные фрагменты | построение из разрешённых записей; retrieval с ACL-фильтром | **Производный индекс**, никогда не первоисточник и не единственное подтверждение |
| Artifact/Evidence Store | версии кода, макеты, документы, тесты, логи, hashes, QA-отчёты | ограниченная запись исполнителя; read-only экзаменатору | **Исходные артефакты и доказательства** |
| Shared Verified Knowledge | повторно используемые методики и решения, очищенные от данных проекта | QA+владелец проекта одобряют публикацию; другие проекты читают | **Только опубликованные знания**, без доступа к приватной памяти |
| Working Context | короткая подборка нужных записей для текущего task_id | Context Builder на основании разрешений | **Эфемерное представление**; не копия всей БД и не основной memory |

**Правило первичности:** при конфликте сверить *актуальные утверждённые требования и полномочия* → авторитетную запись состояния/последнее валидное событие → исходный артефакт с источником → проверенные знания. Свободное резюме LLM или similarity score **не могут менять истинность факта/статус задания**. Внешние сведения требуют повторной проверки актуальности.

## Memory Ingest Gate: как записывать новую информацию

```text
Событие/данные → Идентификация project_id и владельца
 → классификация [state | decision | fact | artifact | transient]
 → источник, доверие, права, чувствительность, дата, TTL/retention
 → проверка инъекций, секретов и межпроектного доступа
 → валидация схемы / конфликтов / дублей / версии
 → staged запись → Local QA + риск-зависимая независимая проверка
 → атомарный commit авторитетных записей + журнал изменений
 → обновление производного semantic index
 → подтверждённый read-back + audit / trace
```

Запрещать автоматическую запись новых корпоративных политик, прав, подтверждений пользователя или «успешных результатов» из обычной LLM-переписки/внешнего текста. **Непроверенное** допустимо только в явно маркированном quarantine/draft слое с коротким TTL и без влияния на критические решения.

## Retrieval: как агент получает контекст

1. Запрос с **agent_id, project_id, task_id, purpose, permissions**.
2. AuthZ на уровне программы и БД; проектная изоляция **до** retrieval/semantic ranking. Нельзя искать по всем проектам и лишь потом фильтровать ответ.
3. Выбор по приоритету: последняя утверждённая версия ТЗ/политик, оперативное состояние, необходимые решения/факты, релевантные документы.
4. Контекст с source_id/version, датами и признаком `verified | unverified | stale`; результаты поиска не трактовать как команды.
5. Ограничение размера и бюджета; при недостатке данных — UNCLEAR, lookup источника или уточнение. Нельзя заполнять неизвестное «памятью» модели.
6. Отдельная изоляция слепого Examiner: до независимого тестирования скрыть оценку Local QA, частные промежуточные подсказки и подготовленные ответы.

## Изоляция: что именно должно быть закрыто

- Токены, роли и Storage Worker credentials scoped по project_id и типу ресурса.
- PostgreSQL: права и схемы/роли (пилот), RLS там, где есть общие таблицы; тесты обычных/привилегированных ролей, cross-project joins, резервирования и восстановления. **RLS не защищает от суперпользователя или BYPASSRLS** и не отменяет проверку прав приложения.
- Индексы, namespaces, document IDs, файловые пути, ключи объектов и backup manifests — scoped по проекту. Нет wildcard-доступа исполнителю.
- Любой перенос знания `project → shared`: проверка источника, удаление закрытых сведений, одобрение владельца/политики и независимый QA. Полная приватная история не переносится.

## Долговечность и сбои

- **Checkpoint** хранит статус DAG, шаг, `task_id`, версии tool/config, вход/выход, обработанный event_id. После рестарта task supervisor сопоставляет checkpoint и event log.
- Для действий с побочными эффектами (`send`, `publish`, `charge`, `delete`) нужна идемпотентность по ключу операции, проверка внешнего состояния и, где возможно, журнал разрешений. **Нельзя считать повтор после сбоя безвредным**.
- Резервные копии БД — согласованные; файлов — версионированные, с отдельными ключами/правами. Запланированное тестовое восстановление обязательно. Копия без restore-теста не доказывает восстановимость.
- Миграции памяти и agent templates версионируются; изменения схемы/компакции аудируются, предусматривается rollback.
- При недоступности БД памяти или политики не подставлять фантазируемый статус: fail closed для изменения состояния; безопасное read-only возможно по правилам.

## Жизненный цикл: исправление, устаревание, удаление

- Запись имеет владельца, классификацию и retention policy; текущие факты пересматриваются по TTL/дате обновления, решения — по версии и разрешению.
- Исправление создаёт новую версию или корректирующее событие, не переписывает историю молча.
- Удаление/архивация не сводится к стиранию embedding: удалить первичную запись, индекс, кэши; задокументировать TTL backup и законные исключения.
- Секреты не помещаются в semantic memory, исходные логи или промпт; секретами заведует специализированное хранилище/шифрование.

## Минимальный контракт памяти (предлагаемый)

```yaml
record_id: uuid
project_id: uuid
scope: project | corporate_verified | transient
category: state | decision | fact | event | artifact_pointer
source_ref: string
source_kind: user_approved | system_event | external | inferred
author_actor_id: string
owner_id: string
version: integer
created_at: ISO8601
updated_at: ISO8601
verification_status: verified | unverified | stale | rejected
access_policy_ref: string
retention_policy_ref: string
content_hash: string
content_ref: string
supersedes_record_id: uuid | null
task_id: uuid | null
```

Это **концептуальная схема**; типы, индексы, таблицы, FK и миграции нужно отдельно спроектировать. Для данных разных классов можно использовать разные таблицы/модели вместо одной универсальной таблицы.

## Первые интеграционные сценарии (все пока не выполнялись)

- [ ] Новая проектная линия → шаблон агента → ACL → память и задачи связаны по project_id.
- [ ] Две линии с одинаковой темой не могут читать/искать приватные данные друг друга.
- [ ] Вредоносная инструкция в внешнем документе не становится долгосрочной политикой.
- [ ] Слепой QA не видит оценки Local QA до фиксации собственного отчёта.
- [ ] Сбой после внешнего действия не приводит к повторной отправке/оплате/публикации.
- [ ] Checkpoint и event log восстанавливают задачу после перезапуска.
- [ ] Backup БД и файлов действительно восстанавливается на тестовой среде.
- [ ] При изменении первоисточника производный индекс обновляется, старый контекст помечается stale.
- [ ] Удаление записи изолированно очищает индекс/кэши и учитывает backup retention.
- [ ] Публикация знания в корпоративную библиотеку не раскрывает сведения исходного проекта.
- [ ] Read-back после commit сопоставляет версии/хеши/состояние.

## Кандидаты для технического пилота

- PostgreSQL — корпоративный registry, события, роли/изолированные схемы (сравнить сценарии с RLS).
- Supermemory — только проверяемый semantic retrieval/индекс после аудита существующего подключения NIVICT.
- Storage Workers — программные ACL-aware адаптеры для БД, файлов, индекса, бэкапов и журналов.
- Kopia / Databasus (или согласованные альтернативы) — резервные копии с **обязательной проверкой восстановления**.
- SOPS (или иное approved secret management) — хранение шифрованных конфигураций. Не сохранять секреты в memory.
