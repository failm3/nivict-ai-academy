# AWE E1: от score-helper к автономному multi-file coding и агентам

**Целевой аудит и план, 08.11.2026. Реализация не начиналась.** Источник — [runtime PR #7](https://github.com/failm3/awe-group-runtime/pull/7), commit `9c3eaa182a862dadd5a326836408063b45f7219c`, открытый draft без merge. Оригинальные runtime/worktree, E0, PostgreSQL, ключи и существующие документы не изменялись. Новых модельных вызовов, подключений к БД и тестовых прогонов в этом аудите нет.

**Вывод:** кратчайший путь проходит через существующий `E1/executors/coding`. Multi-file формат уже есть; отсутствуют его доказанные живые bindings, общий durable-контроллер coding-цикла и безопасная динамическая выдача ролей. Сначала связать реальную двухфайловую задачу, затем доказать автоматическое исправление и восстановление, после этого добавлять динамические экземпляры агентов. Новый orchestration framework, новый ledger или облачная модель не являются предпосылками.

## 1. Основание и точность утверждений

- **ФАКТ** — прочитан owning code либо проверена опубликованная квитанция конкретного запуска.
- **ВЫВОД** — следствие из этих путей, без нового runtime-эксперимента.
- **ПРЕДЛОЖЕНИЕ** — будущая реализация, не существующая возможность.
- **НЕ ДОКАЗАНО** — в проверенном дереве нет достаточного положительного исполнения.

При аудите совпали **112/112** файлов source/evidence manifest и **53/53** независимых source pins; tracked diff runtime равен нулю. [EVIDENCE.json](EVIDENCE.json) отделяет свежую проверку хешей от исторического исполнения. Текущая доступность PostgreSQL/модели и остатки бюджетов повторно не проверялись. Исторические 442 offline / 38 native / 11 финансовых native проверок не являются свежим запуском аудита и не доказывают generic coding.

Astra — независимый рецензент этого аудита относительно его основного автора Sol; отдельный контекст, собственное чтение кода, без изменений SUT. Её прежняя роль — supervisor SANDBOX-RECRUIT. [Рецензия](ASTRA-REVIEW.md) · [машиночитаемые задания](ROADMAP.json).

## 3. Блокирующие разрывы перед generic coding

Это статические наблюдения, не сообщения о совершённой атаке.

1. **Содержание задачи не закреплено grant.** `CodingTaskGrant` содержит repo/issue number/base, но не issue digest; reader self-hash проверяется без сравнения с утверждённым brief. [Grant fields](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/contracts.mjs#L27), [reader check](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/executor.mjs#L35). Нужен trusted immutable brief digest до модели. Изменённый текст issue не может расширить задачу автоматически.
2. **Test receipt не связан с точным tested tree.** Проверяются command/isolation/exit/output digest, но нет явного head/tree/run nonce в receipt. [Проверка](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/executor.mjs#L53). Для live-пути привязать receipt к source tree, command/profile/toolchain, входам, fence и invocation ID; stale PASS другого candidate отвергать.
3. **Нужен явный A2 bridge.** `validatePatchProposal` обогащает patch полями `after_digest/patch_bytes/patch_digest`, а raw output schema запрещает эти поля. [Разница](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/contracts.mjs#L62). В native `result.output` сохранять проверенный raw schema-shaped proposal; enriched patch/CodingArtifact/head/tests — в bound evidence/ref. `result_hash` фиксирует весь envelope. Перед native QA нужен WAIT_QA; generic engine сам этот переход не делает.
4. **Failure не закрывает lifecycle.** Engine возвращает `REPAIR` до `qaPort` при failing producer tests и сворачивает неподтверждённый model envelope в generic BLOCK. [Пути](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/executor.mjs#L59). Bridge обязан сохранять failed-test evidence и terminal/repair state, не оставлять RUNNING без решения. Возможный send — HOLD с исходным native attempt ref; внешний BLOCK не разрешает второй wire.
5. **Текущая защита путей недостаточна как default для общего host.** Exact positive allowlist полезен, но default protected roots не охватывает `.private`, все `E1/qa*`, новые coding/runner/registry модули. [Список](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/contracts.mjs#L6). Нужен host-owned immutable protected set, отдельно read/write scope и проверки symlink/hardlink/ancestry/смены base при записи. Модель не редактирует QA, grants, sandbox или собственную политику.
6. **Multi-file apply требует recoverable операции.** Сейчас это интерфейс порта, а не доказанная реализация. Stage all files → validate → commit → readback должен либо дать один целый candidate, либо обнаруживаемое незавершённое состояние; нужен crash после первой записи и после commit до ACK. Не считать существование branch доказательством успешного полного patch.
7. **Есть receipt для одной функции, нет program profile.** Снимать AST-запреты со score runner недостаточно. Новый профиль должен запускать разрешённый module tree/CLI со stdlib, фиксированными entrypoints/test IDs, readonly input/public fixtures/toolchain, ограниченной writable scratch, network DENY и уничтожением всего execution tree. `RLIMIT_AS` ограничивает адресное пространство процесса; это не доказательство общей memory-квоты для будущих потомков. [Python resource](https://docs.python.org/3/library/resource.html#resource.RLIMIT_AS). Сам bubblewrap требует явно заданной политики изоляции. [Официальное описание](https://github.com/containers/bubblewrap/blob/main/README.md#sandbox-security). Aggregate bounds/подпроцессы проверять для нового профиля отдельно; в этом аудите они не тестировались.
8. **A2 не реализует adaptive repair автоматически.** QA FAIL переводит task в FAILED, а dependencies готовы только после ACCEPTED. [SQL QA](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/coordinator/migrations/0001-durable-runtime.sql#L360). Replan требует тот же spec/grant, следующую revision и drain; счётчики проекта сохраняются. [Replan](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/coordinator/migrations/0001-durable-runtime.sql#L157). Нужна управляющая policy над этими механизмами, а не второй scheduler/ledger.

Ещё два ограничения bridge: `CODING_PERMISSIONS` — отдельный словарь repo/worktree/test прав, его нельзя напрямую вставить в строгий A1 MissionGrant. Нужна связанная derived host authority, а не снятие A1 validation. A1 структурно допускает `program/agent`, но native model reserve разрешён только `executor_kind=llm`; роль агента должна вызывать разрешённые LLM-задачи через A3/D09, а не отправлять неучтённые запросы из нового agent-kind worker. [A1 виды](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/contracts/index.mjs#L117) · [D09 reserve](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/coordinator/migrations/0001-durable-runtime.sql#L255).

## 5. Полный цикл поверх A1/A2/A3

1. **Задача.** Host принимает immutable brief и root grant: repo/original base, read/write paths, criteria/oracle, profiles, сроки, total calls/iterations. Authenticated GitHub snapshot допустим как честный `SNAPSHOT_INPUT`; это не доказательство самостоятельного live GitHub ingest. Наличие GitHub connector у Sol не даёт AWE готовый runtime reader. [Issue #2](https://github.com/failm3/awe-group-runtime/issues/2) — старая однофайловая спецификация на base `09f1…`, не grant нового multi-file запуска.
2. **План.** A3 Head создаёт draft только из approved registry. Host заполняет authority/schema/effect поля, A1 проверяет и публикует, A2 принимает. Версия для coding расширяет нынешний parse/review enum; она не даёт модели shell, SQL или credential issuance.
3. **Исполнители.** Для G1/G2 достаточно установленного coder + независимого QA. Для G3 Head может запросить профиль из заранее разрешённого каталога; host проверяет parent scope и выдаёт child credential. Новый profile не равняется новой программе/привилегии.
4. **Контекст и code generation.** Scoped reader предоставляет разрешённые bytes/refs и before digests; скрытый oracle и host-конфигурация исключены. A3 reserve→SENDING→одна модельная попытка→CONFIRMED или UNKNOWN. Сохранить исходную `LIVE_LOCAL_MODEL` provenance; host composition не превращает mock в live переименованием `.mode`.
5. **Apply/run/tests.** Проверить proposal, подготовить все файлы в isolated candidate, атомарно зафиксировать/readback tree; выполнить только предписанные test capabilities в program profile. Журнал связывает action intent, task/fence, candidate parent/tree и receipt. Никаких произвольных модельных command strings или package-install scripts.
6. **Исправление.** Из known CONFIRMED generation и достоверного failed-test report controller формирует следующую разрешённую revision/задачу. Failures передаются модели как данные. UNKNOWN/возможный send переводит run в HOLD, сохраняет liability и запрещает повтор. Отзыв, лимит, scope mismatch — STOP/BLOCKED, не новый обходной проект.
7. **Независимый QA.** Сверить immutable final tree, public/hidden tests, raw model patch, происхождение, scope и history. Проверенный test report может быть ACCEPTED как **достоверный отчёт о неуспехе**; это не PASS компонента.
8. **Результат.** Отдельный финальный product gate требует положительного independent product verdict. Только он разрешает RESULT_READY и завершение миссии. A2 сейчас ставит COMPLETE, когда все current tasks ACCEPTED; DAG из одних принятых отчётов не должен ошибочно завершить продукт. Выход G1/G2 — exact Git head/package/test/QA bundle и реальный local draft intent. Remote PR dispatch — отдельный scoped capability/outbox/readback; merge/production не входят.

### Repair без сброса лимитов

Предлагается outer `CodingRunGrant`: максимум **3 code attempts всего**, включая SENDING/UNKNOWN/неуспешные, и отдельный общий лимит, например 4 model wires: один начальный Head + до трёх code attempts. Следующие repair steps выбирает детерминированный bounded driver; дополнительный Head тоже расходует этот общий лимит либо требует заранее иного профиля, но не бесплатного сброса. Это предложение будущего профиля, не выданный этим аудитом ресурс. Каждый внутренний v1 coding grant по-прежнему разрешает одну попытку. Root policy выводит per-round exact base/paths из подтверждённой цепочки кандидатов; base второго кандидата — проверенный head первого, с сохранением original base и previous digest. Модель не repin-ит его сама.

Использовать разные `code_r01`, `code_r02`, `code_r03`: SQL считает attempts по mission+task, а не по plan revision. [Guard](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/coordinator/migrations/0001-durable-runtime.sql#L255). Новый task ID не выдаёт новый root budget. A2 revisions разрешены только после drain; original failed candidate/report остаётся в history. Эти правила нельзя заменить автоматическим повтором `executor.run()` после REPAIR/BLOCK.

### Что сохранять для автономного восстановления

Переиспользовать уже сохранённые A2 spec/grant/plan/tasks/attempts/events. Добавить только недостающее: run phase и устойчивый step/idempotency key; goal/oracle/root-policy digest; intended repo/base/tree/worktree/head и disposition Git operation; failure/QA/report refs; next-step decision/Head draft ref; remaining outer counters/stop reason. Всё — в том же transaction domain, с lease/fence и expected predecessor. Credentials/ключи не сохранять в этих документах.

Controller после restart заново подтверждает host identity/current grant, перевыдаёт короткую scoped credential и сверяет Git/native receipts. Crash после intent, первой записи, commit, test и QA не должен создавать второй model wire или принимать stale PASS. Автоматический restart host процесса/службы проверяется отдельно от ручного запуска `resume`; постоянная фоновая служба для первого G1 не обязательна.

## 6. Проверяемые рубежи

**G1 — первый живой multi-file.** Предложенный brief: два небольших Python stdlib файла `normalizer.py` + `cli.py` в новом isolated coding-pilot scope. Library обрабатывает synthetic JSONL events, CLI действительно импортирует library. Exact пути и oracle фиксируются до вызова. Старый base не проходит тесты; замена только любого одного файла тоже не проходит; оба сгенерированных файла и hidden fixture проходят. Native D09/QA, tree blobs, main unchanged, no network/dependencies, one attempt и no-send/UNKNOWN negatives обязательны. Существующие 8 KiB или 2048 output tokens не гарантируют, что ответ поместится или будет качественным; truncation — наблюдаемый REPAIR, а не успех.

Hidden expected outputs, verdict authority и comparator остаются вне candidate mount/process; readonly-доступа к ним недостаточно. Для общего Python-кода внутренний `unittest PASS` или JSON stdout не является доверенным verdict: candidate может подменять import resolution/framework. Внешний evaluator подаёт black-box inputs и сравнивает bounded outputs с закрытым oracle, связывая запуск с tree/profile. Отдельный отрицательный контроль: cheater, печатающий PASS или пытающийся читать expected/shadow judge, не получает product PASS. Узкий score-путь уже показывает полезный образец: candidate получает inputs, а `evaluateScoreResult` сравнивает их результаты вне bwrap; расширять нужно этот принцип, а не монтировать весь oracle внутрь.

**G2 — первый автономный компонент.** Новый отдельный brief: три cooperating production files `parser.py`, `normalizer.py`, `cli.py`; fixed/hidden QA вне write allowlist. После старта — без Sol. Нужны модельный план, настоящий test-failure feedback и хотя бы одно самостоятельное исправление; допустим заранее объявленный fault-injection scenario, но вмешательство injector учитывать отдельно. Приёмочные проверки не менять. После crash controller сам возобновляет тот же run без ручного изменения phase/счётчиков; QA повторно вычисляет результат. Если код с первой попытки корректен, это PASS coding, но repair всё равно требует отдельного доказательства. Нельзя выдавать G1 за G2.

**G3 — динамические агенты.** Доказать data-driven выбор роли и числа детей, а не только несколько заранее fork-нутых workers. Для минимального single-project gate можно заранее включить ограниченный пул principals в исходный grant и использовать отдельные role profiles поверх EXECUTOR. Host agent-request port выдаёт subset capabilities/deadline/quotas; child не может стать OWNER/QA или вызвать `issueCredential`. Отмена родителя, истечение/revoke и restart не расширяют права и общий budget. Дополнительные code/agent implementations и произвольная рекурсия не разрешаются этим gate.

При реальном совместном использовании GPU/модели несколькими проектами нужен host-global admission: существующий `resource_pool` имеет ключ `(project_id, resource_key)`, а `inferenceInFlight` действует в одном Node-процессе. [SQL resource pool](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/coordinator/migrations/0001-durable-runtime.sql#L30), [model guard](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/broker/model.mjs#L7). Для самого короткого G1 и изолированного single-project G3 достаточно явно исключить независимую конкуренцию и обеспечить один enforced parent pool. Общий Router-key ledger остаётся существующим D09/cloud4, не создаётся на каждого агента.

**G4 — новые executor implementations, позже.** Текущие A1 grants закрепляют точные capability refs/digests, а пересмотр grant может только сужать права. Новый код/manifest нельзя просто дописать к active grant. Путь: candidate artifact → sandbox/test → независимый QA → host activation pinned version → отдельный derived scope по заранее утверждённой registration policy. Host/QA остаются вне редактируемого candidate. Можно сначала использовать один установленный sandbox skill-runner с pinned artifact refs, не меняя kernel или исходный allowlist на лету.

## 7. Что мешает работать без Sol сейчас

Нет общего coding host и завершённого binder шести портов; fixtures/principals/capabilities/планы создаёт developer. Driver знает предметные task IDs, сам не выбирает repair и требует supervisor `start/resume`. Контекст и ответы модели ограничены small-canary профилем. Общий multi-file sandbox, tree-bound product QA, recoverable Git/test journal и durable delegation отсутствуют. GitHub PR данного этапа публиковал Sol; scratch Git score-helper не доказывает автономную работу с GitHub. Router cloud blocked технически, но не нужен как обязательное условие первого локального component gate.

После реализации P0–P4 роль Sol должна остаться до запуска — установка доверенных adapters/profile, постановка scope/oracle и начальный grant. Во время проверяемого G2 run ручное исправление кода, планов, состояния или запуск следующей фазы Sol считается вмешательством и отменяет заявление автономности этого run.

## 8. Неопределённости и границы

- **НЕ ДОКАЗАНО:** Qwen 4B успешно напишет выбранный multi-file компонент в заданных output/context/attempt bounds. Это выясняет G1, без обещаний срока/качества.
- **НЕ ДОКАЗАНО:** среда уже обеспечивает требуемые aggregate limits нового program runner; текущий narrow proof не заменяет его negatives.
- **НЕ ДОКАЗАНО:** у AWE есть unattended GitHub credential/reader/publisher; доступ Codex connector не является его реализацией.
- **ФАКТ источника:** cloud4 live binding возвращает BLOCKED; расходы владельцем разрешены, provider cap/ACK не доказаны. Это независимый поток, не повод ждать с локальным G1. [Binding](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/cloud4/provider-contract.mjs#L7).
- **ПРЕДЛОЖЕНИЕ:** начать с Python stdlib из-за доказанной исходной среды; JavaScript/зависимости/сервисы добавлять отдельными измеренными profiles. Наличие подходящего Node/toolchain внутри WSL этим аудитом не утверждается.
- **НЕ ДОКАЗАНО:** production AuthN, hostile arbitrary-code isolation, 24-hour unattended execution, E1 Pilot/Full. Ни модель роли, ни Git branch, ни число unit tests сами по себе этого не дают.

Стоимость реализации в днях, число необходимых модельных попыток и выигрыш скорости не оцениваются без первых результатов G1. Аудит даёт порядок работ, интерфейсы и evidence gates. Реализацию или дорогостоящие испытания этот документ не запускает.
