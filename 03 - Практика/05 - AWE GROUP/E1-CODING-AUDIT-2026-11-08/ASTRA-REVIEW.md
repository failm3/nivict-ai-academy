Автономное исправление компонента и выдача дочерних ролей требуют отдельных испытаний. Исторический PASS применим к синтетической миссии с одной функцией оценки. ## ВЫВОД · условия первого многофайлового теста

1. **Приоритет 1 — связать задачу и права до запроса модели.** V1 фиксирует repo, номер issue и base. Reader сверяет собственный хеш возвращённого текста. Содержимое issue может измениться в пределах того же номера и списка путей. Trusted host должен сверять digest утверждённого brief и создавать отдельную область для двух файлов. Снимок issue допустим при явном происхождении. Старый #2 задаёт ровно один файл. [Поля grant](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/contracts.mjs#L27) · [Проверка reader](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/executor.mjs#L35)
2. **Приоритет 1 — привязать испытание к фактическому дереву.** Generic test receipt содержит command digest, exit и признак sandbox. Закрепить head/tree и digest тестового профиля, входы, fence и уникальный invocation. Положительный тест требует двух совместно работающих файлов, CLI импортирует библиотеку; старый base и каждый одиночный файл должны провалиться. Скрытые ожидаемые ответы и полномочие выставить PASS должны оставаться за пределами процесса и доступных файлов candidate. Read-only доступ к ответам всё ещё допускает их чтение. Проверить, что поддельный `PASS` в stdout и подмена импортируемого тестового модуля отвергаются доверенным проверяющим процессом. Это условие будущего program runner. [Проверка receipt](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/executors/coding/executor.mjs#L53) · [Текущий точечный sandbox](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/recruit/coding/sandbox.py#L60)
3. **Приоритет 1 — сохранить результат и фазу ошибки.** Поле `result.output` должно соответствовать исходному `PATCH_PROPOSAL_SCHEMA`. Результат `validatePatchProposal` содержит дополнительные digests; его сохраняют отдельно вместе с Git, тестовыми квитанциями и исходной модельной provenance, закрепляя всё через `result_hash`. При известной ошибке теста engine возвращает REPAIR до вызова QA; при неподтверждённом модельном ACK общий BLOCK может скрыть сохранённый в A2 UNKNOWN. Bridge должен сохранять failed evidence/HOLD и исходный logical request. Перед Git записывается намерение; повтор после остановки сверяет уже записанные blobs и commit. ## ПРЕДЛОЖЕНИЕ · проверка следующего уровня

- **G1.** Зафиксированный двухфайловый план, одна попытка и локальный draft intent достаточны для первого положительного свидетельства. Использовать неизменяемый host-owned allowlist для source и отдельный запрет записи в runner, QA, protected core и host configuration. Необходима проверка замен путей, ссылок и частичной записи двух файлов. Готовность cloud или реальная публикация в GitHub для этого шага не требуются. ## НЕ ДОКАЗАНО · критерии пересмотра

Для generic coding нет положительного нативного двухфайлового прогона, для adaptive repair — замкнутого теста с восстановлением без Sol, для динамических ролей — измеренного provisioning. Для одного score-helper не доказана безопасность произвольной Python-программы. Подтверждённое восстановление worker не устанавливает наличие автономного сервиса supervisor.

Исторический PASS пришлось бы пересмотреть при несовпадении исходного oracle или байтов helper с принятым `score_author`, использовании fallback вместо этих оценок, расхождении cold readback и замороженного результата, дублировании логического эффекта либо нарушении независимости QA. Отрицательный контроль с подменённым ранжированием должен оставаться различимым. Для будущего G2 отдельным опровергающим наблюдением станет ручной выбор следующей ревизии, подмена кода или запуск следующей фазы оператором во время испытания. [Контроль исходного результата](https://github.com/failm3/awe-group-runtime/blob/9c3eaa182a862dadd5a326836408063b45f7219c/E1/qa4/COLD-cycle04_4101.json#L183)
