# 05 · Размещение аудиторского комплекта в одном GitHub

> **Цель владельца:** передать пяти независимым аудиторам **одну GitHub-ссылку**, а не отправлять каждому 20-МБ файлы или предоставлять доступ к рабочему компьютеру.

**Единая точка входа:** [README этого пакета](README.md) в публичном репозитории `failm3/nivict-ai-academy`. Здесь уже размещены документы 01–04, оригинальная CAREER-01, ссылки на прежние аудиты и текст LEVEL 2.

## Что должно появиться рядом

| Каталог/материал | Содержание | Готовность |
|---|---|---|
| `README.md` | Содержание, карта источников, статусы | Да |
| `01-OWNER-REQUIREMENTS.md` | Все 8 блоков согласованных требований | Да |
| `02-EVIDENCE-AND-INPUTS.md` | Исходные материалы и пробелы | Да |
| `03-INDEPENDENT-AUDIT-PROTOCOL.md` | Нейтральный протокол пяти аудитов | Да |
| `REFERENCE-LEVEL2-OBSERVATION.md` | Текст отчёта последнего наблюдения | Да |
| `build_audit_snapshot.py` | Локальный read-only упаковщик без LLM | Да, **не запускался** |
| `UPLOADS/source/` или `UPLOADS/archives/` | Реальный runtime включая доступные незакоммиченные файлы, в очищенной копии | **Нет** |
| `UPLOADS/evidence/` | Сырые логи, предыдущие тесты и рабочие артефакты после приватного просмотра | **Нет** |
| `UPLOADS/screenshots/` | Реально существующие скриншоты, после просмотра | **Нет** |
| `UPLOADS/manifests/` | File list, хеши, исключённые файлы и проверка целостности | **Нет** |

**Не создавать фальшивые скриншоты.** Их собирают только из реально существующих файлов/результатов испытаний. Если скриншот содержит секреты, приватные сообщения или аккаунты, сделать отдельную очищенную копию, не публикуя оригинал.

## Порядок

1. **Локальный сбор:** на компьютере владельца исполнить [`build_audit_snapshot.py`](build_audit_snapshot.py) в WSL. Скрипт только читает `~/awe-e1-live-runtime` и `~/awe-level2-observation`, собирает локальный baseline и отдельный кандидатный ZIP; текущий runtime не изменяет.
2. **Проверить полноту:** открыть локальные отчёты `reports/`, пройти исключения. Этот скрипт **намеренно не кладёт в кандидатную публикацию** чувствительные файлы, базы данных, изображения и подозрительные журналы автоматически. Это **не конечный полный комплект**; важные исключённые артефакты следует вернуть в очищенном виде после ручной проверки.
3. **Проверить чувствительные данные:** исключить ключи, cookies, персональные данные, письма и private receipts. Само автоматическое сканирование не гарантирует безопасность. Если нужно сохранить приватный неочищенный архив, не размещать его в публичной Academy.
4. **Сформировать release-ready архив** из одобренных материалов: `source/`, `evidence/`, `screenshots/`, версии среды, журналы, hash manifest, структура папок, `README`. Включить все используемые документы и честно отметить недоступные источники.
5. **Загрузить в GitHub.** Малые файлы/читаемые исходники/отчёты удобно держать прямо в папке `UPLOADS/`. ZIP и другие крупные бинарные материалы предпочтительнее поместить в **GitHub Release** того же репозитория и связать ссылки из этого README — всё равно получится **одна GitHub-ссылка для аудиторов**.
6. **Проверить внешним взглядом:** открыть ссылку без локального доступа, скачать архивы, проверить SHA-256, собрать структуру и прочитать документы. Только потом разослать одну ссылку пяти аудиторам.

## Ограничения GitHub

- Для обычного Git размер одного файла жёстко ограничен **100 МиБ**; крупные материалы следует хранить через Git LFS или GitHub Releases.
- Веб-загрузка файла ограничена **25 МиБ**.
- GitHub Releases позволяют прикреплять крупные ZIP и связать их с тем же репозиторием.
- Структура GitHub не обязана совпадать с физическим ZIP: достаточно прозрачных ссылок и проверяемых контрольных сумм.
- **Репозиторий публичный.** «Передать ссылку» означает, что и любой другой человек сможет открыть документы и опубликованные вложения. Если приватность обязательна, сначала использовать **приватный репозиторий + отдельный доступ** каждому аудитору; ссылка сама по себе приватный доступ не выдаёт.

## Чего делать нельзя

- Нельзя выполнять `git add .` в исходном WSL каталоге AWE или `git push` из него как способ «собрать весь проект»: это либо теряет незакоммиченные особенности, либо может слить секреты.
- Нельзя выгружать базу PostgreSQL, файлы авторизации, директории браузеров, личные письма и cookies в публичный репозиторий.
- Нельзя считать ZIP полным при наличии `REQUIRES_MANUAL_REVIEW` без указания, что конкретно отсутствует.
- Нельзя начинать пять формально полноценных технических аудитов, пока не готов **одинаковый и доступный** baseline.

**Статус:** GitHub-каркас есть; локальная упаковка и публикация исходников, логов и скриншотов ещё предстоят.
