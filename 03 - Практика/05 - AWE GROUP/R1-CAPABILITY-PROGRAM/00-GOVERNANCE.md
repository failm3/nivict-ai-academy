# R1-00 — Governance & Truth Registry

**Status:** DRAFT_READY_FOR_REVIEW. Не нормативный документ исполнения до принятия владельцем.

## Назначение

Все последующие блоки R1 должны быть совместимы с действующей архитектурой Head → Mission Manager → Agent Factory → Tool Intelligence → scoped execution → независимый QA → storage. Никакого второго управляющего Head, второго каталога, случайного включения 4504 инструментов и прямого вызова неавторизованных сервисов.

## Источники правды / запреты

1. **Runtime evidence**: только реальный код, версия, запущенный вызов, тест, trace, receipt и hash доказывают работу. Документация доказывает описание; smoke test доказывает отдельный вызов, не production.
2. **User approval**: внешний side-effect, изменение прав, установка непроверенного ПО, деплой, увеличение затрат, отправка заявок или сообщений — отдельное scoped разрешение согласно политике.
3. **Original acceptance**: Head и исполнитель не меняют исходное утверждённое ТЗ и QA oracle. Изменения вносятся только через версию.
4. **Security**: deny-by-default, недоверенная статья/описание tool не имеет полномочий менять инструкции, secrets не попадают в контекст/логи, project ACL фильтруется до retrieval.
5. **Skill vs Tool vs Knowledge**: Skill учит процессу; Tool совершает действие; Knowledge предоставляет факты/стандарты/источники; Pack условно требует их сочетания. Нельзя называть skill «проверенным MCP».
6. **First ready-made**: до написания адаптера проверяем Nox/Mastra built-ins, действующие TI/PG/Manus, стандартные MCP/API/CLI, безопасность, версию, лицензии и совместимость.
7. **No interference**: R0 должен завершиться и получить owner acceptance до внедрения R1 в runtime.

## Правило продвижения статуса

| Термин | Обязательное доказательство | Что не доказывает |
|---|---|---|
| CANDIDATE | URL / реестровый ID / описание | Установку и совместимость |
| VERIFIED | Проверка источника, версии, схемы, ограничений, прав/лицензии | Доступность сервиса из Nox |
| APPROVED | Запись разрешения в политике | Конкретный вызов |
| CONNECTED | Успешная проверка реального адаптера в конкретном окружении | Grant для любого агента |
| GRANTED | Ограниченный проектом/агентом/временем токен-полномочие | Успешный результат |
| INVOKED | Запись фактического tool-call с реальным ответом | Полный продукт |
| VERIFIED_RESULT | Результат, hash, проверка контракта | Качество без независимого QA |
| QA_PASS | Независимый gate против замороженных критериев | Право на опасный внешний side-effect |

Это **логические состояния**: отдельные grants имеют свой жизненный цикл, а регистрация ToolCard — свой. Не обязано быть одной колонкой ENUM в базе.

## Единый стандарт документа каждого блока

- **Problem / concrete user capability**: что сможет делать Nox после интеграции.
- **Reuse inventory**: что уже есть / где доказательства / что не подтверждено.
- **Selected implementation**: сервис, версия, адаптер, альтернатива, зависимость, лицензия, стоимость.
- **Contract**: вход, выход, права, scope, ошибки, telemetry, schema version.
- **Acceptance**: positive + negative + fault injection + independent QA.
- **Human decisions**: что утверждено, что ожидает решения и какой риск.
- **Evidence**: source commit, test invocation, logs, receipts, hashes, spend.
- **Rollback / revocation**: способ остановить и удалить разрешения без потери истории.

## Узлы интеграции

| Компонент | Обязанности |
|---|---|
| Head | Формулирует намерение и выбирает capability; не выпускает гранты сам |
| Tool Intelligence | Хранит/ищет provenance и карточки; не является универсальным executor |
| Capability Broker / Gateway | Проверяет готовность и policy, выдаёт кратковременный grant, вызывает adapter, журналирует receipt |
| Knowledge System | Находит подтверждённые источники с ACL и citations; не исполняет shell |
| Agent Factory | Выдаёт роли только разрешённые task-scoped capabilities |
| Mission Manager | Состояние/бюджет/отмена/recovery/idempotency |
| Independent QA | Сверяет исходные критерии с доказанным артефактом; не полагается на самопохвалу агента |

## Нерешённые решения — явный backlog

- Точная версия Mastra и существующих tool APIs **в локальном R0 checkout не подтверждены текущей документацией**.
- Набор доступных WSL MCP/adapters и разрешённых secrets должен быть подтверждён по реальным наблюдениям после R0.
- Политика user-vs-auto approval и допустимые источники знаний должны утверждаться отдельно.
- Параметры хранения (PostgreSQL/JSON/LibSQL/Supermemory) и схема grants требуют привязки к runtime — без миграции ради миграции.
