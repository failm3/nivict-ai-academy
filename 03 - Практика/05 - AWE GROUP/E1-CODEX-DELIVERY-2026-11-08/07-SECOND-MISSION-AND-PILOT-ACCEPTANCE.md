# B4/A4 · Вторая миссия: работающий продукт на том же ядре
**Статус:** READY_FOR_CODEX · **Зависимости:** A1/A2/A3, отдельный product brief владельца либо ограниченная инженерная fixture. **Параллельно:** B2/B3 после согласования интерфейсов.

## Зачем
Один отклик доказывает лишь карьерный канал. Нужно показать, что **та же AWE**, без нового scheduler/ledger, способна получить другую цель, распределить задачи между инженерными/UX/QA исполнителями и довести их до работающего программного результата. Это техническое доказательство переносимости; **не** предложение владельцу дизайна или концепции нового портфолио.

## Граница продукта
- Если владелец утвердил самостоятельный product brief — работать по нему. Если нет, разработать только минимальную **тестовую fixture** с двумя ролями, записью данных и чтением после restart. Не называть fixture полноценным портфолио и не изобретать продуктовую идею.
- Одинаковые с A версии `MissionSpec/Task/Capability/Artifact/QAResult`, coordinator, D03/D09, model broker, memory/SEC и обычный entrypoint. Разрешены доменные capability-адаптеры B, но **запрещён** специальный путь `if product` внутри generic scheduler.
- AWE самостоятельно планирует и распределяет хотя бы два типа реальных работ (LLM decision/code task и deterministic build/browser/test); не допускается заменять их ручным Codex исполнением и потом записывать `AWE_EXECUTED`.
- У рабочего программного результата должны быть изолированный staging, version/build digest, серверная авторизация, две разные тестовые роли и сценарий: создать запись → изменить/передать разрешённым способом → прочитать другим клиентом → restart → снова прочитать.
- QA независимый: browser E2E, data persistence, unauthorized operation, lost update/conflict и keyboard baseline; visual review по рубрике без утверждения, что автоматическая оценка доказывает художественное качество.

## Положительная приёмка
1. Один утверждённый/тестовый goal получает `mission_id`, версионированный spec/DAG, выбранные executors, real model calls, artifacts и QA verdict. Следы назначения должны исходить из AWE runtime.
2. Независимый клиент на работающем staging выполняет основной сценарий; запись доступна после перезапуска, другая роль не может изменить чужое.
3. Нет подмены `DONE` на реальный результат. QA reject при seeded defect, при повторном запуске не теряется принятая запись.
4. Совпадают **ядро, релиз, версии registry, broker, policy, memory и QA контракты** с A. Diff разрешённых domain adapters отмечен отдельно, без новых ledger/scheduler.
5. Если путь A ещё не прошёл реальный внешний send, B фиксируется отдельно; `A+B VERIFIED` ставить только после обеих доказанных миссий.

## Негативные сценарии
Invalid role, concurrent update, stale task fence, broken API, lost database connectivity, malformed tool proposal, чужой project ref. При поражении QA — исправление и реальный повтор. Если нет owner product brief, fixture может подтвердить **техническую** переносимость, но не подтверждает качество утверждённого продукта для портфолио.

## Выход
Рабочая staging версия, source PR, build digest, два client sessions, запущенные browser/API tests, immutable receipts и comparison trace A/B на общем release; список непроверенных свойств. **Никакой публичной публикации без отдельного grant.**
