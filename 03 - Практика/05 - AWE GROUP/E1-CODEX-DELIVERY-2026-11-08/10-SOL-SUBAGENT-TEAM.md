**Дата:** 2026-11-08 · **Статус:** READY_FOR_CODEX · **Реализация НЕ запущена**

## Назначение и граница
Это команда **разработчиков Codex**, работающих под управлением GPT-6.1 Sol. Они **не являются** реализованными агентами AWE GROUP. Sol — один интегратор и владелец общего архитектурного решения. Субагенты создаются штатной возможностью Codex Multi-agent в текущей доступной среде. Если эта возможность отсутствует, честно сообщить; не имитировать spawning фразами в отчёте.

## Когда расширять команду
После принятия A1+C1 Sol вправе перераспределить слоты:
- **A2 · Storage/Coordinator** — durable queue, PG lease, fencing, outbox.
- **A3 · Registry/LLM** — живой local model, selector, usage/cost, tools.
- **B1/B2 · Career inputs/QA** — отдельный поток проверки фактов/источников, **без реальных откликов**.
- Для B3 (внешний эффект) и B4 (другая миссия) — новые bounded tasks только после соответствующих зависимостей и разрешений.

Начать с 3 активных subagents; Sol может уменьшать число, если параллельность не даёт выгоды. Уменьшать число параллельных **записывающих** агентов, если они затрагивают общую схему. Не формировать глубокую иерархию помощников без независимых задач. Разграничить editor, QA и integration.

## Правила параллельной работы
1. Перед spawn Sol фиксирует список файлов/модулей, которые может изменять каждый агент, версию source, contract ownership и зависимости. **Никаких конкурентных правок одного файла, migration chain, project git index или shared PG namespace**.
2. Предпочитать отдельные Git worktrees/branches. Если реальные subagents Codex работают в одном файловом пространстве, назначать непересекающиеся edit scopes и сериализовать любые общие операции; отдельный subagent сам по себе **не создаёт** worktree.
3. Subagent получает только соответствующее GitHub-ТЗ, нужные source links, тесты и output contract, а не полный многотысячный контекст AWE.
4. О каждом завершённом subtасk subagent сообщает: changed paths, source commit, команды/test exit, фактические отрицательные сценарии, риски, blocker, дополнительные изменения в общих контрактах. Sol проверяет source и интеграцию, не принимает самоотчёт как доказательство.
5. Никаких изменений исходного `C:\Users\1\.codex\worktrees\92ef\AWE-GROUP-INT04`, исторического PG E0, чужих веток, приватных ключей и production. Новый PostgreSQL E1 / внешние API / платные модели / публикация — только в рамках выданных владельцем полномочий.
6. Subagents наследуют ограничения инструментов и среды Codex. **Промпт не отменяет встроенных подтверждений**, внешние действия не разрешены этим документом.
7. Делать регулярную интеграцию **после завершения конкретных вертикальных задач**, а не ждать, пока три ветки накопят огромные несогласованные diff. Sol запускает общий test suite на объединённой версии. Если схема конфликтует — исправить контракт и повторить обе проверки.
8. Модельные/токенные затраты: не запускать subagent для тривиальной последовательной задачи; сравнить wall-clock, суммарные tokens, collisions, тестовый результат и повторную работу после первой итерации.
9. QA из другой роли/контекста не равен независимой криптографической подписи D08: реальные release approvals и signed receipts остаются в E1 policy/QA.

## Проверка запуска
- Codex фактически показывает subagent threads/делегирование, а не просто пишет «делегировал».
- A1 и C1 могут показать разные изменения, у обоих есть source proof/test results, QA называет конкретные замечания или их отсутствие.
- Итоговые общие интерфейсы согласованы Sol, общая сборка и deny tests проходят.
- В GitHub отражены итог и следующий ID; никакой `E1 DONE` за один этап.
