## Рекомендация только для будущего пилота 02

1. **Corporate registry** на PostgreSQL: стабильные project_id, владелец, права, маршруты к хранилищам, версии конфигураций, состояния и аудит. Не рассчитывать, что Supabase самостоятельно реализует фабрику проектов.
2. **Project Provisioner** — тонкий детерминированный сервис + декларативные шаблоны Docker Compose; создаёт ресурсы только в пределах заданного шаблона/квоты, проверяет готовность, не выдаёт сам себе права.
3. **Storage Worker / adapter per storage type/resource**, а не LLM и не обязательно отдельный постоянно работающий процесс. PostgreSQL driver, backup worker, file/object worker, healthcheck; доступ по конкретной линии, журнал, error handling, retriable операции.
4. На старте для данных: **один кластер PostgreSQL и отдельные схемы/роли**, затем отдельные физические БД/кластеры по масштабу/риску. Схемы не создают автоматически жёсткую изоляцию: тестировать роли, RLS, доступы, исключения и многопроектные запросы.
5. **Kopia** для файловых snapshot; **Databasus** для согласованных копий PostgreSQL и проверки восстановления; **SOPS** для файловых секретов на раннем этапе.
6. **SeaweedFS, Infisical, AgentFS** — дополнительные кандидаты, не обязательные зависимости для пилота 02.

## Что доказано по документации

- [Supabase self-hosting](https://supabase.com/docs/guides/self-hosting): самостоятельно размещаемый стек; Studio в self-hosted режиме поддерживает один проект; бэкапы и хостинг администрирует пользователь.
- [AgentFS README](https://github.com/tursodatabase/agentfs): SQLite-based agent filesystem, история операций, snapshots; **BETA**.
- [Kopia features](https://kopia.io/docs/features/): шифрованные файловые snapshots, restore, CLI/API; **файловый snapshot не является доказанной согласованной копией работающей БД**.
- [Databasus README](https://github.com/databasus/databasus): PostgreSQL WAL/PITR, backup + restore verification; совместимость текущего окружения требует теста.
- [SeaweedFS README](https://github.com/seaweedfs/seaweedfs): распределённый S3/файловый слой.
- [SOPS README](https://github.com/getsops/sops): шифрование конфигурационных файлов; не полноценный online secrets manager.
- [Infisical license](https://github.com/Infisical/infisical/blob/main/LICENSE): open source core и отдельные enterprise-части.

## Обязательный пилот перед «Блок 02 закрыт»

Симулировать:
- создание линии с project_id и минимальными правами;
- восстановление существующей линии после рестарта;
- новую БД/схему и адаптер по необходимости, без потери старых данных;
- изоляцию и намеренные попытки чтения данных другой линии;
- файлы, поиск и контрольный журнал;
- корректную резервную копию PostgreSQL и реально выполненное восстановление;
- идемпотентность и поведение при повторной операции;
- удаление/архивацию по политике с подтверждением;
- сравнение затрат и сложности с существующим NIVICT Workspace/Hermes.

**Статус:** кандидаты проверены по документации; интеграции, лицензии всех компонентов и реальные испытания не проверены. Переход к блоку 03 только после обсуждения и решения пользователя. Canvas не менялся в этой операции.
