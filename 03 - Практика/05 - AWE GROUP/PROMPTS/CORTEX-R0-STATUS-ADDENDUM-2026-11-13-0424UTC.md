## 3. Независимые блокеры закрытия R0 — не скрывать и не умалять

Независимый QA зафиксировал следующие дефекты D1–D9 и дополнительный gap по бюджету агентов:

- **D1 / High:** `file_write` может изменить реальный файл **до** повторной проверки ownership/fence под lock. Отказ при регистрации артефакта не отменяет уже произошедшую запись.
- **D2 / High:** браузерный MCP adapter может продолжить реальный вызов после асинхронного обнаружения инструмента, не перепроверив fence непосредственно перед side effect.
- **D3 / High:** size/hash evidence не обязательны для всех артефактов; возможен ложный PASS после замены содержимого, в том числе одинакового размера, в сценариях обычной выдачи, repair, resume и reconciliation.
- **D4 / Medium:** отдельный `run-targeted-repair.ts` содержит жёстко заданный путь `.awe-data`, нарушающий универсальную изоляцию `AWE_DATA_DIR`.
- **D5 / High:** `web_search` не отменяет все исходящие запросы и может начать fallback **после** abort.
- **D6 / High:** abort не гарантированно прекращает выполняемый browser MCP action; эффект может продолжиться после отмены.
- **D7 / Medium:** делегирование в отдельном сценарии не передаёт конкретный `AbortSignal` дочерней работе.
- **D8 / High:** между внешним effect и записью checkpoint существует crash gap; при восстановлении действие может повториться без durable intent/idempotency/ambiguous-outcome policy.
- **D9 / Medium:** явное `child.tools: []` трактуется как отсутствие указания и может наследовать инструменты родителя вопреки ожидаемому least privilege.
- **Дополнительный критичный вопрос:** лимит количества агентов `maxTotalAgents` обходится через регистрацию верхнеуровневых делегаций, а перезапуск/возобновление может сбрасывать счётчик.

В положительную сторону **отдельно подтверждено**, что защита от захвата просроченного lease при живом владельце работает в локальных тестах. Контроль real data isolation и recovery существует частично. Не смешивать `PASS`, `PARTIAL` и `FAIL`.

**Не проверено этим QA:** реальные модели и платные API, фактический Playwright/MCP и внешняя сеть, PostgreSQL под нагрузкой, деплой, Windows computer-use и эксплуатационный стресс.

## 4. Что это меняет в твоём исследовании Cortex

1. **Не переписывай выводы как «R0 завершён».** Прими текущий уровень как `IMPLEMENTED + OFFLINE_TESTED + INDEPENDENT_QA_FAIL`. Окончательная сверка необходима по финальному исходному SHA после устранения замечаний и новой независимой приёмки.
2. **Не запускай исправление R0.** В рамках твоей задачи допустим только read-only разбор причин, enterprise практик, проектирование дополнительных негативных тестов и рекомендаций. Текущий OpenCode продолжает своё отдельное задание.
3. Исследуй с особым приоритетом зрелые готовые механизмы для **scoped permission/fencing в точке побочного эффекта, полной отмены web/MCP операций, idempotency/outbox/recovery, integrity hash/provenance, immutable artifacts, персистентного agent budget и изоляции данных**. Сравни их с действующими возможностями Nox/Mastra; не внедряй второй управляющий движок только ради решения этих проблем.
4. Все предложения по Tool Gateway, библиотекарю, Knowledge System, Skills, профессиональным Capability Packs и внешним API **должны быть привязаны к реальным точкам расширения Nox** и учитывать, что безопасность R0 ещё не принята. Нельзя делать новую «автономию» поверх неподтверждённой границы разрешений.
5. В итоговом `NOX-AS-IS-SOURCE-AUDIT` и `BUILD-BUY-REUSE-MATRIX` отрази уже реализованное, подтверждённые PASS, независимые FAIL/PARTIAL и то, что осталось UNKNOWN.
6. В `OPENCODE-READY-IMPLEMENTATION-PACK` раздели **«R0 acceptance prerequisites»** и **«будущие расширения R1»**. Вторые не должны зависеть от предположения, что первые закрыты. Если появится новый финальный R0 SHA, он заменяет этот срез после проверки.
7. **Исследование рынка и готовые предложения — да. Новые установки, изменения Nox, запуск платных/живых испытаний, вмешательство в R0, самостоятельный release или расширение прав — нет.**

**Ключевая цель не меняется:** найти существующие, легко встраиваемые в Nox решения для инструментов, профессиональных знаний и проверенных Skills; дать независимую критическую оценку и передать OpenCode конкретные небольшие задания для реализации **после** соответствующих допусков.
