### Жёсткий принцип архитектуры
`User → Prompt Master → Head → найти существующего или создать нового агента → агенты создают иерархические дочерние команды по задаче → выбор моделей и инструментов → исполнение → независимый QA по неизменяемому исходному ТЗ → результат владельцу + долговременная память`.

**Не создавай фиксированный штат агентов.** Организационная структура динамическая. В runtime при этом обязательны ограничения бюджета, числа одновременно работающих агентов, глубины рекурсии, повторов и полномочий. QA не может самостоятельно менять критерии, по которым его проверяемая работа оценивается.

### Базовые разрешения и границы
**Разрешено:** использование интернета, web/browser, GitHub, CLI/shell, файлов, тестов, текущих MCP/API и проверенных интеграций; использование доступных платных LLM через Router.Cheap и существующих поставщиков **в рамках уже действующих лимитов**; запуск параллельных независимых проверок и агентов; минимальные необходимые изменения кода.

**Не запрещай и не отключай существующие возможности AWE или OpenCode ради удобства испытания.** Не заменяй модели искусственно на бесплатные. **Не увеличивай лимиты расходов, не активируй новые платные услуги, не обходи доступы** без отдельного разрешения владельца. Никакой автоматической установки/исполнения непроверенного кода, массовых подключений, отправки email/Telegram, публикации сайтов или необратимых действий. Для локального тестового сайта, файлов, скриншотов и изолированных интеграций отдельное согласование не нужно. При блокере требующем sudo/секреты/OAuth/увеличение бюджета запроси ровно нужное разрешение и продолжай остальные безопасные пункты.
Работай с сохранёнными доказательствами, логируй стоимость и usage если API это сообщает. Не добавляй секреты в stdout/Recorder, PR или отчёты. Обеспечь восстановимость изменений.

## Этап 1 — целевое устранение блокеров
Исправь только воспроизводимые дефекты AWE-READINESS-01:
1. **QA и контракт миссии:** сохранить неизменяемую исходную спецификацию/обязательные критерии с версией или digest; верифицировать каждый критический критерий отдельно. `Pending transcription`, `placeholder`, отсутствующий скриншот, неполная передача `ti_search` должны запрещать COMPLETE независимо от среднего score. Добавить негативный регрессионный тест, который раньше ошибочно проходил. Независимый examiner не должен зависеть от самоотчёта writer.
2. **Потеря результатов между агентами:** researcher → writer/Head → QA должен переносить данные и источники, а не только утверждение «поиск выполнен». Проверить end-to-end на реальном каталоге с ожидаемыми source IDs.
3. **Жизненный цикл и resume:** таймаут/потеря процесса не оставляет вечный `running`; процесс обнаруживает прерывание, сохраняет checkpoint, корректно возобновляет миссию по тому же ID без повторного необратимого эффекта. Подтвердить контролируемым kill/resume тестом.
4. **Браузер:** сохранить рабочий Chromium+shell путь; отдельно проверить настоящий вызов разрешённого Playwright MCP агентом. Локальные .deb библиотеки и runtime-конфигурация должны быть воспроизводимы и не зависеть молча от временного `/tmp`; не менять системный Chromium без необходимости.
5. **Проверка рекурсивного делегирования:** Head → руководитель → дочерний исполнитель (минимум два уровня), отдельные контексты, подчинённые права, ограничение глубины/бюджета; если механизм отсутствует, сначала найти минимальное готовое решение среди уже исследованных, не писать новый фреймворк без сравнения.

**Gate 1:** тесты на ложноположительный PASS, потерю `ti_search`, timeout/resume, браузер MCP и двухуровневое делегирование дают воспроизводимые результаты. Любой незакрытый критический пункт = BLOCKED/PARTIAL, а не переименованный PASS. Если критический блокер сохраняется после ограниченного диагностического/исправительного цикла, документируй его и не заявляй полную готовность.

## Этап 3 — каталог для самой AWE и её динамических команд
AWE должна искать **по способностям**, а не копировать 4504 описания в LLM context. Используй существующий Tool Intelligence v2 как основу и проверенные нормализованные exports Codex; не создавай второй параллельный реестр или конкурирующий оркестратор без объективной причины.

- Сохрани исходное происхождение, ID, version, duplicate groups и статусы: DISCOVERED / DOCUMENTED / TESTED / APPROVED / INTEGRATED. **4 504 кандидата ≠ 4 504 разрешённых интеграции.**
- Если полный Manus 3415 export доступен в корректном формате, импортируй в **отдельную тестовую DB/schema**, сравни counts/hash, затем только неразрушающе подключай read-only поиск к AWE; действующую рабочую 12-record DB не затирай. 4504 NIVICT учитывай как отдельный source с дедупликацией и provenance. Если backup / schema не доступен, пометь BLOCKED и используй подтверждённую часть без фантазии.
- Обеспечь Head и его дочерним агентам `searchCapabilities` / `ti_search` с короткими релевантными результатами, источниками, рисками и типом исполнения. Policy engine проверяет права до вызова инструмента; обнаружение никогда само по себе не разрешает установку.
- Покажи 3 реальных сценария: поиск браузерной способности; поиск frontend/design/visual QA; поиск инструмента для разработки/документации. Для каждого: реальные записи, способ использования, существующее разрешение или отказ, вызванный инструмент и результат, если разрешён.
- Один негативный тест: неподтверждённый/отозванный кандидат не может стать автоматически разрешённым и выполненным.

**Gate 3:** AWE и минимум один её реальный подагент извлекают релевантные инструменты и безопасно используют хотя бы один **действительно разрешённый** инструмент. Логи и итоговый отчёт содержат фактический tool call, источники, результат и проверки полномочий.

## Этап 4 — первая настоящая дизайн-миссия AWE (НИКАКОЙ ручной разработки OpenCode)
**После прохождения критических Gate 1 и Gate 3** передай через исходную цепочку `User → Prompt Master → Head` следующее пользовательское задание; не кодируй решение своими руками:

> «Создай профессиональную русскоязычную адаптивную интерактивную веб-страницу NIVICT, демонстрирующую направления Product Design и AI Agent Engineering. Это первый самостоятельный продукт AWE GROUP. Самостоятельно сформируй проектную команду под задачу, определи визуальную концепцию, информационную архитектуру, дизайн-систему, реализуй работающий frontend, проверь страницу в браузере на десктопе и мобильной ширине, исправь обнаруженные визуальные и функциональные дефекты, сохрани исходники и изображения и предоставь открываемый локальный URL/файл с доказательствами. Используй существующие проверенные инструменты и исследовательский каталог для поиска недостающих возможностей. Не выдумывай коммерческих клиентов, награды, отзывы, портфолио-кейсы или статистику. При отсутствии подтверждённых фактов используй нейтральный демонстрационный контент с ясной маркировкой».

Критерии принятия **этой миссии должны быть закреплены до начала работы Head**:
- Не презентация, не Markdown-описание и не один скриншот: реально работающий frontend в отдельном проекте, доступный локально.
- Ясная визуальная иерархия, современная индивидуальная композиция, типографика, адаптивность (проверить хотя бы desktop и mobile), осмысленные состояния интерактивных элементов, отсутствие грубых переполнений/перекрытий/ошибок консоли.
- Реальная динамическая команда (созданные/переиспользованные агенты, фактические tool/model calls, взаимодействие и сохранённый контекст). Не имитировать отдельные роли текстом.
- Снимки desktop/mobile, результаты функционального и визуального QA, замечания/правки, независимая приёмка по первоначальным критериям.
- Материалы и исходники доступны для следующей итерации владельца. Не публиковать в открытый интернет без разрешения.
- **OpenCode только запускает, наблюдает и проверяет**. Если AWE застряла на блокере, OpenCode может отдельно исправить только infrastructure-level отказ, затем повторно предоставить задачу AWE; фиксируй вмешательство, не выдавай работу OpenCode за работу AWE.

**Gate 4:** можно открыть страницу, проверить взаимодействия и адаптивность, увидеть исходники и доказательства, независимый QA подтвердил все критические критерии. При отсутствии любого критического доказательства — честный PARTIAL/FAIL с работающим остатком, без косметического PASS.

### Управление объёмом, временем и стоимостью
- Это одна миссия с 4 этапами и фиксированными gates, **не carte blanche на месяцы переписывания платформы**. Сначала reuse готового, потом минимальная адаптация; расширение scope/архитектуры только после отдельных фактов и согласования.
- Разрешены платные запросы **внутри текущего бюджета и лимитов**. Нельзя самостоятельно увеличивать предельные траты, отключать бюджетные защитные механизмы или устраивать бесконечные retry. На каждом этапе показывай usage и фактические расходы, если provider их отдаёт.
- Не ослабляй acceptance criteria, не снижай проходные пороги ради `PASS`. Нельзя объявлять `COMPLETED`, если критерий не выполнен, даже если QA-модель выставила высокий балл.
- Перед следующим этапом сохрани checkpoint. Если gate не достигнут: выдай PARTIAL, артефакты, точный блокер и останови опасную зависимую работу, но продолжай независимые безопасные пункты.
- Отдельная инженерная ветка и PR, no automatic merge. Сохрани в GitHub проверяемые исходники, конфигурации, тесты, отчёты, artifact manifest и журнал решений, без секретов, огромных бинарников и временных дампов. Зафиксируй git SHA и подтвердить readback. Не заявляй, что push сделан, если не сделан.
