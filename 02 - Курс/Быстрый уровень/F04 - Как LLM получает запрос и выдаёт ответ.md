# F04. Как LLM получает запрос и выдаёт ответ

> **Статус:** освоено на вводном уровне в диалоге. Ученик самостоятельно объяснил устройство приложения с LLM API, необходимость передачи файлов, пакетную обработку и объединение результатов. Реальная программная реализация не проверялась.

**Опора:** [[02 - Курс/Быстрый уровень/F03 - Автоматизация, бот, workflow, LLM и агент|F03 — бот, workflow и агент]].
**Дальше:** [[02 - Курс/Быстрый уровень/F05 - Токены, контекст и вероятностная генерация|F05 — токены, контекст и генерация]].

## Основная модель взаимодействия

Пользователь → интерфейс приложения → программная логика (инструкции, данные, инструменты и разрешения) → API языковой модели → сгенерированный ответ → приложение → пользователь.

- **Интерфейс** принимает ввод и показывает результат.
- **Приложение** управляет сборкой запроса, доступом к файлам, вызовами моделей, очередями и проверками.
- **LLM** получает переданный ей контекст, обрабатывает его и генерирует ответ. API к готовой GPT не превращает приложение в собственную LLM.
- **Собственная агентная система** может включать разные сторонние LLM и собственные инструменты; собственная инфраструктура и собственная модель — разные вещи.
- Модель не получает автоматически доступ ко всем файлам компьютера. Приложение должно выбрать данные и разрешённым способом сделать их доступными модели через контекст или инструменты.

## Пример: 10 000 документов проекта

1. Программа индексирует/ищет документы по нужному проекту; может использовать обычный поиск, метаданные или обученные классификаторы.
2. **Не следует бездумно отбрасывать документы**: если документ не передан модели, модель не увидит содержащуюся только в нём ошибку. Поисковый фильтр тоже может ошибаться.
3. Если требуется полный охват, программа ведёт реестр **всех** документов, разбивает данные на порции по реальному размеру (в токенах, оставляя место для ответа), ставит их в очередь и вызывает модель.
4. Каждая порция получает отчёт с источниками, обнаруженными проблемами и ограничениями. Программа отмечает статус обработки, учитывает ошибки вызовов и может безопасно повторять неудачные операции.
5. Собираем результаты структурированно: область/компонент, серьёзность, доказательства, источник, версия/время, статус проверки.
6. **Нельзя терять критическую находку при суммировании:** даже если большинство отчётов говорят «проблемы не обнаружены», критическая находка должна сохраниться в итоговом реестре.
7. Для разных областей возможны разные статусы (норма/неясно/критично); противоречия **в одной области и одинаковых условиях** требуют повторной проверки. Разные компоненты или версии не обязательно противоречат друг другу.
8. Итоговое текстовое резюме не заменяет полный реестр наблюдений. Отчёт модели тоже может пропустить ошибки; полнота анализа требует отдельного контроля.

## Понятия, возникшие в обсуждении

- **Batch processing:** обработка данных порциями.
- **Task queue:** очередь заданий; порядок исполнения задаёт программа, а не необходимость вручную отправлять каждый файл.
- **Контекстное окно:** ограничение объёма переданного модели содержания, измеряемого токенами, а не количеством файлов.
- **Классификация результатов:** например, «критическая проблема», «требует уточнения», «проблемы при проведённой проверке не обнаружены». Последнее **не равно** гарантии отсутствия проблем.
- **Объединение результатов:** сохраняем первичные наблюдения и их источники, а не только обобщённые пересказы.

## Что ученик объяснил сам

- При подключении GPT по API мы создали собственное **приложение**, но не собственную языковую модель.
- Доступ к локальным документам должен обеспечивать код и доступные инструменты.
- Отобранные 200 документов не позволят найти ошибку в оставшихся 9 800, если информация о ней больше нигде не встречается.
- Анализ тысяч документов можно автоматизировать очередью и ограниченными порциями, не передавая всё за один запрос.
- Для общего отчёта нужны категории по серьёзности; противоречия внутри одной области требуют пересмотра, отдельная проблема в другой области — локального расследования.

## Как объяснить сотруднику

«LLM — не вся система. Приложение собирает данные, вызывает модель через API, управляет её правами, ограничениями и очередями. Для большого массива документов приложение разбивает работу на порции, собирает проверяемые результаты и сохраняет все критические находки».

## Граница освоения

Понятия освоены **концептуально**. Программное создание API-запросов, подсчёт токенов, надёжные очереди, поиск с измеримым охватом и промышленное агрегирование отчётов будут изучаться и тестироваться отдельно.
