# F18. Инженерные роли и итоговая карта системы

> **Статус:** завершён на вводном уровне; итоговая проверка архитектуры проведена.

**Опора:** [[02 - Курс/Быстрый уровень/F17 - Как работает платформа создания агентов|предыдущий урок]]  
**Главная мысль:** Профессиональная компетентность — способность обосновать архитектуру, реализовать и доказать её работу, а не знание названий инструментов.

## Что разберём последовательно
1. Различия между Agent Engineer, Applied AI Engineer и ML Engineer.
2. Ключевые навыки: программирование, API, базы данных, тесты, безопасность.
3. Как читать вакансию и отделять требования от названий фреймворков.
4. Итоговая карта: от пользователя и LLM до инструмента, оркестрации и проверки.

## Один конкретный пример
Кандидат объясняет поток заявки и показывает проверяемый мини-проект, а не только список изученных библиотек.

## Зачем это будущему инженеру
Понимать траекторию от базовой грамотности к техническим интервью и портфолио в РФ и за рубежом.

## Зачем это для платформы создания агентов
Увидеть пробелы перед переходом к прототипу и фундаментальной модели.

## Короткая проверка понимания
Своими словами нарисовать систему из LLM, программы, инструментов, данных, оркестратора и проверок.

## Типичная ошибка
Приравнивать быстрый обзор 18 уроков к готовности к вакансии.

## Вернёмся позже
Python, математика, системный дизайн, английский инженерный словарь, лабораторные работы.

- На вопрос о профессиональных ролях пользователь самостоятельно различил функции: Agent Engineer проектирует агентную схему, Applied AI Engineer внедряет ИИ в продукт, ML Engineer работает с обучением, моделями и эксплуатацией. Не сделал окончательного выбора одной роли; первоначально сузил Agent Engineering до схемы, ML Engineering — до создания работоспособной технической системы.
- Скорректировано: Agent Engineer также реализует инструменты, память, оркестрацию и проверки; Applied AI Engineer может строить агентов и интеграции; ML Engineer отвечает за модели, обучение, инференс и эксплуатационные ML-процессы. Роли пересекаются, не являются строго последовательными этапами или разделением на «красивое» и «работающее». Для Agent Factory наиболее близки Agent Engineering + Applied AI Engineering, позже потребуются ML-компетенции при собственной LLM.
- Следующая проверка: назвать конкретный первый практический навык, который нужно развивать для самостоятельного создания Agent Factory, с объяснением приоритета.

- На вопрос о первом навыке для самостоятельного создания Agent Factory пользователь сначала выбрал **программирование**, затем усомнился, сопоставляя необходимые компоненты агента (запрос, инструменты, LLM, безопасность); честно признал, что пока не готов уверенно расставить приоритеты.
- Разъяснено: программирование связывает компоненты агентной системы — API, вызовы LLM и инструментов, состояние, права, обработку ошибок, тесты. Агент может существовать без внешних инструментов с ограниченной функциональностью; отсутствие защиты не препятствует техническому запуску, но делает рискованной реальную эксплуатацию. Для практики предложены Python или TypeScript, API, JSON, обработка ошибок как базовый стек; не нужно становиться специалистом по всем направлениям до первого прототипа.
- Следующий шаг F18: короткий сценарий выбора исполнителя действий и проверок между LLM и программным кодом, затем итоговая схема системы и план следующего уровня.

- На контрольный вопрос о фактической отправке письма через почтовый API пользователь правильно разграничил роли: **программный код отправляет письмо, LLM генерирует его содержание**. Уточнено, что LLM также может понимать намерение и предлагать действие, однако авторизацию, ограничения и вызов API контролирует код; система должна проверять результат API/фактическое состояние, не доверять одному заявлению модели.
- Следующий шаг: финальная связная проверка системы — кратко назвать ключевые компоненты агентной архитектуры, их роли и порядок работы, затем оформить итоги 18-го урока.

- **Итоговая проверка 18 уроков:** пользователь своими словами построил поток: задача поступает → программный код классифицирует/направляет → проверка маршрута → выбор между кодом/инструментами и LLM → оркестратор распределяет работу → проверяющий оценивает итог → результат пользователю. Подчёркнуты собственная «конституция»/политики и проверки между шагами.
- **Что понял верно:** систему нужно строить из распределённых ролей кода, инструментов, модели, оркестратора и независимого контролёра; не все задачи должны уходить в LLM; формальный результат должен подтверждаться.
- **Уточнения/пробелы:** пользователь не назвал **память** и хранение состояния; оркестратор действует с начала и на протяжении всего процесса, а не только после маршрутизации; код может валидировать и маршрутизировать по заданным правилам, но неоднозначный запрос требует семантической интерпретации (LLM или других методов); инструмент вызывается через контролируемый программный слой; проверка должна быть основана на реальных результатах, а не словах модели. Слишком частый проверяющий на каждом тривиальном шаге может быть избыточен; точки контроля выбирают по риску.
- **Корректная схема:** входной запрос → проверка полномочий/ограничений и маршрутизация → оркестратор планирует шаги → выбор модели, кода и инструментов; чтение контекста/знаний из памяти и сохранение чекпоинтов → выполнение → независимая проверка критериев и инструментальных доказательств → завершение, доработка или эскалация.
- **Результат:** быстрый уровень F01–F18 освоен **концептуально**, не является подтверждением готовности самостоятельно разрабатывать продукционные системы.

## Итоги урока F18

**Понял своими словами:** LLM отвечает за работу с неопределённостью, анализ и генерацию; программный код вызывает инструменты и контролирует выполнение, оркестратор управляет процессом, проверяющий подтверждает результаты. Роли Agent Engineer, Applied AI Engineer и ML Engineer пересекаются.

**Новые термины:** Agent Engineer, Applied AI Engineer, ML Engineer, API, архитектура агента, контрольные точки.

**Осталось освоить на практике:** программирование (Python/TypeScript), API/JSON, базы данных/память, orchestration, тестирование, безопасность, наблюдаемость, реализация и проверка реальной Agent Factory.

**Как объяснить сотруднику:** «Агент — не одна LLM, а система, в которой программа управляет инструментами и правами, модель помогает принимать решения, память хранит контекст и состояние, оркестратор ведёт процесс, а проверка устанавливает, действительно ли результат достигнут».
