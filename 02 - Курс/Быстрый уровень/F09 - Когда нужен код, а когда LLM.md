# F09. Когда нужен код, а когда LLM

> **Статус:** запланировано. Это маршрут будущего диалога, **не освоенный конспект**.

**Опора:** [[02 - Курс/Быстрый уровень/F08 - RAG, знания, память и поиск|предыдущий урок]]  
**Главная мысль:** Если задачу можно надёжно решить фиксированными правилами, агент может быть ненужным; модель добавляют, когда нужна гибкость в интерпретации.

## Что разберём последовательно
1. Детерминированный сценарий и неопределённый вход.
2. События, расписания, проверки и скрипты.
3. Где LLM полезна, а где увеличивает риск и стоимость.
4. Принцип минимально достаточной архитектуры.

## Один конкретный пример
Регулярное резервное копирование выполняет программа по расписанию; LLM может классифицировать нестандартные обращения о сбоях.

## Зачем это будущему инженеру
Аргументировать выбор решения по надёжности и стоимости, а не моде.

## Зачем это для платформы создания агентов
Генератор агентов должен уметь выдавать также обычный workflow/скрипт, если это лучше.

## Короткая проверка понимания
Выбрать минимальную архитектуру для трёх задач: копирование файла, классификация письма, разбор нестандартной претензии.

## Типичная ошибка
Считать количество агентов метрикой качества системы.

## Вернёмся позже
Очереди, вебхуки, cron, надёжность автоматизации.
