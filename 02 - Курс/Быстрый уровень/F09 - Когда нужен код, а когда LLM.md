# F09. Когда нужен код, а когда LLM

> **Статус:** завершён на вводном уровне с проверкой понимания на практических сценариях.

**Опора:** [[02 - Курс/Быстрый уровень/F08 - RAG, знания, память и поиск|предыдущий урок]]  
**Главная мысль:** Если задачу можно надёжно решить фиксированными правилами, агент может быть ненужным; модель добавляют, когда нужна гибкость в интерпретации.

## Что разберём последовательно
1. Детерминированный сценарий и неопределённый вход.
2. События, расписания, проверки и скрипты.
3. Где LLM полезна, а где увеличивает риск и стоимость.
4. Принцип минимально достаточной архитектуры.

## Один конкретный пример
Регулярное резервное копирование выполняет программа по расписанию; LLM может классифицировать нестандартные обращения о сбоях.

## Зачем это будущему инженеру
Аргументировать выбор решения по надёжности и стоимости, а не моде.

## Зачем это для платформы создания агентов
Генератор агентов должен уметь выдавать также обычный workflow/скрипт, если это лучше.

## Короткая проверка понимания
Выбрать минимальную архитектуру для трёх задач: копирование файла, классификация письма, разбор нестандартной претензии.

## Типичная ошибка
Считать количество агентов метрикой качества системы.

## Вернёмся позже
Очереди, вебхуки, cron, надёжность автоматизации.

## Подтверждено в диалоге

- На примере ежедневной резервной копии БД в 03:00 пользователь самостоятельно выбрал обычную программу без LLM: повторяемая задача по расписанию. Верно заметил, что агентная система может включать обычные программные компоненты и поручать им операции.
- Уточнение: для **самого запуска по расписанию** агент также не обязателен — достаточно планировщика и программы. Агент полезен при настройке, мониторинге, необычных ошибках и принятии решений; результат копирования следует проверять программно.
- Дальше: различить автоматическую обработку успешного результата и случаи, где действительно нужна модель.

- При ошибке `backup_integrity_check_failed` пользователь предложил многоуровневую схему: обычная программа делает диагностику и безопасные повторы, при неразрешённой нестандартной ошибке подключает ИИ-агента с инструментами (включая LLM), затем эскалация человеку. Это верный выбор ролей.
- Уточнения: ошибка целостности не означает, что надо слепо повторять операцию; не затирать последнюю исправную копию, сохранять результаты проверок и делать повтор только по заданной безопасной политике. ИИ-агент не должен выполнять разрушительные исправления без прав и контроля.
- Следующая задача: разграничить понимание нестандартного обращения пользователя (LLM) и объективную проверку работы сайта (обычные инструменты).

- На обращение о периодической недоступности сайта для пользователей из Казахстана ученик правильно предложил обычные диагностические инструменты: повторные запросы, проверки DNS, протоколов и сетевой доступности. Для возможного изменения кода выбрал LLM.
- Уточнение: LLM помогает интерпретировать логи и предложить правку, но фактические изменения выполняются программными инструментами/разработчиком с правами и проверками. Не каждое исправление кода требует LLM; сначала доказать, что причина в коде, а не региональной сети, DNS, маршрутизации, CDN или провайдере. Проверки DNS из разных мест не заменяют региональные тесты доступности.
- Следующая проверка: когда предсказуемое исправление конфигурации можно автоматизировать кодом без LLM и какие ограничения нужны для опасных действий.

- При отказе одного сервера с заранее настроенным и протестированным резервным узлом пользователь верно выбрал **автоматическое переключение обычной программой без LLM**: процедура определена, её результат проверяем. Термин: automatic failover. Для надёжности программа проверяет работоспособность резервного узла, успешность переключения, фиксирует события и эскалирует при неудаче.
- Следующий учебный шаг: как выбрать минимально достаточную архитектуру для разных задач, включая неоднозначные обращения без заранее заданного сценария.

- Для классификации свободно сформулированных обращений клиентов пользователь выбрал гибридную схему: LLM первым этапом интерпретирует текст и формирует категорию, затем обычная программа обрабатывает результат по правилам. Причина — формулировки клиентов заранее неизвестны, тогда как маршрутизацию и ограничения полезно держать детерминированными.
- Уточнено: LLM не просто «генерирует информацию», а классифицирует смысл и выдаёт структурированный ответ; программа проверяет допустимую категорию и направляет заявку. При неопределённости или нераспознанной категории — ручная обработка, не придумывать уверенный ответ.
- Следующий шаг: короткая заключительная проверка, где модель может ошибиться при классификации и как программа должна на это отреагировать.

## Итоги урока F09

**Понял своими словами:** когда действие повторяемо и реализуемо надёжно по известным правилам, достаточно обычного кода и планировщика. LLM полезна при интерпретации неоднозначного текста/нештатных ситуаций. В гибридном решении модель классифицирует или предлагает шаг, а программа проверяет и выполняет разрешённые действия.

**Проверено на примерах:** 
- Ежедневная резервная копия в 03:00 — обычный планировщик и программа, агент не обязателен.
- Ошибка целостности резервной копии — сначала программная диагностика и безопасные процедуры, затем агент при сложной проблеме, затем человек; сохранять последнюю исправную копию.
- Региональная недоступность сайта — реальные сетевые проверки из соответствующих регионов; LLM может анализировать результаты, исправления вносит исполнитель.
- Заранее настроенное и протестированное переключение на резервный сервер — обычный автоматический failover.
- Свободный текст клиентских обращений — LLM для классификации, код для проверки ответа и маршрутизации.
- Если модель возвращает `unknown_problem` вместо одной из четырёх разрешённых категорий, ученик предложил отклонить результат, но назвал это синтаксической ошибкой. Уточнено: это **ошибка валидации значения** (`invalid_category`), а не Syntax Error. Программа не должна маршрутизировать заявку наугад, нужна повторная классификация либо ручная обработка.

**Термины:** deterministic workflow, failover, классификация, validation error и syntax error, минимально достаточная архитектура.

**Граница освоения:** понятийное понимание подтверждено; код, тестирование, оркестрация и эксплуатационные сценарии будут изучаться дальше. В частности, различие синтаксиса и валидации требует закрепления практикой.

**Как объяснить сотруднику:** «Если сценарий предсказуем, делай его обычной программой с проверяемым результатом. Если нужно понять свободный текст или новую нестандартную ситуацию, подключай LLM. Само действие остаётся под контролем обычного кода с проверкой входных и выходных данных, разрешений и рисков».
