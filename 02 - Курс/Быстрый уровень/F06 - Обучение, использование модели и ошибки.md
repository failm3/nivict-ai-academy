# F06. Обучение, использование модели и ошибки

> **Статус:** освоено на вводном уровне в беседе. Понимание training / inference, источников достоверности, различия обновления данных и дообучения проверено примерами. Реальная инженерная реализация не проверялась.

**Опора:** [[02 - Курс/Быстрый уровень/F05 - Токены, контекст и вероятностная генерация|F05]].
**Дальше:** [[02 - Курс/Быстрый уровень/F07 - API, JSON и инструменты агента|F07]].

## Основная мысль

- **Training (обучение)** — отдельная процедура изменения параметров/весов модели при оптимизации по обучающим данным.
- **Inference (инференс)** — применение обученной модели для ответа; обычные запросы через GPT API не дообучают веса модели.
- **Prompting** изменяет инструкцию или контекст, **retrieval** предоставляет актуальные внешние данные, **fine-tuning** обновляет параметры модели по специальной процедуре. Это разные механизмы с разными задачами.
- Внешняя память может накапливать опыт работы, решения и результаты без изменения весов LLM. Модель и система вокруг неё — разные сущности.
- Убедительная формулировка модели не равна доказательству. Возможны ошибки или **галлюцинации** даже при полном входном контексте. Предположение LLM о собственной ошибке нужно проверять по фактическим входам, логам, трассировкам и независимым испытаниям; точную внутреннюю причину отдельного ответа не всегда можно установить.
- **Source of Truth** — установленный для конкретного класса сведений актуальный и уполномоченный источник. Для причины отмены заказа — исходное сообщение клиента; для тарифа — утверждённая база/реестр тарифов, если именно он назначен первичным. Сайт может отражать данные из этого реестра или сам быть первичным источником по принятой архитектуре, но не автоматически: возможны устаревший кэш, ошибочные правки и несогласованные версии.
- Если вывод модели противоречит авторитетному первичному источнику, система должна предпочесть проверяемые доказательства и отразить конфликт, не выдавать собственную догадку за факт.

## Что ученик объяснил сам

1. После анализа 500 заказов через API модель сама не переобучилась; улучшиться могла внешняя инфраструктура поиска и памяти.
2. Предложил **проверяющего перед записью** подтверждённых знаний в рабочую базу, отдельное хранение сырого материала, проверяемых и подтверждённых результатов. Размещение по физическим БД — вопрос реализации, а не обязательное условие.
3. В ситуации ошибки классификации отмены заказа предложил расследование с логированием и трассировкой; если сообщение клиентa фактически было передано полностью, гипотеза об обрезке контекста не подтверждается.
4. Обосновал приоритет первичного документа над уверенной интерпретацией LLM («конституция»), с дальнейшим уточнением полномочий и версии источника.
5. Предложил, чтобы агент сам замечал изменения тарифов и кода, классифицировал уровень риска, уведомлял/согласовывал рискованные операции.
6. В финальном примере смены тарифа с 5 000 ₽ на 7 000 ₽ объяснил: программа фиксирует изменение, сравнивает и проверяет версии/разрешения, после чего агент получает подтверждённую актуальную цену через **retrieval/API**, не изменяя веса модели.

## Поправки в ходе обсуждения

- «Подключили GPT, а не LLM» → GPT — семейство LLM; API — способ доступа к модели.
- «Всякий новый тариф нужно дообучить в LLM» → обычно достаточно обновлённого надёжного источника данных и получения актуальной записи, без fine-tuning.
- «Объяснение самой LLM про ошибку раскрывает истинную причину» → это может быть гипотеза, но не доказательство.
- Уточнено недопонимание преподавателя: пользователь **изначально подразумевал проверяющего**, который допускает сведения в основную базу, а не некритичное сохранение всех ответов.

## Как объяснить сотруднику

«Когда приложение вызывает LLM через API, оно использует обученную модель, но не изменяет её веса. Если цены изменились, агент должен получить утверждённую актуальную цену из источника, а не обучать модель заново. Уверенная генерация не подтверждает факт: результаты сверяем с надёжными исходными данными, важные выводы проверяем и фиксируем, что было реально выполнено».

## Граница освоения

Понимание **концептуальное**, без собственной процедуры fine-tuning, запуска API, измерения точности и технического анализа внутренних причин ошибок. Подробный вопрос о механизмах галлюцинаций записан в [[99 - Вопросы/Вернёмся позже|отложенные вопросы]] и вернётся на продвинутом уровне.
