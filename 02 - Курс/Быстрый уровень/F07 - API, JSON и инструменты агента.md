# F07. API, JSON и инструменты агента

> **Статус:** освоено на вводном уровне; пользователь самостоятельно объяснил интерфейсы, права доступа, структуру данных и обработку ошибок. Реальные API и код пока не реализовывали.

**Опора:** [[02 - Курс/Быстрый уровень/F06 - Обучение, использование модели и ошибки|F06]].
**Дальше:** [[02 - Курс/Быстрый уровень/F08 - RAG, знания, память и поиск|F08]].

## Ключевые знания

1. **API** — определённый интерфейс взаимодействия программ. В предложенной пользователем аналогии «кораблик между островами» саму передачу данных выполняет сеть/транспорт, а API описывает «причал и правила». API бывает не только веб-API; взаимодействие с локальным модулем или БД также использует интерфейсы.
2. **JSON** — формат структурированных данных. Объект содержит поля вида `"ключ": значение`. Например, `{"order_id":125,"status":"ready","total":7000}`. Добавление поля в JSON-ответ само по себе не создаёт его в базе, не изменяет код и не обучает LLM.
3. **Tool calling** — LLM может предложить вызвать инструмент. Приложение проверяет запрос и полномочия, код вызывает инструмент, а инструмент сообщает фактический результат. Слова модели «адрес сохранён» без успешной записи не доказывают выполнение.
4. **Права доступа:** существование инструмента не гарантирует право использовать его. Даже если LLM и главный агент ошибаются, исполнительная система/сервер обязаны отклонять неразрешённые действия (например, `permission_denied`). Главный агент должен остановить запрещённое действие и при необходимости запросить права, но не обязательно останавливать весь диалог.
5. **Обработка ошибок:** `database_unavailable` указывает на недоступность БД, но не доказывает отсутствие интернета. Нужны записи фактических вызовов и диагностика. Не выдавать успех до подтверждения; при сбое соединения возможен неизвестный исход операции.
6. **Идемпотентность:** безопасный повтор не должен дублировать эффект. Для повторного создания заказа нужны серверные механизмы уникальности и идентификатор операции (idempotency key); одно чтение перед записью не исключает гонку.
7. **Идентификация клиентов:** `customer_id` и `order_id` описывают разные сущности. Разделение гостевых и авторизованных заказов, сроки хранения данных и привязка истории требуют отдельных правил, а не только изменения JSON.

## Подтверждено самостоятельными ответами

- Пользователь объяснил смысл API через транспорт между «островами» и уточнил, что агент может получать сведения не только через сторонний веб-API, но и через разрешённый прямой доступ к базе.
- Указал, что инструмент без прав не может прочитать БД.
- Предложил добавить в JSON новое поле `delivery_address`, усвоив пары ключ–значение.
- При отсутствии адреса предложил выяснить исходные данные, записать их с помощью исполнителя, а изменения схемы и кода делегировать уполномоченному специалисту с проверкой.
- Отличил результат в JSON-ответе от долговременного хранения в БД, задумался о постоянных данных клиента и данных отдельного заказа.
- При недоступной БД предложил диагностировать причину, а не считать запись состоявшейся.
- При обрыве соединения отличил **повторный запрос на чтение** от **повторной записи**: сначала проверка состояния, потом решение о следующем действии.
- Для повторного создания заказа №126 предложил проверить наличие заказа, не создавать слепо дубль; уточнены ограничения такой проверки и атомарные меры на сервере.
- **Итоговая проверка:** для создания заказа №127 у агента есть только права чтения. Пользователь верно сказал, что программа, исполняющая инструмент, должна остановить действие и вернуть ошибку. Уточнено, что проверки полезны и на уровне главного агента, и на серверной границе полномочий.

## Как объяснить сотруднику

«API — способ, которым одна программа запрашивает сведения или действия у другой. JSON — удобный формат данных. LLM может предложить вызов инструмента, но реальное действие выполняет код с проверкой параметров и прав. Об успехе судят по результату инструмента, а не по формулировке модели. Повторы после ошибок проектируют так, чтобы не создавать дубли».
