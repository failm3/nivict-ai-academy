# F07. API, JSON и инструменты агента

> **Статус:** начат после F06. Следовательно изучаем различия API, JSON и инструментов агента. Понимание F07 пока не подтверждено.

**Опора:** [[02 - Курс/Быстрый уровень/F06 - Обучение, использование модели и ошибки|предыдущий урок]]  
**Главная мысль:** Модель может предложить вызов инструмента, но реальное внешнее действие выполняет код с определёнными правами.

## Что разберём последовательно
1. Что такое API: интерфейс между программами.
2. Запрос и ответ; JSON как формат данных.
3. Tool calling: модель выбирает действие, приложение его исполняет.
4. Разрешения и проверка входных параметров.

## Один конкретный пример
Агент запрашивает статус заказа: модель выбирает функцию get_order, сервер проверяет ID и обращается к базе.

## Зачем это будущему инженеру
Читать простые схемы API и отличать текст модели от фактического вызова инструмента.

## Зачем это для платформы создания агентов
Проектировать безопасный каталог инструментов будущих агентов.

## Короткая проверка понимания
Назвать, кто решает запросить статус заказа, кто проверяет доступ и кто возвращает сведения.

## Типичная ошибка
Полагать, что текст «я открыл файл» означает реальное действие.

## Вернёмся позже
REST/HTTP коды, схемы типов, аутентификация, собственные API.

## Начало диалога F07

- Начали разбирать API как согласованный интерфейс обмена между программами, а не как саму нейросеть.
- Пример: NIVICT Workspace запрашивает актуальный статус заказа через API сервиса заказов и получает ответ.
- Вопрос на понимание способа получения статуса заказа №125 пока открыт: занятие приостановлено для восстановления автоматической синхронизации Obsidian Git.

## Проверенное в диалоге — F07 продолжается

- **API:** после простого объяснения через ресторан пользователь предложил аналогию с корабликом между островами. Уточнили: сеть передаёт данные, API задаёт интерфейс и правила обмена; API — более широкое понятие, чем веб-запрос.
- **Доступ к данным:** пользователь верно понял, что отсутствие веб-API не всегда мешает агенту читать базу при наличии другого разрешённого инструмента, а наличие инструмента без прав доступа не позволяет читать данные.
- **JSON:** ученик объяснил, что это согласованный формат взаимодействия программ, предложил добавить поле с адресом доставки как пару ключ–значение. Сравнили структурированное поле с извлечением данных из произвольного текста.
- **Недостающее поле:** ученик правильно отказался от выдумывания адреса и предложил его выяснить. Дополнительно предложил проверяющего и разделение ответственности между главным агентом, исполнителем, разработчиком и проверяющим. **Уточнение:** сначала поискать адрес в разрешённых авторитетных источниках; если отсутствует, уточнить у уполномоченного лица; при правах на запись сохранять через валидируемый инструмент. Добавление поля к JSON-ответу, запись в БД и изменение схемы/кода — три разных действия. Накопление данных не означает изменение весов LLM.
- Архитектурная идея добавлена как [[03 - Практика/03 - NIVICT Workspace — реестр идей из обучения|W-13]] (не заявлять о реализации). При этом главный агент должен знать статус, полномочия и критерий завершения делегированной работы, даже если не реализует её самостоятельно.
- **Следующий учебный шаг:** закрепить разницу между временным JSON-ответом, записью в БД и изменением программной схемы; затем переходить к tool calling.
