# F16. Приложение с LLM, дообучение и своя модель

> **Статус:** завершён на вводном уровне; понимание проверено на задачах NIVICT.

**Опора:** [[02 - Курс/Быстрый уровень/F15 - Безопасность и участие человека|предыдущий урок]]  
**Главная мысль:** Использовать готовую LLM, дообучить существующую и обучить новую с нуля — три разных инженерных проекта.

## Что разберём последовательно
1. Готовая LLM через API или локальный сервер.
2. Настройка с контекстом, RAG и инструментами.
3. Fine-tuning/дообучение существующих весов.
4. Обучение с нуля: данные, вычисления, эксперименты.

## Один конкретный пример
Нужен агент поддержки: сначала проверяем готовую модель с документами, а не строим фундаментальную LLM с нуля.

## Зачем это будущему инженеру
Отличать Applied AI Engineer от ML/LLM Research Engineer и не переоценивать опыт интеграции API.

## Зачем это для платформы создания агентов
Выбирать способ использования моделей, не смешивая создание агента с обучением сети.

## Короткая проверка понимания
Разнести примеры «подключить API», «дотренировать модель» и «обучить архитектуру с нуля» по трём сценариям.

## Типичная ошибка
Называть настройку промпта созданием собственной LLM.

## Вернёмся позже
Датасеты, Transformer, градиенты, LoRA, GPU и лицензирование моделей.

## Подтверждено в диалоге — начало F16

- На выбор архитектуры поддержки по документации «Сайт Жив» пользователь первоначально ответил «своя модель с нуля», затем уточнил **двухконтурную стратегию**: готовая LLM для задач и оптимизации сейчас, параллельно — исследования и развитие собственной LLM для команды, проектов и личных интересов. Мотивы: больший контроль над данными и собственной инфраструктурой, стратегическая независимость. Пользователь понимает, что обучение с нуля дорого и ресурсозатратно.
- Техническое уточнение: для ответа по проектной документации **необязательно обучать модель с нуля или записывать знания в веса**. Готовая (в том числе локально размещённая) LLM + RAG/внешняя память + инструменты может использовать актуальные документы. Fine-tuning меняет параметры существующей модели; обучение from scratch — отдельный крупный проект. Собственные серверы дают контроль над размещением, но не исключают взлом, ошибки настройки, внутренние угрозы и утечки; нужны реальные меры безопасности.
- Рекомендовано разделить краткосрочный прикладной проект и долгосрочные эксперименты с обучением моделей; решение о создании модели с нуля принимать на основании задач и результатов сравнения с адаптацией существующих моделей.
- Следующий вопрос: какой из трёх подходов нужен, если обновили тарифы в документации и агент должен сразу отвечать по новой цене, без ожидания переобучения.

- На вопрос об изменении тарифов «Сайт Жив» пользователь правильно выбрал **RAG**: модель должна получить актуальные сведения из внешней базы знаний без обучения весов.
- Уточнено: обновление источника не всегда мгновенно отражается в ответах — индекс поиска и кеши могут устаревать. Для **точных цен** предпочтительнее прямой запрос к авторитетной базе тарифов через API с проверкой актуальности; RAG уместен для объяснений по документации. Отличие: RAG обновляет внешний контекст, а fine-tuning изменяет веса модели.
- Следующий вопрос: когда вместо RAG оправдан fine-tuning, например если агент располагает актуальной базой знаний, но систематически неправильно оформляет ответы или не соблюдает специальный формат.

- На вопрос о нарушении формата и стиля ответов при актуальной базе знаний пользователь правильно назвал **Fine-tuning**, связав проблему с адаптацией весов модели, и отметил, что RAG тоже может помочь в зависимости от контекста.
- Уточнение: fine-tuning — возможный инструмент для устойчивого поведения/стиля на хорошо подготовленных примерах, но строгий машиночитаемый формат сначала обеспечивают structured outputs/JSON Schema и программная валидация. RAG даёт документы и примеры в контексте, не обновляя веса модели. Для решения о fine-tuning нужны измеримые evals и сравнение с более дешёвыми мерами.
- Следующий вопрос F16: в каких случаях обучение новой LLM с нуля оправдано и почему это не то же самое, что создавать собственного ИИ-агента на готовой модели.

- На вопрос о принципиальном различии между созданием собственной LLM и созданием агента пользователь прямо ответил **«не знаю»**, предпочёл не гадать. Тему нельзя считать проверенно усвоенной до следующего ответа.
- Объяснено на примере NIVICT: создать LLM с нуля — обучать нейросеть, меняя её веса на данных с большими вычислительными затратами; создать агента на готовой Qwen — соединить модель с инструментами (GitHub, браузер, файлы), памятью, правилами, оркестрацией и проверками **без изменения весов**. Собственный агент не требует обучения собственной LLM. Следующая короткая проверка: при локальной Qwen + GitHub + память + проверяющий что именно создано?

- После объяснения пользователь самостоятельно правильно ответил на контрольный пример: локальная Qwen + GitHub + память + проверяющий — **собственный ИИ-агент на основе готовой LLM**, а не создание новой LLM. Различие между моделью и агентной системой подтверждено на простом примере; обучение LLM с нуля и критерии его целесообразности ещё требуют проверки.
- Следующий вопрос: когда обучение LLM с нуля действительно разумнее адаптации готовой модели (RAG/fine-tuning), с учётом требуемых возможностей, данных, бюджета и ограничений.

- На вопрос о необходимости обучения LLM с нуля пользователь предложил этот путь, если готовая модель не выполняет **критические требования**; самостоятельно выделил три фактора решения: требования, ресурсы и время/сложность задачи. Уточнено: неудача одной готовой LLM **не доказывает необходимости обучения с нуля**. Сначала сравнить другие модели, RAG/инструменты, допустимые способы адаптации и результаты Evals. From scratch оправдан только при фундаментальных ограничениях существующих решений и наличии необходимых данных, ресурсов и экспертизы.

## Итоги урока F16

**Понял своими словами:** собственный агент на базе готовой LLM не равен собственной модели. RAG использует внешние актуальные знания без изменения весов; Fine-tuning меняет веса существующей модели для адаптации поведения; обучение с нуля — отдельный дорогостоящий исследовательский/инженерный проект.

**Проверено на сценариях:**
- Предложил долгосрочный двухконтурный подход NIVICT: готовая модель для текущих задач, параллельное развитие собственной технологии.
- При изменении тарифов «Сайт Жив» правильно выбрал RAG; уточнили, что для точных цен лучше актуальный API/БД и важно обновление поискового индекса/кеша.
- При повторяющихся нарушениях стиля/формата назвал Fine-tuning; узнал о более надёжной программной валидации формата.
- После объяснения самостоятельно правильно определил Qwen + память + GitHub + проверяющий как **агента на готовой LLM**, а не собственную LLM.
- Для from scratch учёл критические требования, ресурсы и время; скорректирована избыточная уверенность, что любая непригодная готовая модель требует обучения с нуля.

**Новые понятия:** готовая модель через API или локальный сервер, RAG, Fine-tuning, Training from scratch, model weights, Evals, агент vs модель.

**Граница владения:** вводная теория; обучать LLM, подготавливать fine-tuning датасеты, выбирать гиперпараметры и оценивать экономику обучения практически ещё не умеет. Выбор конкретного подхода требует тестов.

**Как объяснить сотруднику:** «Для знаний и данных используем базу и инструменты; для устойчивого поведения иногда дообучаем готовую LLM; модель с нуля создаём только при доказанной невозможности удовлетворить требования более доступными способами».
