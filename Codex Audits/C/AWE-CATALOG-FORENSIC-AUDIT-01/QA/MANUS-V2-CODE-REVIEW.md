## Limits that must remain explicit

**LIVE_TESTED is a recorded attestation, not an independent test runner.** `record_live_test` stores the supplied result, evidence URL and hash; it does not retrieve the evidence, recompute its content hash or execute a sandbox test (`registry.py:112–123`). The input model checks a 64-hex hash format, result enum and nonfuture timestamp (`models.py:138–161`). Those checks reject malformed inputs but do not establish that a supplied passing result is truthful. `exporting.py:20` explicitly acknowledges the human-attested boundary. This is a design scope limit, not proof that the four historical smoke tests were fabricated.

**An actor string does not prove independent reviewer identity.** Approval requires actor/reason and valid lifecycle/test links (`registry.py:143–161`), but the helper does not establish a second model family, separation of duties or signed owner identity. HTTP reader/admin separation is claimed in `CORE_STATUS.md:28`; the API/auth implementation and deployment were outside this source slice. No claim that authentication is absent is made.

**The fingerprint is scoped metadata.** It hashes official/repository URLs, resource type, integration names, all recorded version strings and the latest integration-spec/pricing/license hashes (`registry.py:30–39`). It does not include descriptions, capabilities, provenance, generic assertions or verification-run histories. A deployed executable/image digest, actual installed configuration, secrets policy and backend state are not established by those fields alone; a separately validated integration specification could carry some of them, but that binding was not proven here. Adding newly observed releases can also invalidate an earlier fingerprint even when the installed artifact is unchanged. Therefore “fingerprint matches” must not be paraphrased as “same deployed safe tool.”

**Provenance integrity is not source authenticity.** `add_provenance` hashes submitted source URL, post URL and message ID (`ingest.py:72–82`); it does not independently establish ownership, post accuracy or that a linked post supports the resource claim. A provided `raw_hash` is accepted rather than recomputed against provided raw content (`ingest.py:33–46`); `PostImport` has no corresponding hash-content validator (`models.py:49–81`). Independently computed post-version hashes provide useful version tracking, while the claimed raw hash and provenance pointers retain their original trust limits. No record-content defect is inferred solely from this limitation.

**License metadata is insufficient for the reviewed shortlist.** The verifier intentionally omits license-text inspection (`verification.py:81–100`). This cannot resolve Agent Zero's metadata NOASSERTION versus MIT text, the MCP licensing transition, or enterprise-directory exclusions in Mastra/LiteLLM/Activepieces/Langfuse/Infisical. The separate high-risk source review supplies additional text-level evidence; the old `license_evidence` table alone is not a full license audit.

**Normalization is not semantic uniqueness.** `models.py:18–35` strips fragments/trailing slashes, sorts query pairs and removes tracking parameters. `intelligence.py:26–41` reduces deep GitHub/package links to entity roots. These are explicit identity heuristics that can merge meaningful resource distinctions, especially query order or fragments. `intelligence.py:59–69` correctly labels capabilities and entity normalization as unverified. They must not become a unique-tool count or code-function evidence.

**The hourly recheck is bounded, not comprehensive monitoring.** Scheduling is limited to ten jobs per hour and selected GitHub/PyPI URL patterns (`intelligence.py:99–113`). The reviewed verifier implements URL/GitHub/license/release observations, not a general semantic price/license-change agent (`verification.py:28–129`). The report itself lists missing adapters and unfinished deep verification (`DELIVERY_STATUS.md:35`, `59`). Reading a scheduling function does not prove an hourly service is running.

**Export privacy is contextual.** `write_private` uses a temporary file, restrictive POSIX-style modes, fsync and replace (`exporting.py:23–32`). Research export serializes complete resource detail (`35–43`) without a content redaction pass in this function. Imported descriptions, claims, notes and provenance therefore require publication review. File-mode calls alone are not a cross-platform ACL or secret-removal guarantee. The current deliverable pattern scan is separate evidence and is not a general proof of privacy safety.

## Historical snapshot versus current AWE

The supplied registry really contains **3,415** rows. Independent data review found DISCOVERED=3,403, DOCUMENTED=8 and LIVE_TESTED=4, with zero approvals/export approvals. The code explains why a full research export can contain thousands of resources while the executable/integration export remains empty. `DELIVERY_STATUS.md:19–25` describes heuristic candidates and an unresolved backlog; `21` limits the four library smoke tests; `53` explicitly records APPROVED=0 and INTEGRATED=0.

The historical count and source-only bundle do **not** prove the current 12-row working AWE database has imported the complete registry. They also do not prove a native TR-01 adapter, current Head/tool routing, a running 24/7 service, or owner acceptance. The archive's three-row `research/live_stack_resources.jsonl` is another artifact and is not a snapshot of that working database. No current DB readback was taken by this audit.

The original material is candid about these boundaries: no old 4,504 catalog was available/imported (`CONTRACT.md:13`, `DELIVERY_STATUS.md:23`), WSL/systemd operation was unconfirmed (`DELIVERY_STATUS.md:43–47`), and current cleanroom/TR-01 compatibility and actual OpenCode import were not tested (`51–55`). The four-library tests, 55-test run, backup restore and HTTP observations in `DELIVERY_STATUS.md:21`, `29–37` remain archived claims/evidence; none was rerun during this read-only review. `CORE_STATUS.md:11` separately says Docker/Compose runtime and service deployment were not exercised there.

## Reuse assessment within this audit

The preserved claim taxonomy, explicit provenance, idempotent import, lifecycle history, stale-evidence rejection and separate research/approved exports are useful design assets to **PILOT** against the owning AWE schema. They are not an accepted drop-in runtime or a reason to implement TR-01 in this audit.

A later authorized pilot should independently test forged imported verification labels, nonexistent evidence with a well-formed hash, revoked approval, stale/future timestamps, changed operational specification, changed license/version metadata, contradictory source pointers, alias collisions and mutation during export. It should also prove authenticated actor identity, least-privilege access, publication redaction and exact transfer/readback into a disposable AWE-compatible schema. All such proposed tests are **NOT_RUN** here.
